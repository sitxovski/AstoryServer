## L03 — отказ по апострофу в логине/пароле (до сборки SQL)

**Дефект.** Логин и пароль из пакета подставляются в одинарные кавычки SQL без экранирования;
клиентского фильтра на эти поля в срезе нет. Апостроф закрывает литерал — остаток уходит в SQL Server
как код (инъекция). Это **второй рубеж** к защите в самой процедуре.

**Исправление (★).** Перехват КОНКРЕТНОГО `call sub_40F440` @`0x407263` (5 б `e8 d8 81 00 00`) в обработчике
входа. Трамплин проверяет логин (`[esp+0x1C]`) и пароль (`[esp+0x20]`): если в любом есть апостроф —
сборщик НЕ вызывается, ставится `*out = 0` и возврат 0. Обработчик входа при `out==0` уходит в штатную
ветку «UPUserLogin Error» — клиент получает отказ. Иначе — хвостовой `jmp` в настоящий `sub_40F440`,
стек не тронут (вызывающий `add esp,0x38` снимает 14 аргументов).

Хук стоит ТОЛЬКО на логин-запросе ⇒ остальные запросы (имена, заметки, где апостроф легитимен) не затронуты —
в отличие от хука на входе общего сборщика.

Ключи `[L03_LoginSqlRefuse]`: `Enabled` (0 — сток), `MaxScan` (32..4096, предел сканирования поля),
`LogHits` (строка в журнал на отказ, без текста логина).

## L02 — маскировка текста `EXEC UPUserLogin …` в журнале ошибок базы (OLEDB_LOG)

**Дефект.** При ошибке базы `sub_40F440` пишет полный текст запроса в лог
(`sub_410C00(…,"%s :: Execute Error", MultiByteStr)` и `sub_4128E0("… %s", …, MultiByteStr)`). Для входа это
логин, MD5 пароля (без соли), IP и MAC открытым текстом.

**Исправление (★).** Детур сразу ПОСЛЕ `MultiByteToWideChar` (@`0x40F5BC` — это трамплин P17), на
`0x40F5C2` (6 б `89 85 d8 ef ff ff`, `mov [ebp-0x1028],eax`). К этому моменту ШИРОКИЙ буфер уже построен и
именно он исполняется, а узкий `MultiByteStr` (`ebp-0x1020`) дальше нужен только логам. Трамплин
воспроизводит затёртую инструкцию, затем (если текст содержит «UPUserLogin») заменяет содержимое всех `'…'`
на `*` — форма и длина запроса сохраняются, исполнение не затронуто. Другие запросы в логах не меняются
(маска только при «UPUserLogin»).

Результат: `EXEC UPUserLogin '****','********…','*************', 2, '*****************'`.

Ключи `[L02_LoginSqlLogMask]`: `Enabled` (0 — сток), `LogHits` (отметка в журнал установки).

## fix13 (2026-10-13) — L03 не зависит от порядка установки с L06 (ревизия integ2, НИЗК)

- **Было:** L06 делит площадку `call sub_40F440` @0x407263 и встраивался цепочкой только ПОСЛЕ L03. Если L06 ставился раньше
  (другой порядок реестра/ручной вызов), L03 видел не сток → `MISMATCH`, и отказ по апострофу в логине/пароле молча пропадал
  (стенд ревизора `stand_l0306`, порядок 6→3).
- **Стало:** L03 при не-стоковой площадке спрашивает у L06 адрес его трамплина (`L06_TrampolineAddr()`, экспорт L06 — не
  «любой чужой call») и, если на площадке ровно `call L06_Trampoline`, встаёт в слот «следующее звено» L06 через
  `L06_ChainNext(sub_40F440 → L03_Trampoline)` (сравнение с обменом). Итог при любом порядке: site → L06 → L03 → сборщик.
  Любой другой чужой call — по-прежнему `MISMATCH`. Реестр (порядок L03 → L06) не менялся.
- Проверка: `tools/test_l06.cpp` — раздел «установка»: настоящие `L03_LoginSqlRefuse()`/`L06_LoginMac()` на подставной
