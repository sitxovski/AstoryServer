# L07 — шифрование трафика (прослойка AsdaSecure) в LoginManager

Дата: 12.10.2026. Волна В7b «врезка». Основание: «Дополнение 11.10» в `Reports/anticheat/00_PLAN.md`.
Дизайн: `AstoryServer/Docs/_Common/traffic-encryption-design.md`. Зеркало на GameServer — P61.

Исходники (в КОПИИ, не в деплойной сборке): `AstoryServer/_archive_waves/LoginPatch_w07/` (патч `src/patches/l07_traffic_encryption.cpp`,
адреса `src/LoginApi.h`, секция `src/Config.cpp`, реестр `src/patches/Registry.cpp`, сборка `build.bat`
линкует `../AsdaSecure/src/*` + `bcrypt.lib`). Библиотека — `AstoryServer/Patches/AsdaSecure/` (мост `AsdaServerBridge`).

## Что делает
Прослойка между сокетом и разборщиком старого кадра `FB|size|A|B|op…FE`, НЕ меняя старый протокол:
- **приём** клиентского слота → расшифровка AEAD → стоковый разборщик;
- **отправка** → шифрование AEAD перед `WriteFile`;
- **accept/disc** → Reset канала слота.

Схема TLS-типа: эфемерный ECDH P-256 на подключение, подпись сервера ECDSA P-256 (открытый ключ вшит
в клиент), AES-256-GCM с номером кадра (anti-replay `seq==rx+1`), ключи направлений из HKDF-SHA256.
Закрытый ключ — файл `secure_server.key` рядом с `LoginManager.exe` (кладёт владелец, генерит `keygen`);
нет файла → шифрование не включается. Крипто — только Windows CNG (`bcrypt`).

## Точки врезки (образ LoginManager, база 0x400000; сверено verify_traffic.py на живом 12dcd9f1 и деплое 51db86b2)
Способ — замена `call`-инструкций (как у остальных патчей) + один детур входа `SetConnectFlag`.
Межсерверные слоты (10000..10099) НЕ трогаем (связь под-серверов — отдельная волна).

| Площадка | VA | Оригинал (5 б) | Действие |
|---|---|---|---|
| приём клиента (IoWorkerThread `sub_4161E0`) | `0x4165B5` | `e8 46 f0 ff ff` (call `sub_415600`) | → `L07_RecvTramp` (расшифровка) |
| отправка (Ciocp::Send, site 1) | `0x4159F8` | `e8 b3 e0 ff ff` (call `sub_413AB0`) | → `L07_SendTramp` (шифрование) |
| отправка (site 2) | `0x415F1E` | `e8 8d db ff ff` | → `L07_SendTramp` |
| Reset канала (вход `SetConnectFlag sub_4144A0`) | `0x4144A0` | `55 8b ec 6a ff` | детур → `L07_SetConnTramp` → Reset, продолжение `0x4144A5` |

Стоковые функции зовутся трамплинами напрямую (вход не хукнут): recv-синк `sub_415600` (this=ecx; buf,size,slot; ret 0xC),
`Ciocp::Send sub_413AB0` (this=ecx; slot,Src,nBytes; ret 0xC — также для отправки ServerHello). `SendTemp sub_4141D0`
НЕ хукаем: он дослыает УЖЕ зашифрованный буфер слота. Синтетические вбросы accept/disc (0x415594/0x4156EE/0x415804)
НЕ хукаем — это локальные кадры, не с провода.

## Трамплины (ABI, x86)
- **RecvTramp**: вход ecx=this, `[esp+4]=buf [esp+8]=size [esp+0xC]=slot`, ret 0xC. Зовёт cdecl `AsdaWire::OnRecv`
  (расшифровка в per-slot скретч; ServerHello/очередь — через `SendRaw`=стоковый `Ciocp::Send`), затем стоковый
  `sub_415600` с расшифрованным потоком. Пусто → парсеру ничего не отдаётся.
- **SendTramp**: вход ecx=this, `[esp+4]=slot [esp+8]=Src [esp+0xC]=nBytes`, ret 0xC. ★ fix2: зовёт cdecl
  `AsdaWire::SendRoute(this,slot,Src,n)` — шифрование и стоковый Send под замком слота; при незавершённом рукопожатии кадр
  в очереди канала (уйдёт за ServerHello). Возврат eax — итог стокового Send. (До fix2: `OnSend` в скретч, Send — после
  выхода из замка.)
- **SetConnTramp**: детур входа, `pushad` → `AsdaWire::ResetSlot(slot)` (★ fix2: только запрос сброса, без замка) →
  `popad` → украденный пролог → `0x4144A5`.

## Состояние и потоки
Таблица каналов на слот (0..549), у каждого своя критическая секция. IOCP крутит несколько рабочих потоков;
`Ciocp::Send` берёт свой лок уже ПОСЛЕ нашего call-site, поэтому per-slot состояние (seq, накопитель) мы
защищаем своей секцией. CNG/bcrypt открывается **лениво** (первый вызов трамплина на рабочем потоке IOCP),
а НЕ в DllMain (там грузить модули нельзя).

### ★ fix2 (13.10.2026, ревизия INTEG3 Б-1/Б-2): порядок замков «слот → Ciocp»
- Замок Ciocp **L** = `this+0x60D1830` (вход `0x41A620`); берут его 6 функций (`0x4138D0` DisConnect, `0x413AB0` Send,
  `0x4141D0` SendTemp, `0x4144A0` SetConnectFlag, `0x414550` GetConnectFlag, `0x416AB0`), `0x412AC0`/`0x413550` его
  создают/удаляют (метод — `verify_traffic.py`, совпало со списком ревизора).
- Детур `SetConnectFlag` вызывается под L (DisConnect `0x41390B → 0x41399B → 0x4155A3`) и **замок слота не берёт**: только
  запрос сброса (`InterlockedIncrement`), сброс применяется под замком слота при следующем приёме/отправке. Прежде —
  взаимная блокировка с потоком приёма, державшим замок слота и ждавшим L в Send ServerHello.
- Отправка — `AsdaWire::SendRoute`: шифрование и стоковый Send `0x413AB0` одним куском под замком слота (трамплин стоковый
  Send больше не зовёт). У LM логика однопоточная (`0x4022D0`), но порядок замков тот же.
- Сбой CNG: байты идут как есть (AllowLegacy=1 — старые клиенты работают; AllowLegacy=0 — соединение закрывается на
  первом приёме). Запись площадок: детур SetConnectFlag первым, при сбое — откат записанных к оригиналу.
- Журнал (общий AcJournal): строки обрезаются до ширины колонок `joylog1.ac.*` (после SQL `acj2`), файловый журнал при
  недоступной базе — не больше `FileRowsPerMinute` (3000) событий в минуту и `MaxFileMB` (256) в сутки (флуд видом 58 давал
  ~10 МБ/мин без предела).

### ★ fix2b (13.10.2026): отказы до рукопожатия (4101 код 22, 2253) не теряются
LoginManager на accept (20000 → `CUserProc::ProcConnect sub_405A90`, логический поток `0x4022D0`) шлёт до первого байта клиента:
заблокированный IP — `4101` {22} (без разрыва, `LoginManager.c:1974-1980`); переполнение — `2253` и сразу DisConnect `0x4138D0`
(`:1998-2006`). Прежде кадр вставал в очередь канала и стирался сбросом при разрыве — игрок не видел причину. Теперь: очередь
слота моста (`PreHandshakeQueueKB`, 64 КБ), детур **входа DisConnect `0x4138D0`** (украдено `55 8b ec 6a ff`, продолжение
`0x4138D5`) — ворота `AsdaWire::DisconnectGate` откладывают разрыв до выдачи очереди (сразу за ServerHello — Secure; как есть —
старый клиент) или до `PreHandshakeCloseMs` (5000) без байтов клиента; DisConnect из IoWorkerThread `0x4161E0…0x4167E0` не
откладывается. Детур `SetConnectFlag` передаёт флаг (1 accept / 0 разрыв). Клиент: правка не обязательна (защитная —
`Reports/anticheat/wFIX2_logs/client_prehandshake.diff`).

### ★ fix2c (13.10.2026, ревизия FIX2): предел буферов стока 0x1000
Та же библиотека Ciocp, что у GameServer: `Ciocp::Send 0x413AB0` копирует в буфер записи 0x1000 б (`0x413ECE`, `0x414054`) — при
большей длине уходят нули; `ReadFile` по 0x1000 (LoginManager.c:8180…8250), разборщик `sub_415600` → `CopyToWriteBuffer 0x418C00`
(пакет ≤ 0x2BC). Мост: кадры шифрования ≤ 0x1000 на вызов Send (открытый текст ≤ 4068 на кадр), ServerHello и очередь до рукопожатия
покадрово, приём разборщику кусками ≤ 4087 (`SetRecvSink`). Отложенный разрыв — не раньше `PreHandshakeLingerMs`=150 мс после выдачи
(сокет закрывается RST: `SO_LINGER {1,0}` `0x4188C1…0x4188F1`), поколение слота (Н-3: `DisConnect_NoLock 0x413A10` мимо ворот), разрыв
из IoWorker не откладывается (Н-4).

### ★ fix2d (14.10.2026, хвост ревизии FIX2): переполнение досылки стока
Тот же код Ciocp, что у GameServer (сдвиг −0x14E470): `Ciocp::Send 0x413AB0` при записи в полёте (`+8`, `0x413B91`) дописывает кадр в
досылку (длина `+0xA0B2`, `0x413BB1`) и при длина + кадр ≥ 0x9F9C (`0x413BBB`) стирает её вместе с зашифрованными кадрами; `SendTemp
0x4141D0` (зовёт только IoWorker `0x4166E4`) выдаёт досылку под тем же замком `this+0x60D1830` (RAII `0x41A620`). Мост — как в P61:
проверка места под замком Ciocp, очередь слота моста (`TxQueueKB=1024`), отказ стока / переполнение / потеря кадра (пул `0x4199A0`) —
строка `L07: [досылка] …`, `ac.other` 61, разрыв сторожем. Legacy — как сток; новых площадок нет; раскладка сверена `verify_traffic`
на трёх образах LM.

### ★ fix2e (14.10.2026, ревизия fix2d Ф-1): общий предел очередей моста и нехватка памяти
Как в P61 (`../GameServer/traffic-encryption-p61.md`, раздел fix2e): общий на процесс предел очередей моста `TxQueueTotalMB=64`
(Interlocked-счётчик, резерв до выделения памяти; сверх — разрыв этого слота, `ac.other` 61 причина 4, `value2` = общий объём);
сбой выделения памяти внутри моста перехвачен под замком слота — разрыв слота (причина 5), исключение в трамплин и сток не выходит,
LoginManager (без LAA, 2 ГБ) не падает. Новых площадок нет.

## Совместимость перехода
`AllowLegacy=1` (умолчание): старый клиент (первый байт `0xFB`) идёт без шифрования; `0xA5` — рукопожатие.
Когда все клиенты обновлены — `AllowLegacy=0` закрывает старый протокол.

## Конфиг (`ConfigSet\patches.ini`, секция `[L07_TrafficEncryption]`)
- `Enabled=0` — ★ по умолчанию ВЫКЛ (сток, трамплины не ставятся);
- `AllowLegacy=1` — старый клиент без шифрования (переход);
- `KeyFile=secure_server.key` — имя файла закрытого ключа рядом с `LoginManager.exe`;
- ★ fix2d `TxQueueKB=1024` — очередь шифрованных кадров слота при полной досылке стока, КБ (0…65536; 0 — без очереди, сразу разрыв).
- ★ fix2e `TxQueueTotalMB=64` — общий предел очередей моста на процесс, МБ (1…1024); сверх — разрыв слота, `ac.other` 61 причина 4.

## Ограничения (эта волна)
- Ошибка целостности (BadTag/Replay/BadMagic) → кадр **отбрасывается** (0 байт разборщику); активный кик не делаем —
  снимет стоковый idle-таймаут. Активный разрыв по ошибке — отдельной волной.
- Межсерверные соединения не шифруются.

## ★ sec2 (15.10.2026, блок В плана альфы) — Е-1, Е-2, ускорение рукопожатия, допуск подключений до рукопожатия
Отчёт: `Reports/anticheat/wave_SEC2_20261015.md`. Мост `AsdaSecure/src/AsdaServerBridge.{h,cpp}`, `AsdaSecure.{h,cpp}` — общие
для L07 и P61. Новых площадок нет; детур входа `SetConnectFlag` дополнительно передаёт `this` Ciocp (`push ecx` в трамплине,
`ResetSlotEx`). Порядок замков прежний: «слот → Ciocp»; таблица адресов допуска — свой SRW-замок, листовой.
- **Е-1 (ревизия fix2e):** очередь моста слота, упавшего НЕ по виду 61 (сбой шифрования отправки; нарушение приёма при
  `KillOnViolation=0`; отказ допуска), освобождается сразу (`MarkFail` → `TxFreeLocked`; сторож — для любого сбойного слота).
  Место в общем пределе не держится до сброса слота; счёт — через единственную точку обнуления `txBytes`.
- **Е-2 (ревизия fix2e): справедливая доля общего предела.** Постановка, после которой сумма очередей > `TxQueueTotalMB`:
  слот «тяжёлый» (его очередь ≥ средней по слотам с непустой очередью или ≥ `TxQueueFairKB`) — рвётся сам (вид 61 причина 4,
  как fix2e); «лёгкий» (честный клиент грузит карту) — кадр принят, пока сумма ≤ предел + предел/8 (жёсткий потолок), а сторож
  (раз в 50 мс) вытесняет НАИБОЛЬШУЮ очередь процесса — вид 61 **причина 6** «общий предел — вытеснена наибольшая очередь»;
  сверх потолка — причина 4. Почему так, а не «всегда рвать наибольшую»: тяжёлый рвётся синхронно (предел держится без ожидания
  сторожа), лёгкий не страдает от чужого затора; поиск наибольшей — без чужих замков в пути отправки (сторож берёт замок только
  жертвы); жёсткий потолок ограничивает память и при опоздании сторожа.
- **Ускорение рукопожатия:** ключ подписи импортируется в CNG ОДИН раз (`HandshakeKeyCache=1`; до 16 дескрипторов, каждый в
  момент подписи у одной нити); пары ECDH P-256 заранее готовит фоновая нить пониженного приоритета (`HandshakePool=16`), каждая
  пара одноразовая (запись пула затирается при выдаче, дескриптор уничтожается после вывода ключей), старше 10 мин не выдаётся;
  пул пуст — генерация на месте. Ключи только в памяти процесса, на диск ничего не пишется. Протокол не менялся. Стенд: ~2,0 мс →
  ~0,83 мс CPU нити приёма на рукопожатие (`stand_sec2` Х).
- **Допуск до рукопожатия (стойка в интернете):** проверка — один раз на соединение, на первом приёме или сторожем ≤ 50 мс после
  accept (если клиент молчит), до разбора байт (ServerAccept не выполняется):
  - `ConnPerIpMax=120` за `ConnPerIpWindowSec=60` — с одного адреса больше → разрыв, `ac.other` **63** (`value1` счёт в окне,
    `value2` предел, `value3` окно, с; одна строка на адрес за окно);
  - `MaxPendingHandshakes=64` — соединений «accept есть, рукопожатие не завершено» на процесс больше → новое разорвано, **64**;
  - `HandshakeDeadlineMs=10000` — рукопожатие не завершено за срок после accept → разрыв сторожем, **65** (молчащий сокет — только
    при `AllowLegacy=0`); отложенный разрыв fix2b срок не отменяет;
  - разрыв — штатный `GetConnectFlag + DisConnect` под замком Ciocp только своего поколения; PatchLog «[допуск]» (ограничитель
    `LogPerMinute`), 64/65 — не чаще `AdmissionLogGapMs=5000`. Соединения, принятые до первого обращения к мосту, тоже учтены.
  - Числа: 50 тестеров за общим NAT — вход + повтор = 100 подключений с адреса, запас до 120 в минуту; поток с одного адреса — не
    больше 2 рукопожатий/с (≈0,2 % ядра); незавершённых одновременно у 50 тестеров ≤ 50 (рукопожатие длится 1 RTT) — 64 с запасом,
    злоумышленник держит не больше 64 из 550 слотов и не дольше 10 с; клиент ждёт рукопожатие 5 с — срок сервера вдвое больше.
- Конфиг (новые ключи, DLL допишет сама): `TxQueueFairKB=256`, `HandshakeKeyCache=1`, `HandshakePool=16`, `ConnPerIpMax=120`,
  `ConnPerIpWindowSec=60`, `MaxPendingHandshakes=64`, `HandshakeDeadlineMs=10000`, `AdmissionLogGapMs=5000`.
- Не покрыто: при сбое CNG (мост «как есть») допуска нет; таблица адресов 4096 записей — переполнена (≥ 4096 разных адресов в
  окне) → новый адрес пропускается без счёта (`admTableFull`).

## ★ sec2b (15.10.2026, ревизия SEC2 С-1 / Н-1 / Н-2 / Н-6) — LoginManager (L07)
Ревизия: `Reports/anticheat/review_SEC2_20261015.md`; отчёт: `Reports/anticheat/wave_SEC2b_20261015.md`. Мост
`AsdaSecure/src/AsdaServerBridge.{h,cpp}` (общий для P61 и L07); новых площадок нет.
- **С-1:** при `AllowLegacy=1` молчащий сокет (ни байта) по сроку `HandshakeDeadlineMs` по-прежнему не рвётся (старый клиент мог
  открыть его заранее), но **снимается со счёта незавершённых рукопожатий** — молчащие больше не держат `MaxPendingHandshakes`
  (и предел адреса) бессрочно. Снятый потом заговорил (ClientHello / первый байт 0xFB) — работает как обычно, второго вычета нет.
- **Н-1:** новый ключ `MaxPendingPerIp=16` — не больше N незавершённых рукопожатий с одного адреса (0 — без предела). Сверх — новое
