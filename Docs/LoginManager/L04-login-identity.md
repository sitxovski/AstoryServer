# L04 — привязка номера учётки (UserIndex) к сессии

- **Дата:** 12.10.2026
- **Статус:** ✅ L04a+L04b выложены 12.10 12:45 (первый старт 12:53: Applied, Mismatch 0); ✅ **L04c (соулмейт, режим 2) сделан и выложен 12.10 13:10** в `LoginPatch.dll` `a5ac8328…` — рестарт за владельцем
- **Процесс:** LoginManager — `\\@@ASTORY_SERVER_HOSTNAME@@\h(@@ASTORY_SERVER_HOSTNAME@@_ns)\ASDA\Working_ASDA\v2\LoginManager\LoginManager.exe`
- **Тип:** байт-правка (L04a) + код-врезка (L04b) в памяти через `LoginPatch.dll`
- **Загрузчик:** [loginpatch-dll-loader.md](loginpatch-dll-loader.md)

## Модель личности сессии

При входе (1003) обработчик сохраняет подтверждённый `UserIndex` в слоте сессии
`*(DWORD*)(&dword_66B4DA0 + 143*session + 759878)` (пишет `sub_4037B0@0x4037B0`, `ret 8`).
Читает его `sub_4038B0@0x4038B0` (__thiscall this=`&dword_66B4DA0`, a2=session; `ret 4`).
Это и есть «номер сессии», с которым L04 сверяет приходящий в пакетах `UserIndex`.

## L04a — 1016 (выбор персонажа, `sub_40AD30`), режимы 0 и 1

**Дефект.** Сверка `UserIndex` с сессией (`sub_4038B0`) стояла только на режиме 0
(`!LOBYTE(v109[0])`). Режим 1 (вход «душой», SoulState 1 — байт режима уходит 4-м аргументом в
`UPCharSoulState`; режимы: 0 обычный, 1 душа, 2 соулмейт) проваливался мимо проверки — клиент подставлял
любой `UserIndex` (дыра F2, подмена личности). ★ Ранее здесь ошибочно стояло «реконнект».

**Исправление (★).** Правка условия гейта на `0x40B1AB` (8 байт):

```
85 c0 0f 85 a6 00 00 00   test eax,eax ; jne 0x40B259   (сверка только при режиме 0)
3c 02 0f 84 a6 00 00 00   cmp al,2     ; je  0x40B259   (пропуск только при режиме 2)
```

Теперь сверка `sub_4038B0(session) == *(v109+1)` идёт для режимов 0 И 1 (обычный и «душа» — оба своим
персонажем); режим 2 (соулмейт) уходит своей веткой — его закрывает L04c. Поведение режима 0 не меняется.

## L04b — 1005 (список персонажей, `sub_407CE0`)

**Дефект.** `UserIndex` (word `[ebp-0x24]`) брался из пакета и НЕ сверялся с сессией — список
персонажей любой учётки по её номеру (дыра F4).

**Исправление (★).** Перехват `call sub_40F440` (UPCharExist) на `0x407FD2` (5 б `e8 69 74 00 00`).
Трамплин: `sub_4038B0(&dword_66B4DA0, [ebp+8])` → `UserIndex` сессии; сравнивает с `UserIndex`
из пакета (`[esp+0x1C]` — 7-й аргумент; `[esp+0x20]` — группа, 8-й).

> ★ **ОШИБКА первых сборок (b97b99be, a5ac8328), найдена ревизией другой сессии 12.10 ~13:40:** трамплин читал
> `[esp+0x20]`, т.е. **группу**, и сравнивал её с учёткой сессии — у любого честного клиента (группа 0) отказ,
> список персонажей пуст. Дизасм стока `0x407F9F`: `movsx eax,[ebp-0x24]; push eax` (группа) → `mov ecx,[ebp-0x28];
> push ecx` (UserIndex) → … → `call 0x40f440` (cdecl, справа налево) ⇒ после `call` UserIndex в `[esp+0x1C]`.
> Живьём не проявилось: при старте 13:31 ключ `CheckCharList` стоял в 0. Исправлено в сборке **`96bc93a7…`**
> (выложена 13:45); юнит-тест дополнен случаями «учётка совпала, группа 0/1» и «группа == учётка сессии, UserIndex
> чужой → отказ». Слот L03 (`[esp+0x1C]` логин, `[esp+0x20]` пароль из 14 аргументов) перепроверен дизасмом — верен. При несовпадении запрос не выполняется, `*out = 0` (существующая
штатная ветка «нет персонажа» — обработчик ничего не отдаёт). При совпадении — хвостовой вызов
стокового сборщика. Стек сбалансирован: `sub_4038B0` снимает свой аргумент (`ret 4`).

## L04c — 1016 режим 2 (вход персонажем соулмейта) — СДЕЛАНО 12.10 (вторая сборка)

**Дефект.** Режим 2 (`sub_40AD30`) после `UPPreSMConnect` вызывает `sub_4037B0(session, *(v109+1))` @`0x40B3AF`,
перезаписывая личность сессии клиентским `UserIndex` без проверки, что это именно учётка соулмейта.
В режиме 2 чужой номер в пакете законен (учётка партнёра), поэтому сверка L04a тут неприменима.

**Исправление (★).** Перехват `call sub_4037B0` @`0x40B3AF` (5 б `e8 fc 83 ff ff`). Трамплин (`l04_login_identity.cpp`):
1. `realUser = sub_4038B0(session)` — учётка сессии;
2. `EXEC UPCharExist %d,%d` с аргументами **(`realUser`, `group`)** — порядок как в 1005 (`LoginManager.c:2895`:
   `UPCharExist @Userindex, @Seridx`; ★ ранее в этом документе порядок был записан наоборот);
   источник БД — `sub_4060A0(group)`, дескриптор — `[ebp+0x10]` кадра обработчика;
3. `MateUserindex = result[4..7]` (как читает 1005: `memcpy(&v46,&v44[4],4)`), `result[0]` ≠ 0;
4. совпало с `*(v109+1)` (`[ebp-0x27]`) → хвостовой вызов стокового `sub_4037B0` (ecx восстановлен);
   иначе — **штатный отказ 1016**: 1027 (651 б, код 3 «нет активной пары») через `sub_415A40` в стоковый буфер
   `[ebp-0x618]`, `[ebp-4] = -1`, выход из секции (`sub_401040`), переход на эпилог `0x40C8CF` — ровно тот путь,
   которым сток отвечает «занят» (код 2) при `UPPreSMConnect`.

Ошибка запроса к БД — отказ (`SoulMateFailOpen=0`); `SoulMateFailOpen=1` — пропустить, как сток. Свою
учётку в режиме 2 тоже отклоняет (это не пара). Негодный кадр — SEH, отказ без падения.

Дальше по цепочке вход в мир всё равно сверяет P50 (DBManager: учётка, персонаж, пара) — L04c делает отказ раньше,
на LoginManager, и не даёт чужой учётке стать «личностью сессии» (от неё зависят 1005/1016/1018 и гейты оператора).

**Проверка.** Юнит-тест `tools/test_l04c.cpp` (кадр подделан буфером, стабы `sub_4038B0`/`sub_4060A0`/`sub_40F440`/
`sub_415A40`): пара совпала → пропуск и `UPCharExist(учётка сессии, group)`; не пара / своя учётка / пары нет /
учётки нет → отказ; ошибка БД → отказ при FailOpen=0 и пропуск при 1; негодный кадр → отказ без падения; отказ =
1027/651 б/код 3 с session/hdr из кадра — **9/9**. Статически: трамплин в DLL дизассемблирован (push ebp → L04c_Check →
je → mov ecx,0x66b4da0 / jmp [sub_4037B0]; ветка отказа add esp,12 → L04c_SendRefuse → [ebp-4]=-1 → sub_401040 →
и «душой» после рестарта.

## Проверка

- **Юнит-тест** `AstoryServer/Patches/LoginPatch/tools/test_l04.cpp` (через `L04_TestSetup` + фейковый кадр,
  стаб `sub_4038B0` с `ret 4` и стаб сборщика): совпадение → запрос выполнен и `UserIndex` проброшен;
  подмена `UserIndex` → запрос НЕ выполнен, `*out=0`. Прошли.
- **Статически**: сверены байты площадок с живым образом (`0x40B1AB = 85 c0 0f 85 a6 00 00 00`,
  `0x407FD2 = e8 69 74 00 00`); новые байты L04a декодируются как `cmp al,2 / je 0x40B259`; переходов
  внутрь затираемых байтов нет; трамплин скомпилирован с литералом `0x66B4DA0` (не адресом);
  `sub_4038B0` = `ret 4` (баланс стека).
- **Сквозной прогон**: секция `[L04_LoginIdentity]` создана (Version=5), патч дошёл до сверки; на
  НЕ-LoginManager-образе — `MISMATCH`, запись не производится.

Логика L04a идентична штатной проверке режима 0 (`sub_4038B0` + `cmp`), что подтверждает корректность.
