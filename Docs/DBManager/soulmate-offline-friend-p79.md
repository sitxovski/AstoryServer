## ЗАЧЕМ

Вкладка «Друг» окна 6400 (поля 6520 имя, 6521 уровень, 6556 профессия, 6523 локация, 6522 «Последний выход» — подпись 6575 = loc 12103)
у Друга вне игры пуста. Пара в БД привязана к **аккаунту** (`Joy1.dbo.SoulMate` Userindex/Ouserindex, State 1), GameServer о Друге
вне игры знает только номер его аккаунта (`CUser+99014`) — имени, уровня, карты у него нет. Оригинал по 5226 гасит четыре поля, а 6522
не пишет **никогда** (слот `this+6` не трогает ни `itemTooltip_RefreshControls`, ни `uiPanelClearAllFields`) — дефект оригинала.

Единственный существующий путь «клиент спрашивает — БД отвечает» без новых опкодов: **2244 → 2243** (кнопка 6584 «прежний Друг»):
клиент 2244 → GS `sub_499A30@0x499A30` (режим 0) → DB 2244 → DBManager `sub_42EA20@0x42EA20`: `EXEC UPCharSoulMateInactive %d`,
копирует первые **0xF3 = 243 б** буфера строк → 2243 → GS `sub_499A30` (режим 1) → клиенту 2243 → эталон `uiRefreshSlotGrid3x3`
(окно 6640, 3 группы × 3 персонажа). Раскладку строк DBManager строит **сам по типам столбцов результата** (обобщённый OLE DB-путь
`sub_447720`: привязки по `ulColumnSize`, шаг = сумма размеров) — поэтому типы и порядок столбцов оставлены ровно стоковыми.

## ЧТО ИЗМЕНЕНО

### P79-SQL — `dbo.UPCharSoulMateInactive`

Стоковые строки (прежние Друзья, `State = 0`) — те же и в том же порядке (`Regdate DESC, Lvl DESC, Expe DESC`; добавлен только
устойчивый последний ключ `Charidx` для равных). **После них** — две строки активной пары, если она есть и у Друга есть персонаж:

| Строка | Smidx | SmLvl | Lvl | Job | Charname |
|---|---|---|---|---|---|
| персонаж | Smidx пары | **254** | `Charinfo.Lvl` | `Subjob <> 0 ? Subjob : Job` (= 6556, loc 12556+id) | `Charinfo.Charname` |
| место и время | Smidx пары | **253** | карта `CharPos.Cporidx` (нет строки → 255) | канал `CharPos.Channel` | последний выход **UTC** `yyyyMMddHHmmss` (`''` — неизвестно) |

- Персонаж — тот, которым Друг **вышел последним**: последняя строка `JoyLog1.dbo.LogInfo` с `Logout IS NOT NULL` по существующему
  персонажу (`JOIN Charinfo` — отсекает Charidx 13 строк выбора персонажа и удалённых). `LogInfo.Logout` пишут и обычный выход
  (`UPLogOutGame` → `UPLogOut`), и аварийный (`UPLogOutCharacter`). Запасной путь — `CharPos.LastDate` (его двигает и портал
  `UPPortalLogOut`, поэтому только запасной), затем любой персонаж без времени.
- Время БД — местное МСК (сервер «Russian Standard Time», UTC+3, `datetime` без смещения); процедура переводит в UTC
  (`DATEADD(MINUTE, DATEDIFF(MINUTE, GETDATE(), GETUTCDATE()), …)`), клиент покажет местное время игрока.
- Сток-сетка 6640 оригинала строки 254/253 **прячет** (`(signed char)SmLvl > 0` ложно) — вид окна прежних Друзей не меняется.
- Объём: в истории `SoulMate` не больше 3 строк на аккаунт (вместе с активной) → прежних не больше 2 × 3 персонажа = 6, плюс 2 = **8 ≤ 9**.
- Типы результата (`sys.dm_exec_describe_first_result_set`) — как в стоке: int 4 / tinyint 1 ×3 / varchar(20) 20 = 27 б.
- Модуль: `uses_ansi_nulls = 1`, `uses_quoted_identifier = 0` — как у стока. MD5 тела после правки `DB8B33A11BA86C655167ADBAE322B8AE`
  (сток `E19CB3AB07E3C8F66F181A9483BE2F29`). Других читателей процедуры нет (`sys.sql_modules` — только она; в DBManager — одно место).

### P79-DLL — AsdaPatch v51 (P55, таблица длин)

`gen_opcode_lengths.py` MANUAL: **2244 — 34..53** вместо 253..∞. Прежняя запись описывала режим 1 `sub_499A30` (ответ DBManager,
`memcpy 0xF3`), а клиентский 2244 — режим 0, тела не читает. Эталон `antiCheat_SendBitMaskCheck` (security.c:2121) и порт
(`SendSoulmateOldPartnerReq2244`) шлют 24 б (секрет 8 + MD5 16, payload 0) с падом → 9+8+16+0+1 = 34 … 53. Живой журнал P55
(`Mode=0`) 19–22.10: **6 ложных** «кадр короче минимума для опкода; опкод 2244 … размер 40..53 [253..∞]». При `Mode=1` это был бы отказ
и +1 к Hack Packet на каждое нажатие кнопки. Изменилась ровно одна строка `OpcodeLengths.h`; новых ключей нет, Version 50 → 51.
