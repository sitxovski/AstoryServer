# P61 — шифрование трафика (прослойка AsdaSecure) в GameServer/Indun

Дата: 12.10.2026. Волна В7b «врезка». Зеркало L07 (LoginManager). Дизайн:
`AstoryServer/Docs/_Common/traffic-encryption-design.md`. План: «Дополнение 11.10» в `00_PLAN.md`.

Исходники (в КОПИИ): `AstoryServer/_archive_waves/AsdaPatch_w61/` (патч `src/patches/p61_traffic_encryption.cpp`, адреса
`src/SrvApi.h` namespace `Hooks`, секция `src/Config.cpp`, реестр `src/patches/Registry.cpp`, сборка
`build.bat` линкует `../AsdaSecure/src/*` + `bcrypt.lib`). Один образ/роль/ключ для GameServer и Indun →
под-сервер **Game** для обоих (под-сервер входит в подпись и HKDF).

## Что делает
То же, что L07, на боевом сервере (15601):
- приём клиентского слота → расшифровка AEAD → стоковый разборщик `CopyToWriteBuffer`;
- отправка (Ciocp::Send) → шифрование перед `WriteFile`;
- accept/disc (SetConnectFlag) → Reset канала.

## Точки врезки (образ GameServer; сверено verify_traffic.py на стоке 4e20f0ad и живом/Indun e7b4ac38)
Межсервер (10000..10099) НЕ трогаем.

| Площадка | VA | Оригинал (5 б) | Действие |
|---|---|---|---|
| приём клиента (IoWorkerThread `sub_564900`) | `0x564CD5` | `e8 46 ef ff ff` (call `sub_563C20`) | → `P61_RecvTramp` |
| отправка (Ciocp::Send `sub_561F20`, site A) | `0x4C2ACA` | `e8 51 f4 09 00` | → `P61_SendTramp` |
| отправка (site B) | `0x4C2BDC` | `e8 3f f3 09 00` | → `P61_SendTramp` |
| отправка (site C) | `0x56435E` | `e8 bd db ff ff` | → `P61_SendTramp` |
| Reset канала (вход `SetConnectFlag sub_562910`) | `0x562910` | `55 8b ec 6a ff` | детур → `P61_SetConnTramp` → Reset, продолжение `0x562915` |

Стоковые функции (вход не хукнут): recv-синк `sub_563C20` (this=ecx; buf,size,slot; ret 0xC),
`Ciocp::Send sub_561F20` (this=ecx; slot,Src,nBytes; ret 0xC — также ServerHello). `SendTemp sub_562640`
НЕ хукаем (дослыает уже зашифрованный буфер). У GameServer **три** send-площадки (у LM две) — хукаются все.
ABI трамплинов, состояние/потоки, лениво-CNG, совместимость, ограничения — как в L07 (см. его документ).

## ★ fix2 (13.10.2026): порядок замков и отправка (ревизия INTEG3, Б-1/Б-2)
Замок Ciocp **L** = `this+0x60D1830` — один на весь Ciocp; его берут 7 функций через `0x568D50` (Send `0x561F20`,
DisConnect `0x561C30`, SetConnectFlag `0x562910`, GetConnectFlag `0x5629C0`, SendTemp `0x562640`, `0x561E10`, AcceptEvent
`0x5651D0`), ещё 2 (`0x560E20`, `0x5618B0`) его создают/удаляют. Мост держится одного порядка: **«замок слота → L»**.
- **Б-1.** Детур `SetConnectFlag` вызывается ПОД L (DisConnect → `0x563B60` → SetConnectFlag; accept `0x563C50`; ошибка
  WriteFile 64 в Send → `0x561D70`). Прежде он брал замок слота → взаимная блокировка с потоком приёма (тот держит замок
  слота и ждёт L в Send ServerHello) — вставал весь Ciocp. Теперь `AsdaWire::ResetSlot` только ставит запрос
  (`InterlockedIncrement`), сброс применяется под замком слота при следующем обращении к слоту (приём, отправка). Accept
  ставит запрос до первого `ReadFile` нового клиента, поэтому он никогда не видит старых ключей и номеров кадров.
- **Б-2.** Трамплин отправки вызывает `AsdaWire::SendRoute`: шифрование и стоковый `Ciocp::Send` одним куском под замком
  слота. Номер кадра совпадает с порядком попадания в буфер сокета (Send копирует под L; досылку из буфера `+178` делает
  SendTemp по порядку и через наши площадки не проходит). В GS одному игроку шлют до 21 нити карт + нить 6004
  (`0x416460 → 0x563E80`) — раньше кадры уходили не по порядку (клиент: Replay → разрыв).
- **Проверка:** `verify_traffic.py` — из-под L нет пути к площадкам send/recv (обход вызовов от L-функций, 3 образа GS и
  3 LM); стенд `AsdaSecure/stand/stand_b7d_locks` (S1/S1b/S3/S5 без блокировки, S2 2×50 000 и S2m 22×5 000 кадров на
  один слот — порядок верный, S4 — новый клиент на переиспользованном слоте).
- **Сбой CNG** (НИЗК-5): мост пропускает байты как есть — старые клиенты (AllowLegacy=1) работают; при AllowLegacy=0
  соединение закрывается на первом приёме. **Запись площадок** (НИЗК-7): детур SetConnectFlag — первым; при сбое любой
  записи записанные площадки возвращаются к оригиналу.

## ★ fix2b (13.10.2026): кадры сервера до рукопожатия
GameServer на accept (опкод 20000 → `AcceptExUser 0x5233A0`) при переполнении шлёт `Send_DisConnectType` (`sub_52EDB0` →
`0x563E80` → площадка C, 6004 тип 14/15), `Sleep(100)` и разрывает (`sub_526E40` → GetConnectFlag → DisConnect `0x561C30`) —
до первого байта клиента. Прежде кадр вставал в очередь канала и стирался сбросом при разрыве: игрок не видел «сервер
переполнен». Теперь: кадры при неготовом канале — в очередь слота моста (`PreHandshakeQueueKB`, 64 КБ; сверх — отбрасываются
и считаются); детур **входа DisConnect `0x561C30`** (украдено `55 8b ec 6a ff`, продолжение `0x561C35`) — ворота
`AsdaWire::DisconnectGate`: при невыданной очереди разрыв откладывается (eax=1, сток не выполняется), очередь уходит сразу за
ServerHello (Secure, шифрованная, по ≤ 64 КБ) или как есть (старый клиент) на первом приёме, затем отложенный разрыв
выполняется (присланное клиентом стоку не отдаётся — в стоке сокет был бы закрыт). Клиент молчит дольше `PreHandshakeCloseMs`
(5000) — разрыв сторожем. DisConnect из IoWorkerThread (`0x564900…0x564F00`, нулевой приём/ошибка сокета) не откладывается.
Детур `SetConnectFlag` передаёт второй аргумент (1 accept / 0 разрыв): кадр встаёт в очередь только при флаге 1 (сток при 0
Send отвергает), а сброс accept применяется до первого кадра новой сессии и её очередь не стирает. Ворота без замков моста
(вход DisConnect бывает под замком Ciocp) — порядок «слот → Ciocp» сохраняется. Стенды: `stand_wire` раздел 8,
`stand_b7d_locks` S6 (3000 итераций отказа против ClientHello в случайном порядке — отказ доходит всегда, разрыв ровно один).

## ★ fix2c (13.10.2026, ревизия FIX2): предел буферов стока 0x1000
- **Отправка (Н-1, был БЛОКЕР).** `Ciocp::Send 0x561F20` копирует данные в буфер перекрытой записи 0x1000 б
  (`0x5653B0(tag, ov+0x1C, 0x1000, src, n)`): при n > 0x1000 копии нет (только лог), а `WriteFile` уходит с n байтами обнулённого
  буфера и чтением за ним. GS копит пакет игрока до 0xFFF б (`0x4C2A9D`), шифрование добавляет 28 б (`[len4][seq8][ct][tag16]`) —
  кадр 4069…4123 б уходил нулями → разрыв Secure-клиента на плотном трафике. Теперь `SendRoute` режет открытый текст на куски
  ≤ **4068** (0x1000 − 28), каждый — свой кадр и свой вызов Send под тем же замком слота (номера по порядку); ServerHello и очередь
  до рукопожатия — тоже покадрово (Legacy — сырыми кусками ≤ 0x1000).
- **Приём.** Сток читает сокет по 0x1000 (`ReadFile`, GameServer.c:138021) и разбирает порцию `CopyToWriteBuffer 0x5656D0`
  (обрывок заголовка < 10 б + вся следующая порция в буфере сборки слота 0x1000; пакет клиента ≤ 0x2BC). Мост отдаёт расшифрованный
  поток разборщику `sub_563C20` кусками ≤ **4087** (0x1000 − 9) сам (`SetRecvSink`), без своих замков. Кадр клиента любой длины до
  64 КБ мост собирает из нескольких порций — клиенту резать отправку не нужно.
- **Н-2.** Сокеты стока закрываются с RST (`SO_LINGER {1,0}` при accept, `0x567FC1…0x567FF1`); сток GS ждал `Sleep(100)` между 6004
  и киком. Отложенный разрыв выполняется сторожем не раньше `PreHandshakeLingerMs` (150) после выдачи отказа; потоки сервера не
  ждут (`RecvRoute` = −1, ReadFile не перевыставляется).
- **Н-3.** При откладывании запоминается поколение слота (`resetReq`); если слот сброшен (`DisConnect_NoLock 0x561D70` из Send/SendTemp
  мимо ворот, затем accept нового клиента) — отложенный разрыв снимается и новое соединение не задевает.
- **Н-4.** DisConnect из IoWorkerThread (клиент сам закрыл) при отложенном разрыве — сток сразу, отложенный снимается.
- Стенды: `stand_limit4096` (мок Send/разборщика с пределом 0x1000; на мосте fix2b — 5 провалов, на fix2c — 0), `stand_wire` 8.9–8.14,
  `stand_b7d_locks` S2big (пакеты 4095 б) и S6L (пауза 150 мс).

## ★ fix2d (14.10.2026, хвост ревизии FIX2): переполнение досылки стока
- **Находка (дизасм `Ciocp::Send 0x561F20`, `SendTemp 0x562640`).** Пока предыдущая запись в полёте (`[sess+8]==1`, сессия
  `[Ciocp+0x60D1898] + slot·0xA0BE`), Send дописывает кадр в досылку `+0xB2` (длина `+0xA0B2`); при длина + кадр ≥ **0x9F9C**
  (`0x56202B`) — memset досылки, длина 0, флаг полёта 0, возврат 0: стираются уже зашифрованные кадры, у Secure-клиента разрыв
  Replay, сервер этого не видит. Бывает, когда клиент не читает сокет (клиент читает только в `FAsdaConnection::Tick`, `OpenLevel`
  держит игровой поток секунды), а GS шлёт вход в мир и окружение (120–170 КБ).
- **П-1.** Мост перед стоковым Send входит в тот же замок Ciocp `this+0x60D1830` (Send/SendTemp берут его первым: RAII `0x568D50` →
  EnterCriticalSection), читает флаг соединения `+4`, флаг полёта `+8`, длину досылки `+0xA0B2` и там же зовёт Send (замок рекурсивный)
  — без гонки с SendTemp из IoWorker. Кадр, который досылка не вместит, ждёт в очереди слота моста (уже зашифрованным, номера по
  порядку; пока очередь непуста, новые кадры — в её хвост); сторож раз в 50 мс (и каждый следующий кадр слота) выталкивает её, пока
  досылка принимает. Порядок замков «слот → Ciocp» не меняется. Разрыв/сброс слота — очередь выбрасывается, память освобождается.
- **П-2.** Отказ стокового Send (ошибка WriteFile), переполнение очереди (`TxQueueKB`), потеря кадра стоком (пул перекрытых структур
  `0x5680A0` пуст: Send возвращает 1 без записи; досылка без записи в полёте больше 0x1000 — сток отправил бы мусор, `0x56233E`) у
  Secure-слота → строка `P61: [досылка] слот … — разрыв` (ограничитель `LogPerMinute`), `ac.other` **61** (`item_code` причина 1/2/3,
  `value1` очередь, `value2` досылка), разрыв сторожем (поколение слота проверяется под замком Ciocp). Не зависит от `KillOnViolation`
  (поток номеров уже не восстановить).
- Legacy-слоты — как сток (без очереди, сток стирает досылку как раньше). `Enabled=0` — патч не ставится. Новых площадок нет
  (мост только читает поля стока и берёт его замок); раскладка сверена `verify_traffic` на стоке и живом/Indun (21 инструкция).
- Стенд `stand_backlog` (мок стокового Send/SendTemp по дизасму, ядро 80 КБ, клиент не читает 1,5 с): на мосте fix2c поток 120/160/200 КБ
  — Replay 3 из 3; на fix2d — целы, порядок верный; 22 нити отправки — порядок по нитям цел; переполнение очереди — ровно один
  разрыв и один вид 61; стресс разрыв/accept против 4 нитей отправки — ошибок клиента 0, блокировок нет
  (`Reports/anticheat/wave_FIX2_20261013.md` §9).

## ★ fix2e (14.10.2026, ревизия fix2d Ф-1): общий предел очередей моста и нехватка памяти
- **Находка ревизии.** Предел очереди моста был только на слот (`TxQueueKB` = 1 МБ): при массовом «клиенты не читают» (сбой сети,
  несколько аккаунтов злоумышленника в людном месте) набиралось до 550 × 1 МБ кучи; `std::bad_alloc` из постановки в очередь уходил
  через C-обёртку в naked-трамплин — падение процесса GameServer.
- **Общий предел.** Ключ `TxQueueTotalMB=64` (1…1024 МБ). Учёт — один Interlocked-счётчик на процесс: место резервируется ДО выделения
  памяти под кадр, отдаётся при выталкивании, сбросе слота (в т. ч. по поколению) и разрыве (одна точка обнуления очереди слота) —
  сумма принятых кадров во всех очередях никогда не больше предела, после разрыва всех — 0. Превышение при постановке → разрыв ЭТОГО
  слота (П-2): `P61: [досылка] … (вид 61, причина 4; …, во всех очередях моста N б)`, `ac.other` 61 `item_code` 4, `value2` = общий объём.
- **Нехватка памяти.** Все выделения моста (очередь до рукопожатия, буфер шифрования, очередь моста, буферы приёма канала) — под
  `try/catch(std::exception)` внутри замка слота: сбой → разрыв слота, причина 5 (`value2` = общий объём), исключение в трамплин и
  сток не выходит, процесс работает. Ловятся только C++-исключения (DLL с `/EHa`, но SEH не перехватывается — как раньше). Под замком
  Ciocp мост память не выделяет. Нехватка памяти при построении таблицы слотов (первое соединение) — мост как при сбое CNG (байты как
  есть при `AllowLegacy=1`).
- Стенды: `stand_backlog` Т9 (150 слотов не читают, предел 2 МБ — разрывы только причины 4 (прогон 1: 126), принятый объём ≤ предела,
  выжившие (24) получили поток целым, после — счётчик 0), Т10 (подставной `operator new`: отказ в очереди до рукопожатия, буфере шифрования,
  очереди моста, на приёме — исключений наружу 0, разрыв с причиной 5); стенд ревизора `stand_rev4_fix2d` B4/B5 (`wave_FIX2_20261013.md` §10).

## ★ sec2 (15.10.2026, блок В плана альфы) — Е-1, Е-2, ускорение рукопожатия, допуск подключений до рукопожатия
Отчёт: `Reports/anticheat/wave_SEC2_20261015.md`. Мост `AsdaSecure/src/AsdaServerBridge.{h,cpp}`, `AsdaSecure.{h,cpp}` — общие
для P61 и L07. Новых площадок нет; детур входа `SetConnectFlag` дополнительно передаёт `this` Ciocp (`push ecx` в трамплине,
`ResetSlotEx`). Порядок замков прежний: «слот → Ciocp»; таблица адресов допуска — свой SRW-замок, листовой.
- **Е-1 (ревизия fix2e):** очередь моста слота, упавшего НЕ по виду 61 (сбой шифрования отправки; нарушение приёма при
  `KillOnViolation=0`; отказ допуска), освобождается сразу (`MarkFail` → `TxFreeLocked`; сторож — для любого сбойного слота).
  Место в общем пределе не держится до сброса слота; счёт — через единственную точку обнуления `txBytes`.
- **Е-2 (ревизия fix2e): справедливая доля общего предела.** Постановка, после которой сумма очередей > `TxQueueTotalMB`:
  слот «тяжёлый» (его очередь ≥ средней по слотам с непустой очередью или ≥ `TxQueueFairKB`) — рвётся сам (вид 61 причина 4,
  как fix2e); «лёгкий» (честный клиент грузит карту) — кадр принят, пока сумма ≤ предел + предел/8 (жёсткий потолок), а сторож
  (раз в 50 мс) вытесняет НАИБОЛЬШУЮ очередь процесса — вид 61 **причина 6** «общий предел — вытеснена наибольшая очередь»;
  сверх потолка — причина 4. Почему так, а не «всегда рвать наибольшую»: тяжёлый рвётся синхронно (предел держится без ожидания
  сторожа), лёгкий не страдает от чужого затора; поиск наибольшей — без чужих замков в пути отправки (сторож берёт замок только
  жертвы); жёсткий потолок ограничивает память и при опоздании сторожа.
- **Ускорение рукопожатия:** ключ подписи импортируется в CNG ОДИН раз (`HandshakeKeyCache=1`; до 16 дескрипторов, каждый в
  момент подписи у одной нити); пары ECDH P-256 заранее готовит фоновая нить пониженного приоритета (`HandshakePool=16`), каждая
  пара одноразовая (запись пула затирается при выдаче, дескриптор уничтожается после вывода ключей), старше 10 мин не выдаётся;
  пул пуст — генерация на месте. Ключи только в памяти процесса, на диск ничего не пишется. Протокол не менялся. Стенд: ~2,0 мс →
  ~0,83 мс CPU нити приёма на рукопожатие (`stand_sec2` Х).
- **Допуск до рукопожатия (стойка в интернете):** проверка — один раз на соединение, на первом приёме или сторожем ≤ 50 мс после
  accept (если клиент молчит), до разбора байт (ServerAccept не выполняется):
  - `ConnPerIpMax=120` за `ConnPerIpWindowSec=60` — с одного адреса больше → разрыв, `ac.other` **63** (`value1` счёт в окне,
    `value2` предел, `value3` окно, с; одна строка на адрес за окно);
  - `MaxPendingHandshakes=64` — соединений «accept есть, рукопожатие не завершено» на процесс больше → новое разорвано, **64**;
  - `HandshakeDeadlineMs=10000` — рукопожатие не завершено за срок после accept → разрыв сторожем, **65** (молчащий сокет — только
    при `AllowLegacy=0`); отложенный разрыв fix2b срок не отменяет;
  - разрыв — штатный `GetConnectFlag + DisConnect` под замком Ciocp только своего поколения; PatchLog «[допуск]» (ограничитель
    `LogPerMinute`), 64/65 — не чаще `AdmissionLogGapMs=5000`. Соединения, принятые до первого обращения к мосту, тоже учтены.
  - Числа: 50 тестеров за общим NAT — вход + повтор = 100 подключений с адреса, запас до 120 в минуту; поток с одного адреса — не
    больше 2 рукопожатий/с (≈0,2 % ядра); незавершённых одновременно у 50 тестеров ≤ 50 (рукопожатие длится 1 RTT) — 64 с запасом,
    злоумышленник держит не больше 64 из 550 слотов и не дольше 10 с; клиент ждёт рукопожатие 5 с — срок сервера вдвое больше.
- Конфиг (новые ключи, DLL допишет сама): `TxQueueFairKB=256`, `HandshakeKeyCache=1`, `HandshakePool=16`, `ConnPerIpMax=120`,
  `ConnPerIpWindowSec=60`, `MaxPendingHandshakes=64`, `HandshakeDeadlineMs=10000`, `AdmissionLogGapMs=5000`.
- Не покрыто: при сбое CNG (мост «как есть») допуска нет; таблица адресов 4096 записей — переполнена (≥ 4096 разных адресов в
  окне) → новый адрес пропускается без счёта (`admTableFull`).

## ★ sec2b (15.10.2026, ревизия SEC2 С-1 / Н-1 / Н-2 / Н-6) — GameServer / Indun (P61)
Ревизия: `Reports/anticheat/review_SEC2_20261015.md`; отчёт: `Reports/anticheat/wave_SEC2b_20261015.md`. Мост
`AsdaSecure/src/AsdaServerBridge.{h,cpp}` (общий для P61 и L07); новых площадок нет.
- **С-1:** при `AllowLegacy=1` молчащий сокет (ни байта) по сроку `HandshakeDeadlineMs` по-прежнему не рвётся (старый клиент мог
  открыть его заранее), но **снимается со счёта незавершённых рукопожатий** — молчащие больше не держат `MaxPendingHandshakes`
  (и предел адреса) бессрочно. Снятый потом заговорил (ClientHello / первый байт 0xFB) — работает как обычно, второго вычета нет.
- **Н-1:** новый ключ `MaxPendingPerIp=16` — не больше N незавершённых рукопожатий с одного адреса (0 — без предела). Сверх — новое
  соединение с этого адреса разорвано до рукопожатия, `ac.other` **64** (текст журнала `pending handshakes from IP N/M`, PatchLog
  «[допуск] … незавершённых рукопожатий с этого адреса … (предел MaxPendingPerIp …)»); предел процесса `MaxPendingHandshakes` — как
  был (текст без «from IP»). Счёт — по живому состоянию слотов (адрес пишется при проверке допуска вместе с поколением accept),
  отдельного счётчика, который мог бы «утечь», нет. Один адрес больше не отсекает остальных на срок рукопожатия.
- **Н-2:** сторож вытесняет очередь (вид 61 причина 6), только если под замком жертвы она всё ещё наибольшая или «тяжёлая» (≥ средней
  или ≥ `TxQueueFairKB`); очередь, успевшая вытолкнуться, не рвётся — выбор заново.
- **Н-6:** общий предел `TxQueueTotalMB` (и справедливая доля, и `value2` вида 61) считается в **реальной памяти кадров** в куче
  32-битного процесса: блок данных (округление корзины LFH + заголовок 8 б; кадр 4096 б — «большой блок» MSVC +35 б) + блок
  элемента deque (24 б) + 2 указателя карты — по замеру HeapWalk; мелкий кадр 43 б стоит 88 б, кадр 2028 б — 2088 б.
  Предел очереди слота `TxQueueKB` — по-прежнему в байтах кадров.
- **Гонка «сторож допуска ↔ первый приём»** (найдена стендом при сборке): ClientHello соединения, которое сторож в этот момент
  отвергал, разбирался уже на разорванном слоте (ServerAccept, пара ECDH). Теперь первый приём ждёт решения сторожа, а порция
  приёма соединения, уже разорванного допуском/сроком, не разбирается (−1).
- Конфиг: `MaxPendingPerIp=16` (DLL допишет сама); AsdaPatch Version 40; AsdaPatch `0f16948c` — НЕ выложено.
- Проверено: `AsdaSecure/wire/stand_sec2` (С-1, Н-1, Н-2 — детерминированная гонка на «воротах» стокового Send, Н-6 — сверка с кучей
  процесса), стенд ревизора `stand_rev5` на новом мосте (R1 не воспроизводится), полный регресс — логи `wSEC2b_logs/`.
