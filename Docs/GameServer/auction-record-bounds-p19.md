## 2. Механизм дефекта (общий для S3 и S4)

Оба обработчика разбирают хвост пакета как массив записей по 45 (`0x2D`) байт. Длина берётся из
шапки самого пакета (`i16` по смещению `+1`) и проверяется ТОЛЬКО на кратность:

```c
// sub_5218A0@0x5218A0, GameServer.c:109805 — вызывается как sub_5218A0(len, 45, 1)
if ( a1 - 34 <= 0 )        return 0;
v4 = a1 - 49; if ( v4 <= 0 ) return 0;
if ( v4 % a2 )             return 0;
return 1;                  // ← верхнего предела НЕТ; i16 допускает до 727 записей
```

Тело цикла копирует запись и ТОЛЬКО ПОТОМ сверяет счётчик:

```c
for ( i = v13 + 24; i < v17 - 1; i += 45 )
{
    memcpy(&Src[45 * v14], (char *)a3 + i, 0x2Du);      // ← запись УЖЕ произошла
    memcpy(&v25[v28 + 15], &Src[45 * v14], 0x2Du);
    v28 += 45;
    if ( ++v14 > 8 ) { v34 = 1; goto LABEL_55; }        // ← проверка на шаг ПОЗЖЕ, чем нужно
}
```

**S3 (9905).** `char Src[364]` @ `[ebp-0x58C]`, сконструировано 8 записей × 45 = 360 б. Дальше по
кадру лежат `v19[8]` @ `[ebp-0x420]` (15-байтовая шапка, которая ниже уходит пакетом 9905 в
`ItemRelayServer`), `v20` @ `[ebp-0x410]`, `v21` @ `[ebp-0x409]`, `v22` @ `[ebp-0x408]`,
`v23` @ `[ebp-0x404]`, `v24` @ `[ebp-0x400]`, `v25` @ `[ebp-0x3FC]`.
Девятая запись пишет `Src[360..404]` = `[ebp-0x424]…[ebp-0x3F7]` — **45 байт за концом массива**,
затирая шапку и все перечисленные счётчики.

**S4 (9909).** `char Src[460]` @ `[ebp-0x5EC]`, сконструировано 10 записей × 45 = 450 б, следом та
же гряда переменных с `v19[8]` @ `[ebp-0x420]`. Одиннадцатая запись пишет `Src[450..494]` =
`[ebp-0x42A]…[ebp-0x3FE]` — **35 байт за концом объявленного массива**.

**Чем это НЕ является.** До сохранённого EIP запись не достаёт: между `Src` и эпилогом ещё около
килобайта локальных переменных (`v25[704]`, `Buffer[260]` и т.д.). Это не захват управления, а
**управляемая порча соседних переменных кадра** — шапки запроса к `ItemRelayServer` и счётчиков
цены/веса/количества. Второй `memcpy` (в буфер отправки `v25`) в границы укладывается и его не
трогаем.

**Достижимость.** Штатный клиент шлёт максимум 8 и 10 записей соответственно
(`Reports\npc_exchange_win_13000.md` §9.4), поэтому в норме путь недостижим. Собранный вручную
пакет достигает его гарантированно — но с 2026-08-27 подтверждено, что подпись MD5 тела пакета на
живом сервере проверяется (см. §5), то есть отправитель обязан знать ключ клиента.

## 3. ЧТО именно меняется — адреса и байты «было → стало»

Все VA даны для `ImageBase = 0x400000`; смещение в файле = `VA − 0x400000` (`.text` отображается 1:1).
Правки живут в памяти процесса, файл на диске не меняется.

### S3 — `FixBuyRecordBounds` (9905 «купить», `Recv_TransAction_BuyItemReq@0x51AA10`)

| VA | было | стало |
|---|---|---|
| `0x0051ACC5` (5 б) | `6A 2D 8B 4D 0C` — `push 0x2d` + `mov ecx,[ebp+0xC]` | `E9 <rel32>` — `jmp` на трамплин в DLL |

Сверяется ПЕРЕД записью **18 байт** (короткая пятёрка `6A 2D 8B 4D 0C` встречается в образе не один
раз и ничего не доказывает):
`6A 2D 8B 4D 0C 03 4D E0 51 8B 95 E0 F9 FF FF 6B D2 2D`
плюс **13 байт ветки отказа** по `0x0051AD25`:
`83 BD E0 F9 FF FF 08 7E 09 C6 45 EF 01`.

Трамплин (проверен дизассемблером в собранной DLL):
```
83 BD E0 F9 FF FF 08   cmp   dword ptr [ebp-0x620], 8     ; записей уже скопировано
7C 06                  jl    ok
FF 25 <ptr>            jmp   [ptr] -> GameServer 0x0051AD2E   ; штатный отказ: v34=1 + LABEL_55
ok:
6A 2D                  push  0x2d                        ; ← вытесненные площадкой команды
8B 4D 0C               mov   ecx, dword ptr [ebp+0x0C]
FF 25 <ptr>            jmp   [ptr] -> GameServer 0x0051ACCA   ; site+5, цикл идёт дальше как раньше
```

### S4 — `FixDeleteRecordBounds` (9909 «снять лот», `Recv_TransAction_DeleteItemReq@0x51E380`)

| VA | было | стало |
|---|---|---|
| `0x0051E630` (5 б) | `6A 2D 8B 4D 0C` | `E9 <rel32>` — `jmp` на трамплин в DLL |

Сверяемые 18 байт: `6A 2D 8B 4D 0C 03 4D E4 51 8B 95 9C F9 FF FF 6B D2 2D`
плюс 13 байт ветки отказа по `0x0051E690`: `83 BD 9C F9 FF FF 0A 7E 09 C6 45 EF 01`.

Трамплин:
```
83 BD 9C F9 FF FF 0A   cmp   dword ptr [ebp-0x664], 0x0A
7C 06                  jl    ok
FF 25 <ptr>            jmp   [ptr] -> GameServer 0x0051E699   ; штатный отказ: v33=1 + LABEL_49
ok:
6A 2D                  push  0x2d
8B 4D 0C               mov   ecx, dword ptr [ebp+0x0C]
FF 25 <ptr>            jmp   [ptr] -> GameServer 0x0051E635   ; site+5
```

### Почему отказ ведёт на существующие адреса, а не на новый код

`0x0051AD2E` и `0x0051E699` — это ровно те `mov byte ptr [ebp-0x11], 1` + `jmp`, которые сток и так
выполняет при превышении предела. Они уводят в ветки `0x51B26F` / `0x51EB9E`, отправляющие клиенту
**штатный ответ 9906 / 9910 с кодом 1** (`push 0x26B2` / `push 0x26B6`, `call 0x4C28F0`).
Ни одного нового пакета, ни одной новой строки лога патч не создаёт.

### Что НЕ меняется в штатном пути

Ровно 8 (10) записей по-прежнему принимаются полностью. После копирования восьмой (десятой)
счётчик становится 8 (10), но тело цикла в этот проход больше не выполняется — условие
`i < len-1` уже ложно, и цикл заканчивается по своей обычной причине. Новая проверка срабатывает
только там, где сток и так возвращал отказ 1; разница ровно одна: отказ наступает **ДО** записи за
буфер, а не после неё.

## 5. Почему S1 опровергнут — доказательство

Полный побайтовый диф нашего образа (`RE\ida\server_work\GameServer.exe`) и живого показывает
**семь** переворотов ветвлений, и все они в одну сторону:

| VA | наш образ | живой | что это |
|---|---|---|---|
| `0x00523F8B` | `EB 47` (`jmp`) | `74 47` (`je`) | `sub_523F00`, ветка «есть секрет» |
| `0x0052400D` | `EB 41` (`jmp`) | `74 41` (`je`) | `sub_523F00`, ветка «без секрета» |
| `0x00526CFC` | `EB` | `74` | соседнее семейство проверок |
| `0x00526D3B` | `EB` | `74` | — |
| `0x00526D7A` | `EB` | `74` | — |
| `0x00526DB9` | `EB` | `74` | — |
| `0x00526DEE` | `EB` | `7E` | — |

В живом образе ветка несовпадения MD5 полностью на месте: она наращивает счётчик нарушений у
`CUser+8` (его читает `sub_524070@0x524070`: `return v3 && *(CUser+8) > 5`), пишет в лог строку
`if( memcmp(szMD5, &pMsg[(HEADER_SIZE-1)+iSecretSize], MD5_SIZE) != 0 ) Command = %d`
(`.rdata` @`0x598E10`, вторая — @`0x598DC8`) и возвращает 0, после чего вызывающий обработчик
просто не выполняется.

⇒ Утверждение отчёта верно **для нашей локальной копии**, которая, как и записано в MEMANTO
(`gameserver-decompile-stale`), является сборкой со снятой защитой. К живому серверу оно
не относится. **Патч по S1 не нужен и не пишется.** Ключ `ReportMd5GateState` оставлен, чтобы это
можно было перепроверить прямо на живом процессе при следующем старте, не веря ни отчёту, ни
этому документу.

## 9. Риски и связанное

- **Риск изменения штатного поведения — нет.** Новая проверка срабатывает исключительно на девятой
  (одиннадцатой) записи, то есть там, где сток и так отвечал отказом с кодом 1. Разница лишь в
  моменте отказа.
- **Риск ложного MISMATCH — низкий**, но реальный, если владелец подменит `GameServer.exe`: сверка
  идёт по 18 + 13 байт на каждый дефект, и при несовпадении патч НЕ ставится (это штатное
  безопасное поведение, а не ошибка).
- **Связанное:** S6 (пул лотов) — `ItemRelayServer/lot-pool-exhaustion-s6.md`; там же объяснено,
  почему это дефект ДАННЫХ, а не размера пула, и почему лечится не патчем.
- **Оставлено открытым (владельцем не поручено):** S2 (инверсный фильтр цены), S5 (немой отказ по
  флагу окна), S7 (контроль количества), D8 (в клиенте нет четвёртого срока 168 ч / 7 %).
- Проверка `verify_dll.py` расширена двумя площадками (`P19.S3`, `P19.S4`) и двумя трамплинами;
  прогон 2026-08-27 — «ВСЁ СОШЛОСЬ».
