## ЧТО ЛЕЧИМ

### СО-1 — CompleteLock [ключ `CompleteLock`, ВКЛ]
`CharExchangeCompleteReq@0x4E4720` при обоюдном подтверждении сразу зовёт `…Complete` (запрос в
БД). Дефекта два: (а) между запросом в БД и ответом БД нет замка «в полёте» по окну; (б) сверяются
только оба ПОДТВЕРЖДЕНИЯ (`+659`/`+660`), но не обе ФИКСАЦИИ (`+657`/`+658`). Повторное подтверждение
по тому же окну до ответа БД снова видело бы оба подтверждения и снова инициировало бы БД-запрос
по тому же окну.

Правка — трамплин на `0x4E48B3` (перед стоковым диспетчером `…Complete`). Условия перед вызовом:
1. обе стороны подтвердили (стоковое `v10`);
2. ОБЕ фиксации взведены (`запись+0xE1D` && `+0xE1E`, они же `+657`/`+658`);
3. окно НЕ «в полёте» (`g_inflight[idx]==0`).

Пометка «в полёте» ставится тут и снимается в ЕДИНСТВЕННОЙ точке освобождения окна
`sub_4DF6D0@0x4DF6D0` (её зовут ответ БД `recvDB…`, отмена `CharExchanageCancelReq`, разрыв
`DisConnectUser`, реген) — трамплин на прологе `0x4DF6D0`. Повторный 5293/Complete по помеченному
окну идёт в штатный эпилог функции без БД-запроса.

### СО-3 — WindowBounds [ключ `WindowBounds`, ВКЛ]
`windowIndex` в 5288/5290/5291/5293 проверялся только на `< 0`; при `idx >= 550` обращение
`561*idx` уходит за массив окон (ёмкость 550, `sub_4DF660`). В каждом из четырёх обработчиков
добавлена верхняя граница `idx < 550`; отказ ТЕМ ЖЕ штатным путём (лог / 5289 код 0 и т. п.).
Для 5288 дополнительно граница ячейки лотка `dragReq[4]` (`activeSlot`) `< 5` (u8 идёт в `54*slot`).

### СЛ-1 — StoreSlotBounds [ключ `StoreSlotBounds`, ВКЛ]
`CharSelfStoreBuyItem@0x504E70`: индекс лота витрины `v42 = record45[+22]` из тела 6309 идёт в
`57*v42+1587` без верхней границы (штатно 0..9). В обоих циклах (проверка/сумма и применение)
сразу после чтения `v42` из пакета добавлена граница `0 <= v42 < 10`; отказ штатным 6310
(код 2 в цикле проверки, код 5 в цикле применения — обе ветки сбрасывают замок покупки `+0x5AEF`
и шлют 6310).

### DeathCancelExchange [ключ `DeathCancelExchange`, ВКЛ]
`SendCharDead@0x4CB480` в момент смерти не сбрасывал обмен (нет строки Cancel) — «зависший» обмен
жил до разрыва/регена. В ветке установки «мёртв» (`0x4CB5D8`, `mov [pUser+0x4F],1`) при
`CUser+0x145` (в обмене) вызывается `CharExchanageCancelReq(this, userNum, nullptr, CUser+0x149)`
— ровно как уже делают `CharRegenVillage`/`CharRegenIndunBeforePortalMove`/`DisConnectUser`
(партнёру уходит 5287, окно освобождается, `g_inflight` снимается).

### СО-4 — AcceptNeedsRequest [ключ `AcceptNeedsRequest`, ВЫКЛ по умолчанию]
`CharExchangeAcceptReq@0x4DFC80` подкод 1 создаёт окно, проверяя лишь «обе стороны свободны» —
факта висящей заявки A→B сервер не хранит (клиент держит таймаут 33 с сам). Правка двойная:
(а) в `CharExchangeReq@0x4DF830` на УСПЕХЕ (5283 код 1 ушёл цели, `0x4DFBEE`) запоминается
«заявка initiator→target» с меткой времени; (б) в AcceptReq перед взятием окна (`0x4DFE5B`)
требуется свежая (< `AcceptTtlMs`, по умолчанию 60 000 мс) запись `target==принимающий,
initiator==заявитель`, иначе штатный отказ 5285 код 0. Запись одноразовая (снимается при принятии).
TTL с запасом над клиентскими 33 с, чтобы ни одна честная заявка не была отклонена.

**По умолчанию ВЫКЛ** — решение владельца (оригинал живёт с этим, `trade_re_report §3.1`).
Включать после сверки на живом, кто ещё вызывает Req/Accept.
