## 1. Дефект стока (симптом → диагноз)

Жалоба игроков на «телепорты» при ходьбе. `MoveSyncProcess` (нить карты, `RunProcess sub_4C0EA0` раз в ≥ 100 мс, та же нить, что
`ConnectSocketMsgProcess` → `CharMove/CharStop`) интегрирует позицию идущего: `new = cur + dt·скорость·направление`
(`CUser+0x54EE/+0x54F2`). Если новая точка вне карты или на непроходимой клетке, сток зовёт `sub_542520` (снимает игрока со стека
хода: DWORD `CUser+0x33` := 0) — и всё: позиция остаётся последней пройденной, **клиенту ничего не уходит**. Клиент (свой грант 4007 —
или серверный ход «Паники» `ProcessState_SKILL_STATE_FEAR@0x488040` на 2000 ед.) продолжает траекторию по своей сетке. Следующий 4006
попадает в ветку «стоит» `CharMove@0x544EB0` (0x5453F1, `fucompp` — ТОЧНОЕ равенство cur клиента и сервера) → «CharMove Hack Position»
в GameLog, 4007 result=5 и снап клиента. За 21.10 — 82 строки у пяти игроков (пачки раз в ~1 с у стены — каденция клавиатурного 4006).

требует: игрок остаётся в стеке, клиент сам дойдёт до цели и пришлёт 4008/4006 (ветка «идёт» терпит 1000 мс).

## 3. Что делает P77

Каждая из S1…S4 `call 0x542520` заменена на вход DLL с тем же соглашением (thiscall: `ecx` = CUserMoveManager, `[esp+4]` номер
игрока (слово), `[esp+8]` строка причины; снимает 8 б). Вход читает флаг стека `CUser+0x33`, зовёт сток `sub_542520` и **только если
игрок действительно снят со стека** (флаг был ≠ 0, стал 0; сток мог не снять — «Exception Error 1…4») шлёт штатный 4009 в точку сервера
той же формой, что CharStop «Revision Pos» (0x546030…0x546172):

| смещение тела (27 б) | значение |
|---|---|
| +0 | 0 |
| +1 i16 | номер игрока (userNum) |
| +3 i16 | 0 (MOVE_STATUSIDLE) |
| +5 / +9 float | текущая X / Z сервера (`CUser+0x54EE/+0x54F2`) |
| +13 / +17 float | те же X / Z |
| +21 float | скорость сервера `CUser+0x54FE` (вне (0; 5) — 0: порт кэширует +21 только в этом диапазоне) |
| +25 i16 | −1 (нет цели) |

Себе — `SendPacket@0x4C28F0(нить, 4009, 27, userNum, тело, userNum, 1)`; сектору — `sub_52E6D0(CUserManager, userNum, 4009, 27, тело, 1)`
(кроме себя; скрытому оператору `CUser+0x3BC3B == 300` + `IsOperatorIndex` — не шлём, как P74). Точка ≤ 0 / не число — не шлём.

**Клиенты.** Оригинал: `Recv_EntityStop@0xF3AB50` (network.c:39457) — свой: `player_setPositionAndTarget(pos)` (снап + цель = точка);
чужой: состояние 0 и снап при другой клетке. Порт: `UAsdaNetSubsystem` case 4009 → `OnEntityMove(bStop)` →
`UAsdaWorldSubsystem::OnNetEntityMove`: свой — `NetSnap(cur)` (стоп + позиция; бит 2 и +25 не трогает — как эталон), чужой — `NetSnap`.
Перевод координат порта — перестановка осей и знак (`AsdaCoord`), без масштаба: float точки 4009 возвращается в следующем 4006 тем же
float → ветка «стоит» проходит точным равенством (стенд: 4006 из точки 4009 через настоящий CharMove — result 1, Hack Position 0).

**Частота.** Не больше одного 4009 на каждое снятие со стека; вернуть игрока на стек может только `CharMove` (4006 или ход «Паники»), т.е.
4009 от P77 не чаще принятых 4006 (а каждый принятый 4006 сток и так рассылает сектору 4007). Если сток не снял — ничего не шлём (стенд T6:
6 шагов подряд в стену без снятия — 0 пакетов). `MinIntervalMs` — дополнительный пол на сессию (по умолчанию 0).

**Нить.** Вход исполняется в нити карты внутри `MoveSyncProcess` — там же, где сток зовёт `SendPack_CharPositionToBattleServer`, и в той же
нити, что `CharMove/CharStop` шлют свои 4007/4009. Новых нитей и замков стока нет (свой замок P77 — только таблица сессий для журнала).

**Что остаётся.** Если следующий 4006 клиента ушёл ДО прихода 4009 (окно ≈ ½ RTT + шаг синхронизации ≤ 100 мс), сток по-прежнему пишет
«CharMove Hack Position» и шлёт 4007 result=5 в ту же точку — снап в ту же точку, что и 4009. У стены остаётся мелкий откат на величину
пробега клиента за RTT (вместо пробега до 1 с с откатом). Сетки проходимости клиента и сервера P77 не сверяет (вариант 3 разбора — отдельно).

**Связанные патчи.** P57 (счёт Hack Position, режим журнала на живом) — срабатываний станет меньше, логика не меняется; P57 в
MoveSyncProcess только СВЕРЯЕТ байты 0x542F34/0x542F49 (не пересекаются). P53/P55/P56/P66 — не затронуты. С P01…P76 площадок не делит
(verify_p77: в `src/patches` других записей в 0x5427D0…0x542F90 нет; stand_map — пересечений байт 0).

## 4. Ключи `[P77_MoveSyncStopPoint]`

| ключ | умолч. | смысл |
|---|---|---|
| `Enabled` | 1 | 0 — не ставится (сток) |
| `BlockedTile` | 1 | ветка «don't move tile» (S4) |
| `PosOverMap` | 1 | ветка «iMovePos Max Over» (S3) |
| `PosBelowMap` | 1 | ветка «iMovePos - Value2» (S2) |
| `MotionStartZero` | 1 | ветка «iMotionStartTime = 0» (S1) |
| `SendToSector` | 1 | 4009 и соседям по сектору (как «Revision Pos»); 0 — только себе |
| `SkipHiddenOperators` | 1 | скрытому оператору соседям не слать |
| `MinIntervalMs` | 0 | пол между 4009 от P77 на сессию, мс (0..60000) |
| `LogEvents` | 1 | строка в PatchLog на событие |
| `LogIntervalSec` | 10 | не чаще 1 строки за столько секунд на сессию (0..3600; 0 — каждое), в строке — число пропущенных |

Сверяемые байты (кроме площадок): аргументы перед каждым вызовом (`push` строки причины, номер `[ebp-40h]`, `this` `[ebp-5Ch]`),
`jmp 0x542F4F` после, пролог `sub_542520`, чтение флага `[ecx+33h]` (0x542597), получение CUserManager `[edx+4]→[eax+34h]` (0x542572),
проверки «в игре»/UserIndex MoveSyncProcess (0x5428F5). Расхождение — `Mismatch`, ничего не пишется.

## 5. Журнал

PatchLog (`Log\Log_Patch\PatchLog_<дата>.txt`): при установке — `P77 S1…S4 … -> 0x…: сток + 4009 в точку сервера` и `P77: площадок 4; …`;
на событие — `[P77] «don't move tile»: <имя> (UserNum N, UserIndex M) остановлен сервером в (X, Z), клетка x,z — 4009 себе и сектору; по этой
сессии с прошлой строки без журнала: K`. Журнала античита нет (это не нарушение). Счётчики — экспорт `P77_GetStats` (стенд).
