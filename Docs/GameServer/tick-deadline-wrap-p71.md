## 1. Зачем
Такт `GetTickCount` = аптайм хоста @@ASTORY_SERVER_HOSTNAME@@; с 04.10.2026 он ≥ 2^31, **29.10.2026 09:51:50 UTC** проходит через 2^32 и обнуляется.
Сток GameServer держит четыре срока как абсолютные такты и сравнивает их с «сейчас» **беззнаково** (`cmp now, срок; jb/jae/ja`).
Срок, взведённый до обнуления (~0xFFxxxxxx), после обнуления «не наступает» 49,7 суток: периодика хранителя души встаёт,
голосование отряда висит, предметы на земле не исчезают, штраф лагеря не снимается (и наоборот — срок, перевалившийся через
2^32 при взводе, «наступает» сразу).

Лечение — **модульное сравнение**: «срок не наступил» ⇔ `(int)(now − срок) < 0`. Разность берётся по модулю 2^32, поэтому и
переход через 2^32, и аптайм ≥ 2^31 безвредны, пока расстояние до срока < 24,8 сут (у трёх площадок — 15 с / 5 мин; у
штрафа лагеря — потолок 24,8 сут, см. §3C).

## 3. Логика стабов
Все стабы — `__declspec(naked)`, вызываются `call` с площадки, выставляют ровно те флаги, которые читает следующий jcc стока
(`jb`/`jae` — CF; `ja` — CF и ZF). `shl r,1` даёт CF = бит 31 разности (знак по модулю 2^32). Регистры и стек сохраняются
(кроме результата, который сток сам ждёт: eax на D, edx на C3). push/pop/ret флаги не трогают.

- **A** (ecx = now, eax = CUser): `edx = [CUser+3F461h]; если 0 → CF=0 («истёк», как сток при now ≥ 0); иначе edx = now − edx; shl`.
  Проверки «поле ≠ 0» у стока на этой площадке нет; поле 0 — у слота CUser, не тронутого с запуска процесса; при входе DB-пакет
  2473 (`sub_48E0A0`, 0x48E15E) пишет свежий срок. Срок всегда «свежий такт + 15000» (три писателя), знак стоку не нужен.
- **B** (edx = now, ecx = this, eax = 0x41·i): `edx −= [this+eax+122h]; shl`. Гейт «≠ 0» (0x46C0F4) стока остаётся перед площадкой.
- **C** — штраф лагеря RoseWar `CUser+0x3F454`. ⚠ Абзац ниже — первичная (до ревизии) модель; поправка p71fix — в §7. Источник значения:
  DB-пакет **2460** (DBManager `sub_43A140`: `EXEC UPCharCamp UserIndex, CharIdx`, байты 12..15 результата) → GS `sub_465FC0`
  (диспетчер DB-ответов, `case 0x99C`) пишет `+0x3F454 = 1000 × значение` и тут же сравнивает с `GetTickCount` (0x4660FD/`jae`):
  «не истёк» → 6741 флаг 1; иначе поле := 0, `sub_46AA10(…, 0)` → **2471** `UPCharCampPenaltyUpdate UserIndex, CharIdx, Time`.
  TimerProcess (`sub_46A960`): истёк → поле := 0, 2471 Time 0, 6741 флаг 0. Разрыв/портал: `sub_46AA10(поле)` → лог
  «[I] Convert Penalty Time..!! … Time:%d» с `Time = поле/1000` → 2471. ~~Ни одно место GS не взводит штраф~~ — **ЛОЖНОЕ «НЕТ» (ревизия КРИТ-1):** вызовов `sub_46AA10` пять, пятый — кик голосованием
  `sub_46C090` @0x46C349 с `GetTickCount() + 1800000`: в БД уходит АБСОЛЮТНЫЙ такт/1000, и в пределах одного аптайма сток самосогласован (см. §7).
  Лечение (ключ `FixTimer3F454`, шесть площадок одним ключом — формат значения в БД обязан быть единым):
  - **C5 (p71fix)** `0x46C335` `add eax,1B7740h` → `mov eax,1B7740h`: от кика в БД уходит длительность 1800 с.
  - **C1** `St71_PenaltyWrite` (eax = с): `с ≤ 0 → 0`; `с > MaxPenaltySec` (ini, 604800) → **старое абсолютное значение/мусор**:
    поле := `now − 1` (ненулевой истёкший срок; `now = 1` → `0xFFFFFFFF`) + `P71_StalePenalty` (строка PatchLog и Log_Operator
    «penalty value N s > MaxPenaltySec M, treated as stale absolute tick, cleared  UserIndex  Name»); дальше сток сам: C1b «истёк» →
    поле := 0, 2471 Time 0 → значение стёрто в БД (при поле 0 сток не шлёт ничего — поэтому именно истёкший срок, а не 0);
    иначе `1000·с`; `срок = GetTickCount + мс` (через ту же ячейку импорта 0x583028); сумма ровно 0 → 1; запись в `[CUser+3F454h]`;
    eax = записанное (дальше у стока eax мёртв: `lea ecx,[ebp-8]; call sub_49B9B0`), ecx/edx сохранены. Молчаливого потолка
    24,8 сут больше нет; `MaxPenaltySec > 2 147 483` режется до него со строкой PatchLog (1000·с должно помещаться в int).
  - **C1b/C2** — модульное сравнение (CF = знак(now − срок)); `jae`/`jb` стока как были.
  - **C3** `St71_PenaltyRemain` (ecx = CUser): `edx = (int)(срок − now)`, отрицательный → 0. Дальше сток: `push edx` →
    `sub_46AA10` → Time/1000 с (меньше 1000 мс → 1 с, как сток) → 2471 → в БД уходит **остаток**, не срок. Остаток 0 → снять штраф.
  - Не меняются гейты «≠ 0» (0x4660EB, 0x46612F, 0x46A999, 0x463E6C, 0x525C9D, 0x5268B0, 0x5433A3) и 6707 код 9 (RegistUser
    0x463E7C шлёт младшее слово поля — у стока это мусор от `1000·с`, остаётся мусором; см. отчёт, открытый вопрос).
  - Предел `MaxPenaltySec` (7 сут при штатных 1800 с): модульная разность держит < 24,8 сут; у стока `1000·с` переполнялось с 49,7 сут.
- **D** (edx = предмет, `[ebp-4] = T = now − 300000`): `eax = [предмет+25h]` (такт падения, как сток); `0 → ZF=1` (удалить, как
  сток: `0 ≤ T`); иначе `eax − T; shl` → `ja` ⇔ CF=0 ∧ ZF=0 ⇔ `(int)(такт − T) > 0` (моложе 5 мин — оставить).

⚠ Предостережение аудита §4 (поля, пишущиеся свежим тактом после такта кадра): на всех четырёх площадках срок пишется
только как «свежий такт + 15000 / + штраф», т.е. всегда в будущем относительно любого позднейшего чтения; знак стоку нигде
не нужен. Единственный источник «устаревшего» срока — слот CUser, не тронутый > 24,8 сут при работающем процессе (A), и он
перезаписывается при входе.

## 5. Откат
Снять DLL (или `Enabled=0` в секции) и перезапустить GameServer/Indun. Побочных данных нет: формат поля `+0x3F454` живёт
только в памяти процесса; в БД хранятся секунды: с P71 — ДЛИТЕЛЬНОСТЬ/остаток (1800 от кика), у стока — абсолютный такт/1000.
⚠ После отката строки БД с длительностью (≤ 7 сут) сток прочтёт как «такт/1000» — штраф истечёт сразу (малое число < now).
⚠ GameServer и Indun должны стоять на одной версии DLL: сток на одном из них запишет в БД абсолютный такт, который P71 на
другом обнулит как старое значение (с записью в Log_Operator) — штраф не удержится, но и не зависнет.

## 7. p71fix по ревизии 15.10 (`review_P71P72_20261015.md`)
**Что было (КРИТ-1).** Утверждение «GS никогда не взводит штраф сам, значение из БД — длительность» — ложное «нет»: вызовов `sub_46AA10`
пять. Пятый — кик голосованием отряда, `sub_46C090` (GameServer.c:44131), дизасм (три образа одинаково):
```
0046C32F  FF 15 28 30 58 00    call dword ptr [583028h]   ; GetTickCount
0046C335  05 40 77 1B 00       add  eax, 1B7740h          ; + 30 мин
0046C33A  50                   push eax                   ; Time → sub_46AA10 → /1000 → 2471 UPCharCampPenaltyUpdate
0046C33B  66 8B 95 50 FF FF FF mov  dx, [ebp-0B0h]        ; userNum кикнутого
0046C342  52                   push edx
0046C343  8B 8D 4C FF FF FF    mov  ecx, [ebp-0B4h]       ; this
0046C349  E8 C2 E6 FF FF       call 46AA10h
```
`eax` после площадки нигде, кроме `push`, не используется (0x46C34E `movzx eax,[ebp-9]`); поле `+0x3F454` кикнутого при кике НЕ пишется
(писатели в .text: 0x46608B, 0x46613B, 0x46A9B3 — скан `54 F4 03 00`); он уходит порталом 5055/−1, штраф приходит с 2460 при входе. Т.е.
в стоке в БД лежит абсолютный такт/1000, и в пределах одного аптайма сток самосогласован; первичный C1 (`now + 1000·Time`) превращал
30-минутный штраф в 24,8 сут (потолок), а C3 на разрыв сохранял остаток — штраф самоподдерживался через БД.

**Что стало.**
- **C5** `0x46C335` `add eax,1B7740h` → `mov eax,1B7740h`: от кика в БД уходит 1800 с — семантика «длительность» едина на всех путях
  (кик → 1800; разрыв/портал → остаток; истечение → 0). GetTickCount по 0x46C32F по-прежнему зовётся (сосед не тронут), результат не нужен.
- **СРЕДН-1**: ключ `MaxPenaltySec` (604800). Значение из БД больше предела — старая строка прежней семантики (кик до P71: такт/1000 ≈
  аптайм в секундах, на @@ASTORY_SERVER_HOSTNAME@@ ≈ 3,1·10⁶) или мусор: поле := истёкший срок `now − 1` + строка PatchLog и Log_Operator
  `P71: penalty value N s > MaxPenaltySec M, treated as stale absolute tick, cleared`; сток следом сам шлёт 2471 Time 0 и стирает строку в БД
  (при поле 0 сток не шлёт ничего — поэтому не 0). Молчаливый потолок 24,8 сут снят.
- **КОСМ-1** (P72 `Site check[12]` → `[9]`), **КОСМ-2** (док P72 §7: маршрут «молча» и дефект D4), **КОСМ-3** (комментарий о соседях:
  подтверждение ревизии 169 VA). **НИЗК-2** — задокументировано в §3C, не трогается.

**Почему так, а не «минимальный вариант» (только C1b/C2).** Минимальный вариант оставляет дефект рестарта хоста (старое абсолютное
значение «висит» до 49,7 сут) и несовместим с остатком на разрыв; единая длительность переживает рестарт и переход 2^32, а старые строки
БД вычищаются сами при первом входе каждого персонажа. Текст процедур `UPCharCamp`/`UPCharCampPenaltyUpdate` по-прежнему не виден
Log_Operator «stale absolute tick» у свежих киков — тогда MaxPenaltySec/C5 пересмотреть.
