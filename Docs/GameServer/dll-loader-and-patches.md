# GameServer — DLL-загрузчик `AsdaPatch.dll` и состав патчей

- **Дата:** 2026-08-04.
- **Статус:** 🟡 **ЭТАП 1 (каркас) ГОТОВ И ПРОВЕРЕН ЛОКАЛЬНО.** Реестр патчей пока пуст —
  наполнение этапами 2…6. На живом сервере НЕ применялось.
- **Процесс:** GameServer.
- **Тип:** смена всей схемы правок — вместо десятка бинарных патчей `.text`
  **одна** правка exe (инъекция импорта) + внешняя DLL, которая ставит патчи в памяти.
- **Проект:** `AstoryServer/Patches/AsdaPatch/` (исходники, `build.bat`, `tools/inject_import.py`).

---

## ЗАЧЕМ (проблема старой схемы)

К августу 2026 в живом `GameServer.exe` накопилось **447 байт правок в 19 участках**
(GM-объявление, лог скиллпоинтов, гейт неуязвимости, премиум-гача, DB-2601, снятые
проверки, строка IP, свежий обработчик 6616). Каждая — байты в `.text` + код в
нулевом хвосте секции. Последствия:

- хвост `.text` кончался: под четыре хука анонса оставалось ~780 байт;
- любую правку нельзя выключить, не пересобирая бинарь;
- «чей это патч и зачем» восстанавливалось дифом постфактум;
- сборка велась от бэкапа, который **сам уже содержал чужие правки**.

Новая схема снимает всё это разом.

## КАК DLL ПОПАДАЕТ В ПРОЦЕСС — инъекция в таблицу импорта

Скрипт `AstoryServer/Patches/AsdaPatch/tools/inject_import.py`. **Единственная** правка exe.

1. В нулевой хвост `.rdata` (`0x1A57E2..0x1A6000`, 2078 б свободно) кладётся новый
   массив дескрипторов импорта: 5 исходных **1:1** + наш (`AsdaPatch.dll` / `AsdaPatchInit`)
   + терминатор, а также `OriginalFirstThunk`, `IMAGE_IMPORT_BY_NAME` и строки.
   Блок: RVA `0x1A5800`, **180 байт**.
2. ★ **`FirstThunk` (IAT нашего импорта) кладётся в хвост `.data`** — RVA `0x1A7F80`,
   8 байт. Секция `.data` имеет характеристику `WRITE`.
3. В PE-заголовке меняются **только** `DataDirectory[IMPORT].VirtualAddress` и `.Size`
   (файловое смещение `0x170`): `rva 0x1A4B84 size 0x78` → `rva 0x1A5800 size 0x8C`.

Не меняются: `.text`, число секций, `SizeOfImage`, размер файла (1 740 800 б), CheckSum.

### ★★★ Грабля, на которой это падало (задокументировать намертво)

Первая версия клала `FirstThunk` тоже в `.rdata`. Результат — `ACCESS_VIOLATION`
на старте, **до** входа в `DllMain`. Отладчик:

```
ntdll!LdrpSnapModule+0x3cc   mov dword ptr [eax], edi     ← запись адреса функции в IAT
```

Причина: загрузчик снимает защиту страниц только с региона, описанного
`DataDirectory[IAT]` (здесь `0x183000..0x18325C`). Всё, что вне него, обязано
лежать на **изначально записываемой** странице. `.rdata` — read-only ⇒ падение.
**Правило: OriginalFirstThunk можно в read-only, FirstThunk — только в записываемую секцию.**

### Почему именно импорт, а не TLS/EntryPoint

- **ноль байт в `.text`** — правкам кода нечего ловить античиту в файле;
- DLL грузится загрузчиком ОС **до точки входа**: потоков ещё нет, HackShield/GameGuard
  не инициализированы, образ `.text` уже отображён — патчить безопасно и без гонок;
- TLS-директории в exe **нет** (строить с нуля + вызов под loader-lock — хуже);
- хук точки входа = правка `.text`, то есть ровно то, от чего уходим;
- откат = 8 байт в заголовке (скрипт их печатает) либо подмена exe обратно.

### ⚠ Принимаемые риски

1. **Нет DLL — процесс не стартует** (`0xC0000135`). Аварийный откат — исходный
   `GameServer.exe_before_mine_patch.exe`.
2. Патчи теперь **в памяти**, файл на диске — чистый сток. Если античит сверяет `.text`
   в памяти с файлом, это отличие от прежней схемы. Проверочный шаг после первого
   старта: `Log\Log_HackShiled\*`. (`HackShield.crc` от 2008 г. — клиентский блоб;
   живой сервер годами работает с 447 патчеными байтами, самопроверки образа нет.)

## УСТРОЙСТВО DLL

```
AstoryServer/Patches/AsdaPatch/
├─ src/
│   ├─ dllmain.cpp          DllMain → Config → Log → паспорт хоста → якоря → реестр патчей
│   ├─ SrvApi.h             ★ ЕДИНСТВЕННЫЙ реестр адресов/сигнатур GameServer
│   ├─ Config.h/.cpp        ConfigSet\patches.ini (UTF-16LE), автосоздание с комментариями
│   ├─ Log.h/.cpp           Log\Log_Patch\PatchLog_<ГГГГММДД>.txt (cp1251, как прочие логи)
│   ├─ Hook.h/.cpp          Verify / WriteBytes / WriteJmp / WriteCall / Dump, RAII-Unlock
│   └─ patches/             Patches.h + Registry.cpp + по .cpp на патч
├─ build.bat                VS2022 x86, /MT /O2 /GS- → out\AsdaPatch.dll
├─ tools/inject_import.py   инъекция импорта (+ верификация результата)
└─ out/                     AsdaPatch.dll, GameServer.exe.dllhost.exe
```

- **Сборка:** `build.bat` (ищет `vcvars32.bat` VS2022 Community/Pro/Enterprise/BuildTools).
  Флаги: `/MT` (статический CRT) → зависимости DLL только `KERNEL32` + `USER32`.
- **Хуки:** 5-байтовый `jmp rel32` из `.text` в трамплины DLL (`__declspec(naked)`),
  вытесненные инструкции воспроизводятся в трамплине. `rel32` покрывает всё
  32-битное адресное пространство.
- **★ Сверка обязательна:** каждый патч перед записью сверяет оригинальные байты
  (`VerifyAllSites`). Несовпадение → патч **не ставится**, в лог идёт строка
  `MISMATCH <патч> @0xVA: ожидалось […], в памяти […]`, остальные патчи продолжают.
- **Ранняя трассировка:** `<GameServer>\asdapatch_boot.log` пишется чистым kernel32
  (без CRT/user32) на каждом шаге инициализации. Если `DllMain` упадёт — последняя
  строка в файле покажет, на каком именно шаге.

### Паспорт хост-образа в логе

При каждом старте пишутся: путь, база, размер и **CRC32** файла, `SizeOfImage`,
точка входа, таблица секций и **якорные байты 14 будущих точек перехвата** — то есть
адреса из `SrvApi.h` сверяются с реальным образом ещё до установки патчей.

## `ConfigSet\patches.ini`

Создаётся автоматически при первом запуске (UTF-16LE + BOM — родной формат Win-ini API),
с комментариями по каждому патчу. Правится при **остановленном** сервере, читается один
раз при старте.

- `[General] MasterEnable` — главный выключатель. **При создании = 0** (режим проверки
  каркаса). После успешного старта администратор ставит 1.
- По одному разделу на патч, у каждого `Enabled`.
- `[P11_ServerAnnounceSources]` — параметры анонса: `PickupEnabled`, `GachaEnabled`,
  `PremiumGachaEnabled`, `RefineEnabled`, **`RefineThreshold=7`**, `Scope` (0 = весь
  сервер, 1 = сектор), `GradeTableFile`.
- `[P12_DefaultServerIp] Value` — строка IP; пусто = не трогать.

### ⚠ P08 и P09 — это ОБХОДЫ, а не фиксы

`P08_FunctionItemUseCheckOff` (`Char_FunctionItem_Use`, `0x4ED8DE`) и
`P09_ChargeShopBuyChecksOff` (`CharChargeShopBuy`, 4 флипа) — правки **чужого
происхождения**, найденные дифом живого сервера; автор и мотив в проекте не
зафиксированы. По смыслу это **снятие штатных проверок**, а не исправление ошибки.

**По решению юзера значение по умолчанию = `1`** («как сейчас на живом»), чтобы
поведение сервера не менялось при переходе на DLL. Флаги заведены, чтобы можно было
выключить позже. **Отключение (`0`) вернёт штатные проверки** — использование
функциональных предметов и часть покупок в кэш-шопе начнут отклоняться там, где обход
их глушил. Менять только осознанно и с проверкой на игроках.

## Этап 2 — P12, P02, P03, P04 (СДЕЛАН, ждёт проверки на живом)

### Бережное слияние `patches.ini`

Администратор уже правил файл руками, поэтому конфиг больше **никогда не
перезаписывается целиком**:

- существующие значения и **комментарии администратора сохраняются как есть**;
- отсутствующая **секция** дописывается в конец файла вместе со своими комментариями;
- отсутствующий **ключ** вставляется в свою секцию через `WritePrivateProfileString`;
  пользовательские значения не трогаются;
- всё добавленное перечисляется в `PatchLog` построчно;
- кодировка определяется по BOM: файл, пересохранённый администратором как ANSI,
  дописывается в cp1251, UTF-16LE — в UTF-16LE.

**Проверено отдельным тестом.** Подсунут «правленый вручную» ini: свой комментарий
в шапке, `MasterEnable=1`, `[P02] Enabled=0`, `[P12] Value=10.20.30.40`, без ключа
`Version`, без 10 секций. Результат: все пользовательские значения и комментарии
`P02` корректно отработал как `[ВЫКЛ]`, `P12` применил **пользовательское**
значение `10.20.30.40`.

### Реализация патчей

Все — трамплины в DLL, вызываемые 5-байтовым `jmp`/`call rel32` из `.text`;
вызовы функций сервера — косвенные (`call dword ptr [...]`), чтобы не портить регистры.

| патч | точка | как |
|---|---|---|
| **P12** | `0x585610` (.rdata) | слот **16 байт**: `"61.106.140.206\0\0"` (дальше идёт `"GameServer_AR"`). Пишет значение из ini, дополняя нулями; максимум 15 символов; пустое значение = не трогать |
| **P02** | `0x42CF5D` (5 б) | подмена цели `call`: `Send_ScreenShotCommand@0x551000` → трамплин. Сигнатура сохранена `int __thiscall(mgr, __int16 userNum, int* pkt)`, `ret 8` |
| **P03** | `0x551530` (11 б) | `jmp` → трамплин, возврат `0x55153B`. Воспроизводит `mov ecx,[ebp-0x40C]; call 0x52EA20`, добавляет лог, результат сохраняется через `push/pop eax` |
| **P04** | `0x5518FF` (10 б) | `jmp` → трамплин, возврат `0x551909`, отказ `0x551960`. Проверка `sub_52ED50` (оператор?), затем оригинальные `mov edx,[ebp-0x0C]; cmp [edx+0x3BC3D],1` |

★ **P02 — исправлена мина оригинала.** В бинарном кейве `0x582A80` пролог делал
`push ecx` (резервируя `[ebp-4]`), но `mov [ebp-4], ecx` **отсутствовал** — оба
последующих `mov ecx,[ebp-4]` читали неинициализированную ячейку стека. Работало
только по счастливой раскладке стека вызывающего. В DLL `this` сохраняется явно.

★ **P04 — флаги.** Последняя инструкция трамплина перед возвратом — тот самый `cmp`,
а `jmp dword ptr [...]` флаги не меняет ⇒ `jne` на `0x551909` получает ровно те же
флаги, что и в стоке.

⚠ **Известное ограничение P02 (оставлено как в оригинале, не «чиним» молча):** тело
объявления не валидируется (нет Secret/MD5-проверки) и берётся как C-строка от
`pkt+0x18`. Путь закрыт гейтом оператора. Кандидат на отдельную доработку.

### Проверка этапа 2 (локально, отладчиком)

Прогон в изолированной папке с `MasterEnable=1`; после срабатывания точки входа exe
снят дизассемблер памяти:

### ⚠ Что именно делают P08 и P09 (и чем грозит их отключение)

- **P08.** В стоке `Char_FunctionItem_Use` вызывает `sub_523F00` — **проверку
  MD5-подписи тела пакета**. Патч убирает вызов и подставляет «результат = 1»
  (`add esp,0x10` вручную снимает 4 уже положенных аргумента). Нетто: **проверка
  целостности пакета «использование функционального предмета» полностью отключена**;
  модифицированный клиент может слать такие пакеты произвольно.
  *Отключение патча (`Enabled=0`)* вернёт штатную проверку — если обход ставили
  из-за несходящейся подписи в текущей связке клиент/сервер, функциональные
  предметы перестанут работать у **всех** игроков.
- **P09.** Все четыре площадки в `CharChargeShopBuy` устроены одинаково:
  `cmp <значение из пакета>, dword_5F5E9C[eax]` → `je` мимо ветки «ошибка 14».
  Патч делает переход безусловным ⇒ **сверка со справочной таблицей кэш-магазина
  не выполняется**, ветка отказа недостижима, значение клиента принимается как есть.
  *Отключение патча* вернёт проверки — если серверная таблица не совпадает с тем,
  что шлёт текущий клиент, часть покупок начнёт отклоняться с ошибкой 14.

в проекте не зафиксированы. По решению юзера значение по умолчанию `Enabled=1`
(«как сейчас на живом»); флаги заведены, чтобы можно было выключить осознанно.

В ветке «условие не выполнено» кейв живого сервера уходит на `0x4F6E42` **без**

условным. Это поведение живого сервера, перенесено как есть, молча не «исправлялось».

### ★ Грабля MSVC inline asm (стоила отдельного круга проверки)

`mov ecx, dword ptr [0x7E0380]` MSVC собирает как **загрузку константы**
(`mov ecx, imm32`), а не чтение памяти. Нужен сегментный префикс:
`mov ecx, dword ptr ds:[0x7E0380]`. Ошибка видна только в дизассемблере — поймана
статическим верификатором. Также `out` — зарезервированное слово (инструкция),
меткой быть не может.

### Заточка: порог по ступени, показ в процентах

Решение юзера: **порог считаем по ступени `item+24 >= 6`** (`RefineThresholdLevel`),
а в тексте показываем **процент `item+27`** — то единственное, что игрок реально видит
(разбор ниже). Доп. порог по проценту — `RefineThresholdPercent=0` (не учитывать).

### Анонс неудачи

После зелёного анонса успеха взводится состояние; следующая **провальная** попытка
улучшить **тот же предмет** даёт красную строку. Реализация:

- состояние — статический массив в DLL на `0x226` записей по `userNum` (та же граница,
  что у серверной `sub_5328F0`), ~22 КБ, без аллокаций;
- ключ — `userNum + имя персонажа + код + plate + слот`. Уникального id экземпляра
  предмета в 57-байтовой записи **нет** (проверено), а один `userNum` после выхода
  игрока переиспользуется другим — поэтому имя обязательно;
- срок годности `RefineFailWindowSec=600` — страховка от переиспользования слота;
- **одна красная строка на один зелёный анонс**: после выдачи состояние снимается;
  следующий успешный анонс того же предмета взводит его снова. Отдельный кулдаун
  не нужен — очистка сама исключает серию.

### ★★ Почему не было анонса неудачи — и что исправлено

По утверждённому дизайну красная строка выдаётся **только после зелёного анонса того же
предмета**: состояние взводится при **успешной** попытке ступени ≥ порога. Если предмет
уже был выше +6 и игрок просто фейлил, состояние никогда не взводилось ⇒ тишина.
Работало как задумано, но не как ожидалось.

**Исправления:**
1. Новый ключ **`RefineFailRequiresPriorSuccess`** (по умолчанию `1` — штатное
   поведение). Поставить `0` — и анонсируется **любая** неудача по предмету, ступень
   которого уже ≥ `RefineThresholdLevel`, без предварительного зелёного анонса.
   Именно этого ждали на живом тесте.
2. **Диагностика в `Log_Item` на КАЖДУЮ попытку улучшения** — теперь видно, доходит ли
   до нас управление и что именно отсекло:

| строка | когда |
|---|---|
| `Refine IN User … Ok … Code … Plate … Slot … Lv … Pct …` | всегда, на входе |
| `Refine ARM …` | состояние взведено после зелёного анонса |
| `Refine SKIP … Reason <текст>` | отказ с причиной (ступень ниже порога, окно истекло, `RefineFailEnabled=0`, `CUser` не найден) |
| `Refine KEYMISS … arm(…) vs cur(…)` | ключи не совпали — печатаются оба |

Проверено по декомпилу: обе ветки (успех `v38 > v71` и провал `v38 <= v71`) **сходятся
на `0x500602`**, поэтому хук срабатывает и на неудаче; единственный ранний `return` до
нашей точки — при `CouponAmount < UseCoupon`.

## ★★★ РАЗБОР: улучшение предмета — это ПРОЦЕНТЫ, и сервер их знает

Требование юзера: «в игре фактически не отображается +1,2,3…, там В ПРОЦЕНТАХ; проценты
не константа, они по-разному применяются в зависимости от материалов». **Подтверждено
полностью, цепочка замкнута от таблицы на диске до `sprintf` в клиенте.**

### 1. Запись предмета (57 байт, общая для клиента и сервера)

| смещ | тип | смысл |
|---|---|---|
| `+24` | BYTE | **ступень улучшения** 0..20 (счётчик успешных попыток) |
| `+25` | BYTE | счётчик попыток всего |
| `+26` | BYTE | MaxUpgrade из таблицы предметов (`172*(code−20551)+146`) |
| **`+27`** | **WORD** | ★ **накопленный ПРОЦЕНТ улучшения** — то, что видит игрок |

Раскладка одинакова с обеих сторон: клиент ходит по инвентарю тем же шагом 57
(`item_inventory.c:49`: `*(_DWORD *)(this + 57*i)` — код, `+9` — количество, `+4` — plate,
`+5` — слот, `+14` — прочность).

### 2. Что именно показывает клиент

`item_inventory.c:4173`, и точно так же в ещё 9 местах (инвентарь, экипировка, тултип,
окно улучшения):

```c
if ( invSlotPtr[24] )                                    // предмет улучшался?
{
    v4 = Util_Identity16(*(_WORD *)(invSlotPtr + 27));   // ← item+27
    sprintf(Buffer, "+%d%%", v4);                        // ← "+N%"
}
```

`Util_Identity16@0xFF1140` — тождественная функция (`return a1;`), масштабирования нет:
**в `+27` лежит готовое целое число процентов**. Гейт показа — `item+24 != 0`.
Косвенно подтверждают игровые строки: `110112` «сила улучшения предмета выше **+88%**»,
`110324` «Результат: [%s] **[+%d%%]**».

### 3. Откуда берётся процент — считает СЕРВЕР

`CharShellItemUpgdate_0@0x4FEE50`, ветка успеха (`0x4FFF30…0x4FFF84`):

```
[ebp-8]      = старый процент                       (сохраняется «до»)
[ebp-0x112]  = 1                                    (успех)
++[ebp-0x208]                                       (ступень  = item+24)
++[ebp-0x207]                                       (попытки  = item+25)
[ebp-0x205] += ItemUpgrade[ScrollType-70].+8 + [ebp-0x0C]
   ^ процент   ^ прирост свитка              ^ бонус купона (Function_Table +9)
```

Таблица — **`ItemTable_Info\ItemUpgrade.txt`** (загрузчик `GameServer.c:70927`, шаг 12 б),
на живом сервере 21 строка:

| кол | смещ | смысл | значения |
|---|---|---|---|
| 0 | `+0` W | ScrollType | 70…90 |
| 1 | `+2` B | **нижняя граница процента** | 1, 20, 40, 60, 80 |
| 2 | `+3` B | **верхняя граница процента** | 19, 39, 59, 79, 99 |
| 3 | `+4` D | шанс успеха из 100000 | 70000 / 30000 / 20000 / 50000 |
| 4 | `+8` W | ★ **прирост процента за успех** | **3, 6, 10, 5** |
| 5 | `+10` B | класс свитка (оружие/броня) | 0 / 1 / 2 |
| 6 | `+11` B | требуемый tier предмета | 0…5 |

Колонки 1–2 — диапазоны **процентов** (1–19, 20–39, 40–59, 60–79, 80–99), сервером не
используются (клиентские, для подбора свитка). Шкала процента — **0…99**.

⇒ Прирост = «свиток + купон», то есть **зависит от материалов и из одной лишь ступени
НЕ выводится**. Вариант «слать уровень, а проценты считать на клиенте» **невозможен
в принципе** — одному и тому же `+24` соответствуют разные `+27`.
