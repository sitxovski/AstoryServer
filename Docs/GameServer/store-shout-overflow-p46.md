## 1. ЗАЧЕМ

Обработчик опкода **6316 «крик лавки»** `Recv_SelfStoreGlobalChat @0x508B40` (рассылает
сообщение всем онлайн-игрокам опкодом **5087**) в стоке копирует тело пакета в стековый
`char[80]` **БЕЗ проверки длины** — проверки стоят НИЖЕ по коду, уже ПОСЛЕ `memcpy`.
Декомпил (`RE/ida/server_work/GameServer.c`, `Recv_SelfStoreGlobalChat`):

```c
char  Str[80];      // [ebp-0x338]
_BYTE v17[708];     // [ebp-0x2E8]   — sendBody, ВПЛОТНУЮ за Str
...
memcpy(Str, (a4 + 36), (__int16)(a3 - 10) - 27);   // ← БЕЗ проверки длины
...
if (a3 < 700 && a3 > 0) {                            // поздно (после memcpy)
    if (strlen(Str) < 80 && strlen(Str) > 0) {       // поздно (после memcpy)
        memcpy(v17, Src, 0x1B);
        memcpy(&v17[27], Str, strlen);
        ... sub_4C28F0(..., 5087, strlen+27, ...) ... // рассылка всем
```

`a3` (длина пакета) — **знаковый** `__int16`. Два независимых вектора:

1. **Длинное тело.** Длина копии = `(a3 − 10) − 27` до ~660 байт. `Str[80]` вплотную к
   `sendBody[708]`, выше по кадру — /GS-кука (`[ebp-8]`) и сохранённый EIP. Один
   модифицированный пакет затирает кадр стека.
2. **Короткое тело.** `(a3 − 10) − 27` становится **отрицательным**; `memcpy` принимает
   его как `size_t` ≈ 4 ГБ.

Это **тот же класс дефекта**, что P14 закрыл для чата `5084/5086/4120`; в список P14
функция 6316 **не вошла** (проверено по `p14_chat_message_length.cpp` и
`chat-message-length-x2.md`). Живой клиент сюда кладёт ≤79 байт, но защиты от
собранного вручную пакета у сервера нет.

## 2. ЧТО ИМЕНЕНО — ОДНА площадка

В отличие от P14 **предел НЕ поднимается**: «крик лавки» остаётся на стоковых 80 байтах
(клиент режет ввод до 79). Поэтому переезд буфера и снятие гейта `< 80` **не нужны** —
достаточно зажать длину копии **ДО `memcpy`**.

Площадка вычисления длины `0x508B59` (7 байт `0F BF 45 0C 83 E8 0A` =
`movsx eax,[ebp+0xC]; sub eax,0x0A`) заменяется на `jmp` в стаб. Результат уходит в
`mov word [ebp-0x348], ax` @`0x508B60` и ЕДИНСТВЕННО там читается как длина `memcpy`
(`0x508BDE`: `movsx edx,[ebp-0x348]; sub edx,0x1B; push edx`). Стаб приводит `(a3 − 10)`
к **`[0x1B .. 0x1B+80]`** и возвращается в сток на `0x508B60`:

| вход (текст) | `a3−10` | после зажима | текст копии | итог |
|---|---|---|---|---|
| ≤ 0 (короткий/отриц.) | < 0x1B | 0x1B | **0** | сток отсеет по `> 0` |
| 1 … 79 (легальный) | 0x1C…0x6A | без изменений | 1…79 | **байт-в-байт как сток**, гейт `<80` пропускает |
| = 80 | 0x6B | 0x6B | 80 | копия ровно 80 = ёмкость `Str`; `strlen=80` → гейт `<80` ОТБРАСЫВАЕТ (как сток) |
| > 80 | > 0x6B | 0x6B | 80 | зажато; гейт `<80` отбрасывает |

★ Копия **никогда** не превышает 80 байт = ёмкость `Str[80]` ⇒ переполнения нет ни на
каком входе. `sendBody` обнулён `memset`-ом ДО копии, поэтому `strlen(Str)` на полном
80-байтовом буфере останавливается на первом нуле `sendBody[0]` (= 80) и гейт `<80`
штатно отбрасывает — стоковое поведение приёма/отказа сохранено.

Гейты `a3 < 700` (`0x508D5E`) и `strlen < 80` (`0x508D95`) **НЕ трогаются**.

### Стаб (`ClampStoreShout`)
```asm
movsx eax, word ptr [ebp+0Ch]   ; packetLen (a3)   — как в стоке
sub   eax, 0Ah                  ; a3 - 10          — как в стоке
mov   edx, g_hiBound            ; 0x1B+80 = 0x6B   (8B 15 — префикс стаба уникален)
cmp   eax, edx
jle   s_lo
  pushad / push edx / push eax / call AsdaStoreShoutClamped / popad   ; лог обрезки
  mov   eax, g_hiBound
s_lo:
cmp   eax, 1Bh                  ; короче заголовка «крика» (27 б) → текст 0
jge   s_done
mov   eax, 1Bh
s_done:
jmp   dword ptr [g_retStoreShout]   ; -> 0x508B60 (mov word[ebp-0x348], ax)
```
Запись: `Hook::WriteJmp(0x508B59, &ClampStoreShout, 7)` = `E9 rel32 + 90 90`; инструкция
возврата `0x508B60` не затрагивается.

## 3. ОХВАТ — проверен тот же класс у ВСЕХ обработчиков (no-scope-cutting, false-negatives)

Сплошной скан `.text` на идиому «длина = `packetLen − 10`» (`0F BF 45 0C 83 E8 0A`) дал
РОВНО:

| функция | опкод | статус |
|---|---|---|
| `0x5471A0` | 5084 | закрыт P14 (A) |
| `0x547670` | 5086 | закрыт P14 (B) |
| `0x403F50` | 4120 | закрыт P14 (C) |
| **`0x508B40`** | **6316** | **этот патч (P46)** |
| `0x54D710` | 3404…3408 | НЕ этот класс: `(packetLen−10)` делится на 13 для подсчёта ФИКСИРОВАННЫХ записей, тело в стек не копируется (P23/P24) |

Прочие обработчики текста игрока защищены **MD5-подписью ФИКСИРОВАННОЙ длины тела**
(`sub_523F00`) и копируют фиксированное число байт — не переполняются (сверено
дизассемблером):

| опкод | обработчик | подпись `sub_523F00` | копия |
|---|---|---|---|
| 6313 чат лавки | `0x507930` | `0x6A` (106) | фикс. `0x6A` |
| 6302 открыть лавку | `0x502E50` | `0x1F9` (505) | фикс. |
| 5200 соулмейт | `0x4924F0` | `0x99` (153) | фикс. `0x99` |
| 6718 канал армии | `0x466FF4` | `0x6C` (108) | фикс. (намеренно оставлен и P14) |
| 6080 «о себе» | `0x498960` | `0x80` | фикс. |

⇒ **6316 — единственный незакрытый представитель класса**; у него вызова `sub_523F00`
нет вовсе. P46 закрывает ровно его.

## 4. Ключи `patches.ini` (секция `P46_StoreShoutOverflow`)

| ключ | по умолч. | смысл |
|---|---|---|
| `Enabled` | `1` | патч ставится. `0` = поведение стока (**переполнение снова открыто**) |
| `RuntimeLog` | `1` | строка `[storechat6316] * OVERFLOW BLOCKED` только при фактической обрезке (попытка переполнения / рассинхрон лимита); антифлуд: первые 50, далее каждое 500-е |

Предела `MaxTextLen` у P46 НЕТ намеренно: лавка остаётся на стоковых 80. Поднятие предела
потребовало бы (как в P14) переезда буфера и снятия гейта `<80` — против решения владельца
«лимит 80 сохраняется».

## 5. СВЕРКА И ПРОВЕРКА (только статическая — GameServer локально не запускается)

* **Оригинальные байты** площадки `0x508B59` = `0F BF 45 0C 83 E8 0A` сверены в стоке
  (`GameServer.exe_before_mine_patch.exe`, MD5 `4e20f0ad…`), в живом main и в живом Indun
  (оба `e7b4ac38…`) — совпали. Патч сверяет их же в памяти (`VerifyAllSites`); при
  несовпадении — `MISMATCH`, остальные патчи всё равно ставятся.
* **`verify_p46.py`** (эмуляция Unicorn настоящего стаба из собранной DLL) на длинах
  `{-5, 0, 1, 79, 80, 81, 663, 700}`: длина копии всегда ≤ 80 (Str[80] не переполняется),
  легальные 1…79 без изменений, всё > 80 зажато в 80; возврат стаба = `0x508B60`;
  применение к копии образа даёт `E9 rel32 90 90`, `0x508B60` не тронут. «ВСЁ СОШЛОСЬ».
* **`verify_dll.py`** — все площадки GameServer/Indun, пересечений 0, расхождений 0,
  стаб P46 найден по уникальной сигнатуре `0F BF 45 0C 83 E8 0A 8B 15`. «ВСЁ СОШЛОСЬ».
