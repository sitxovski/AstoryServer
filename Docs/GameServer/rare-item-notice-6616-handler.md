## ЗАЧЕМ (симптом → диагноз)

Оригинальный **клиент** умеет анонсировать редкую добычу: единая точка
`CItemManager_NotifyItemInfo@0xD0C8F0` при **грейде ≥ 3** (и `itemType ≤ 9` либо
`itemType == 11 && itemSubType == 200`) показывает у себя HERO_NOTICE (loc 20250) и шлёт серверу
**C→S 6616** (`netSendSignedPacket6616@0xA0F140`), тело = `name[20] + itemCode`, то есть ровно
payload серверного анонса 6131. Вызывается из ЧЕТЫРЁХ мест: подбор (5013), открытие
гача-коробки/бустера, успешная заточка, выдача в магазине.

**GameServer не имеет обработчика 6616.** Диспетчер клиентских пакетов `sub_42A9D0@0x42A9D0`
в этом диапазоне идёт `… 0x19CC, 0x19D0, 0x1A2C …`; литерал `19D8h` в `.text` встречается только
как смещение структуры. Пакет молча выбрасывается → ретрансляции 6131 нет → анонс видит только
сам счастливчик. Отсюда известное «сервер УМЕЛ, но НИКОГДА не делал».

Патч добавляет недостающий приёмник.

## ЧТО изменено (было → стало)

Ровно **2 участка, 374 байта**, размер файла не меняется.

### 1) Точка перехвата @ VA `0x42AB5C` (10 байт), внутри `sub_42A9D0`

```
ориг: 81 BD 38 EF FF FF 75 17 00 00     cmp dword ptr [ebp-10C8h], 1775h
патч: E9 50 80 15 00 90 90 90 90 90     jmp 0x582BB1 ; nop x5
```
`[ebp-0x10C8]` — уже разобранный опкод пакета; `0x42AB5C` — самое начало бинарного дерева
сравнений. Следующая инструкция `0x42AB66: jg 0x42AD3F` не тронута — стаб восстанавливает
и сравнение, и флаги.

### 2) Code-cave @ VA `0x582AB0 … 0x582CEA` (572 байта, v2)

Свободный нулевой хвост `.text` (VirtualSize 0x181843 → 0x582843, RawSize до 0x583000).
До патча диапазон `0x582AA9..0x583000` был полностью нулевым (проверяется скриптом; при
несовпадении сборка отказывает).

| адрес | что |
|---|---|
| `0x582AB0` | **обработчик** `Recv_RareItemNotice` (`__thiscall(CUserManager*, __int16 userNum, int* pkt)`, `ret 8`) |
| `0x582C0D` | **стаб ветки диспетчера** |
| `0x582C5C` | строка `"Recv_RareItemNotice()"` (имя для Secret-лога) |
| `0x582C72` | `"RareItemNotice\tIN\tCode\t%d\tUserNum\t%d"` |
| `0x582C97` | `"RareItemNotice\tFAIL\tCode\t%d\tUserNum\t%d\tStage\t%d"` |
| `0x582CC7` | `"RareItemNotice\tOK\tCode\t%d\tUserNum\t%d"` |

**Стадии в строке FAIL** (`Log_Item/ItemLog_<дата>.txt`):
| Stage | что не прошло | где ещё будет след |
|---|---|---|
| 1 | индекс пользователя ≥ 0x226 (`sub_5328F0`) | — |
| 2 | анти-реплей `sub_524390` (счётчик не возрос) | `Log_Secret\Secret_*.txt`: `Secret Error … Recv_RareItemNotice()` |
| 3 | **MD5-подпись тела** `sub_523F00` | `Log_Exception_Asm\AsmLog_*.txt` (категория 2) |
| 4 | `sub_5324A0` вернул NULL | — |
| 5 | itemCode вне 20551..`dword_5F5EAC` (`sub_532A90`) | — |

**Стаб ветки** (`0x582C0D`):
```
cmp dword ptr [ebp-10C8h], 19D8h
jne  not_ours
mov  edx,[ebp+8] ; mov dword ptr [edx], 19D7h      ; маркер прогресса (как у штатных case)
lea  eax,[ebp-1048h]  ; push eax                   ; a3 = буфер пакета
mov  cx, word ptr [ebp-44h] ; push ecx             ; a2 = userNum
mov  edx,[ebp-10C4h] ; mov eax,[edx+4] ; mov ecx,[eax+34h]   ; CUserManager
call 0x582AB0
mov  edx,[ebp+8] ; mov dword ptr [edx], 19D8h
jmp  0x42F036                                      ; общий хвост switch
not_ours:
cmp dword ptr [ebp-10C8h], 1775h                   ; восстановить исходное сравнение
jmp 0x42AB66
```
Пролог вызова скопирован 1:1 с штатного `case 0x17F1 → Recv_ItemInfoDisplay` (@0x42DFA7).

**Обработчик** (`0x582AB0`) — структура повторяет `Recv_ItemInfoDisplay@0x55BF80`:

| # | шаг | вызов |
|---|---|---|
| 1 | индекс пользователя < 0x226 | `sub_5328F0` |
| 2 | `memcpy(&ts, pkt+9, 8)` | `0x56A040` |
| 3 | **анти-реплей (Secret)** — монотонный счётчик пакета | `sub_524390(this, ts, userNum, "Recv_RareItemNotice()")` |
| 4 | **проверка подписи MD5 тела 24 б @pkt+33 против pkt+17** | `sub_523F00(pkt, 24, userNum, 1)` |
| 5 | `CUser*` отправителя | `sub_5324A0` |
| 6 | `itemCode = *(int*)(pkt+33)` | — |
| 7 | код в допустимом диапазоне (20551..`dword_5F5EAC`) | `sub_532A90` |
| 8 | тело 44 б: `memset(buf,0,44)`, `buf[0]=itemCode`, `buf[4..23] = *(CUser+376)` — **имя берётся С СЕРВЕРА, поле имени из пакета игнорируется** | `0x56A5A0`, `0x56A040` |
| 9 | лог в `Log_Item/ItemLog_*.txt`: `RareItemNotice\tCode\t%d\tUserNum\t%d` | `sub_569DF0(1, …)` |

Любая неудачная проверка → тихий выход без рассылки.

### Почему зона рассылки — весь сервер, а не сектор

Рабочей реализации в оригинале нет (приёмник отсутствовал), поэтому «оригинальной зоны» не
существует — выбор обоснован так:
- **правило самого клиента** (NOTICES_ALL §0): HERO_NOTICE = «сверх-значимое событие про ДРУГОГО
  игрока/мир» — глобальный канал, в отличие от локальных отказов;
- оба серверных прецедента глобальных объявлений (`sendNoticeClient` 3113,
  `SendPacketToAllChannel` 6145) — server-wide;
- секторная зона (как в боссовой ветке `Search_AddMonsterMapItem`) даёт видимость только
  соседям в AoI, что противоречит требованию «видят ВСЕ игроки»;
- `SendPacket_AllPlayer_InMap` — тот же цикл `sub_523E50` + те же фильтры получателя, что и
  `sendNoticeClient`, т.е. проверенный штатный путь.

### Почему имя берётся с сервера

В боссовой ветке оригинала имя читается `dword_5F5F84[11*a8]`, где `a8` — **индекс массива
монстров**, а таблица ключуется **ID монстра** → в пакет уходит пустая строка (баг оригинала,
`Reports/server_notice_senders.md` §2.3). Здесь баг не повторяется: имя читается из
`CUser + 376` (подтверждено лог-строками `"…CharName %s…"`, GameServer.c:59183, 79902).

## ⚠ Чего патч НЕ делает (осознанные ограничения)

1. **Грейд предмета на сервере не проверяется.** Серверная `ItemTable_Info\Item_Table.txt`
   (42 колонки, 55 920 записей; полное соответствие «колонка → смещение 71-байтовой записи»
   снято с загрузчика GameServer.c:68109) **поля грейда не содержит** — проверены распределения
   всех колонок, кандидата с диапазоном 0..4 нет. Грейд живёт только в клиентской `item_list`
   (поле +0xEC). Поэтому фильтр «грейд ≥ 3» остаётся **на приёмной стороне** — ровно там же, где
   он был в оригинале (`Recv_ItemFound@0x9744B0`: `if (itemGrade >= 3)` — проверка получателя).
   Наш порт этот фильтр выполняет.
2. **Фактическое наличие предмета в инвентаре не проверяется.** `sub_4D61E0` требует
   `plate`+`pos` слота, которых в пакете 6616 нет; полный обход инвентаря на ассемблере —
   несоразмерный риск для живого сервера.
3. **Rate-limit не реализован.** Защита от повтора — только монотонный Secret-счётчик
   (`sub_524390`) и MD5-подпись тела (`sub_523F00`, в живом билде **включена**: байты
   `0x523F8B`/`0x52400D` переведены `jmp`→`je`). Модифицированный клиент, знающий соль,
   теоретически может слать анонсы чаще положенного — **каждый такой пакет попадает в
   `Log_Item` с кодом и UserNum**, злоупотребление отслеживается. Кандидат на v2: пер-юзерный
   кулдаун в свободном поле `CUser`.

## Рестарт / риски / связанное

- **Рестарт:** GameServer (практически — вся стойка через `stop_servers.bat` / `start.bat`).
- **Риск: СРЕДНИЙ.** Новый сетевой путь + правка диспетчера. Смягчено: перехват не ломает
  исходное сравнение и флаги; обработчик собран ассемблером и сверен дизассемблером; стек
  сбалансирован на всех пяти ранних выходах; при коротком/битом пакете буфер диспетчера
  занулён → `itemCode = 0` → `sub_532A90` отсекает.
- **Не тестировался на живом сервере** (рестарт запрещён на момент правки). Сценарий проверки —
  в `Reports/server_notice_senders.md` §9.
- **Связанное:** клиентская сторона порта — отправка 6616 из `UAsdaItemNoticeSubsystem`
  (см. CHANGELOG порта), приём 6131 → HERO_NOTICE уже был.
