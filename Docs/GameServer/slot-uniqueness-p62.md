# P62 — уникальность слотов/uid в многослотовых заявках (5018/6549/6506/6555/6096/6112) и «слот 0 ≠ слот 1» у 6067

- **Дата:** 2026-10-12 (античит, волна A7 «экономика / предметы / рыбалка-лут-квесты»; план `00_PLAN.md` §8 механизм L3, приоритет A5; `02_parts/economy2_handlers.md` «Топ-5» п.3; `02_parts/fishing_loot_quests.md` FAME-1).
- **Статус:** собран в копии `AstoryServer/_archive_waves/AsdaPatch_w60_p62` (DLL v37, md5 `fdeacf7df1d7f2951392afe24c8ba650`, 553 472 б); статика `tools/verify_p62.py` — 209 проверок, 0 ошибок (три образа); стенд `tools/stand_p62` — 44/44 в Mode 0 и 44/44 в Mode 1. На живой сервер НЕ выложен (интегрирует координатор). **По умолчанию `Mode=0` — только журнал.**
- **Процесс:** GameServer.exe (основной и Indun — e7b4ac38; для всех 16 площадок/соседей = сток 4e20f0ad, сверено побайтно).
- **Тип:** [ПОРТ/СЕРВЕР-ДОРАБОТКА]; протокол не меняется, отказ = стоковое тело отказа того же обработчика (тот же опкод ответа и код, что сток шлёт на соседней ветке ошибки).
- **Файл:** `src/patches/p62_slot_uniqueness.cpp`; секция ini `[P62_SlotUniqueness]`; журнал P53 `ac.other` виды 30…34.

## Что и зачем

Шесть обработчиков принимают **список** ссылок (контейнер, слот) и, проверив каждую по отдельности (`sub_4D61E0@0x4D61E0` — вещь по паре, с границами контейнера: 1 → 30 слотов, 2 → 60, 3 → 11, 4 → 12, 5 → `MaxWeight`), отправляют их в DBManager одним пакетом (`sub_5646C0`), **не проверяя, что ссылки разные**. Одна и та же вещь, указанная дважды, считается дважды: сумма материалов (6549/6506/6555), цена продажи (5018), два зачисления в один слот (6096), один питомец как два материала (6112). Седьмой (6067) принимает два слота званий и применяет бонусы `sub_54D210` по каждому, не проверяя «слот 0 ≠ слот 1» (FAME-1: бонус звания удваивается, пока надето).

Одна общая функция `CheckRefs()` по кадру обработчика (`ebp`): среди **активных** ссылок (контейнер 1…5; слот ≥ 0 — либо любой у 5018, где «неиспользуемая запись» = контейнер 0) ищет
- **вид 30** — повтор пары (контейнер, слот);
- **вид 34** — цель/источник заявки среди материалов (6549 источник, 6506 цель, 6096 слот коробки);
- **вид 31** (`CheckBounds=1`) — ссылку, по которой `sub_4D61E0` (той же thiscall-сверкой и с тем же `this`, что сток) вещи не находит: слот вне границ или пуст. ★ У 5018 это отдельный дефект стока: буфер `a5` между итерациями не обнуляется (GS:103440+), и пустой слот получает **код предыдущей записи** — в БД уходит запись «слот N, код K» для пустого N. У 6096 целевые слоты могут быть законно пустыми (сток проверяет их `sub_4D6910`), вид 31 там не применяется;
- 6112 — **вид 32** повтор uid среди материалов до первого −1; 6067 — **вид 33** `slot0 == slot1 ≥ 0`.

**Mode=0** (умолчание): строка `P62 SlotUniqueness: <опкод> <обработчик> <вид> <детали>, UserNum, UserIndex, имя -> JOURNAL ONLY (Mode=0)` в лог сервера (`LogChannel`, 1 = Log_Item) + журнал `ac.other` (v[0] контейнер/uid/звание, v[1] слот/индекс, v[2] 0 журнал / 1 отказ, text = обработчик и записи), отправка в БД идёт как в стоке. **Mode=1**: стаб возвращает esp к состоянию до push'ей (`add esp,18h`) и уходит в стоковое тело отказа (см. таблицу); у 5018 при этом снимается замок «в полёте» `pUser+0x157` (сток взводит его на `0x50E6B2` до нашей площадки — иначе продажа заперта до ответа БД); у 6067 слот 1 := −1 и сток идёт дальше. Ограничитель: одна строка на (сессия по userNum с привязкой к UserIndex, вид) за `JournalIntervalSec`; подавленные → `repeat_suppressed`.

## Честный порт

## Цепочка P62 → P63 на общих площадках (интеграция integ2, 2026-10-12)

**Конфликт.** P62 и P63 перехватывают ОДИН И ТОТ ЖЕ `call sub_5646C0` (E8 rel32, отправка в DBManager) в пяти обработчиках:
6096 @`0x55AE4F`, 6506 @`0x501A5C`, 6549 @`0x535202`, 6555 @`0x5376F3`, 6112 @`0x4590C7`. До integ2 P62 ставился первым
(по реестру), P63 видел изменённый rel32 → `MISMATCH P63 @0x0055AE4F: ожидалось [e8 6c 98 00 00]` → все 25 семей P63 не ставились.

**Решение — общая точка в `Patches.h`** (как цепочка L06→L03 в LoginPatch):
* у стаба P62 на каждой из шести площадок отправки (5018 + пять общих) — свой слот «следующий вызов» (`g_next*`, по умолчанию
  `sub_5646C0`); на проходе стаб уходит в него **хвостовым `jmp`** (раньше — вложенный `call` с копией 5 аргументов): стек,
  `ecx` = CUserMoveManager, `ebp` = кадр обработчика и **адрес возврата в обработчик** — побайтно как у стоковой `call`;
* P63 при установке видит rel32 → стаб P62 **этой** площадки (`P62_SendStubAt(va)`), байты не пишет, исходные сверяет по
  таблице P62 (`P62_SendOrigAt(va)` = его `sendBytes`), кладёт `St_Send` в слот (`P62_ChainSend(va, St_Send)`);
* P62, если ставится ПОСЛЕ P63 (rel32 → `St_Send` P63, `P63_SendStubAt(va)`, исходные байты таблиц совпали), забирает
  площадку себе и кладёт `St_Send` в слот — порядок в рантайме тот же;
* выключен один из двух (или площадка ключом `Sell5018…PetUnion6112` / `Lock<op>`) — второй ставит площадку сам по стоковым байтам.

**Порядок в рантайме: P62 (уникальность) → P63 (замок) → `sub_5646C0`.** Отказ P62 (Mode=1) уходит в стоковое тело
отказа обработчика — до P63 управление не доходит, замок «в полёте» НЕ ставится (иначе семья была бы заперта до тайм-аута
без ответа БД — правило «не защёлкивать состояние заранее»). `St_Send` площадку по адресу возврата не определяет: семья — по
опкоду БД `[esp+4]`, слот — `[esp+20]`, `this` — из кадра `ebp`; вход через P62 и напрямую одинаков.

Экспорт для стендов: `P62_GetSendNext(va)` — цель слота «следующий вызов» (0 — площадка не у P62). Лог установки:
P62 — «цепочек с P63 при установке N» (N>0 только если P63 встал раньше), P63 — «из них через P62 5» и по строке
«<обработчик> (<op>) — цепочка через P62 @0x…: P62 → P63 → sub_5646C0» на каждую общую площадку.

**Проверено:** `stand_map` на трёх образах — P63 Applied (48 своих диапазонов + 5 через P62 = 53 площадки), записей двумя
патчами 0, пересечений байт 0, `CHAIN` ×5 = `St_Send`, 5018 → `sub_5646C0`; прогон «без каждой записи по очереди» — общих VA
только P62/P63 (5, цепочка) и P53/P57 (2, известная цепочка). `verify_p63.py` §5 — unicorn с инструкции `call` обработчика:
через P62 (чисто+пропуск / чисто+подавление / отказ) и напрямую, стек/регистры/адрес возврата, `P63_OnSend` видит один и тот
же вход — 5/5. `stand_p63 <Mode> both|rev|p62|p63` — оба порядка установки, только P62, только P63, Mode 0 и 1: нарушение
уникальности в Mode=1 → тело отказа, замок не поставлен, следующая честная заявка без «дубля»; Mode=0 → журнал P62, замок
поставлен и снят ответом. Логи `Reports/anticheat/wINTEG2_logs/`.

## Откат

`Enabled=0` (или флаг обработчика =0) + рестарт GameServer/Indun. Прежняя DLL (v36) сама опустит `Version` и проигнорирует секцию. Exe не меняется.

## Не сделано / замечания

- Вид 31 у 6096 не применяется (цели законно пустые); у 6112 границ нет (uid ищется в списке питомцев самим стоком).
- Ущерб от повторов на стороне DBManager (процедуры 2023/2527/2306/2531/2272/2282) не проверялся — как и в разборе `economy2_handlers.md`; патч закрывает вход, а не процедуры.
- Что шлёт **оригинальный** клиент в неиспользуемых записях 6549/6555 — не разобрано (отправителей в клиентском эталоне не найдено по опкоду); принято «слот < 0 = не используется», как у 6506 (контейнер 1 / слот −1). При `Mode=1` это влияет только на оригинальный клиент (запрещён владельцем), порт эти опкоды не шлёт.
