# P98 — стопочный предмет из премиум-почты приходит одной штукой (30.10.2026, волна bugs7)

[ИСПРАВЛЕНИЕ] дефекта оригинала. Протокол клиента не меняется (11006/11007 и DB 2604 — те же длины и раскладки).
Баги игроков 30.10: знак охоты 75521 — нумпад «Все» = 0, сдача 6150 отказывает кодом 6; свитки 20936/20946/20952/23229 у 8 игроков
с количеством 0 (покупки премиум-магазина, `BuyType 3`).

## Дефект

`Recv_PremiumItemToInven_Req@0x4F8340` (11006, GameServer.c:95835) переносит покупку из премиум-списка в инвентарь.

1. Шаблон записи предмета (57 б, `a5` = `[ebp-5Fh]`, он же тело DB 2604 +13) строит `sub_5340B0(this, userNum, код, a4 = 0, a5, 0, 0)`
   (GameServer.c:117645; дизасм 0x5343C2…0x53449A). Для стопочного предмета item_list — контейнер 2 (`+36 != 3` и тип `+26` вне
   {0,1,2,3,4,8,9,12,13,14,15}) и `+35` «стопка» != 0 — функция ищет стопку того же кода в контейнере 2 (`sub_4D6CE0`):
   - найдена → шаблон `+9` (Amount) = её количество N, `+14` (вес) = её вес, `+5` = её слот;
   - нет → `+9` = 0 (0x53443B), `+14` = 0, `+5` = свободный слот;
   - затем `+9 += a4`, `+14 += a4 · вес штуки` (`+5` строки Item_Table).

   Функция рассчитана на ДОБАВЛЕНИЕ `a4` штук к стопке (так её зовут рыбалка и ремесло с `a4 = 1`). Премиум-почта зовёт её с `a4 = 0`.
2. Обработчик выбирает `Count` (≤ 7) свободных ячеек `sub_4D6740` в контейнере шаблона и шлёт DB 2604 (87 б, тело `[ebp-6Ch]`).
   DBManager `sub_43F3E0` → `UPCashitemToinvenFunctional` (`@Amount` = тело +22 = шаблон +9, `@Weight` = тело +27 = шаблон +14)
   делает INSERT на каждую ячейку и эхом возвращает тело; `sub_4F89D0@0x4F89D0` копирует тот же шаблон (`rep movsd` 0Eh из тела +13)
   в каждую ячейку памяти персонажа и прибавляет вес — сумму `+14` записей.

Итог:
- **новая стопка — Amount 0**, вес 0: предмет нерабочий («Все» = 0; `RecvClient_TitleItemCheck@0x55F090` — стопка < сдаваемого → код 6);
- **дюп** — при наличии стопки N каждая новая ячейка получает Amount N и вес стопки.

`joylog1.dbo.CashBuyFunctional` (поле `Ramount` = Amount доставки) с 01.07: 48 стопочных доставок, из них 46 с `Ramount 0`
и 2 с `Ramount 1` (стопка из 1 уже была — дюп «случайно правильный»); доставок с N > 1 не было. На 30.10 в `Joy1.dbo.Item` живы 9
таких строк (Amount 0), 36 — уже удалены игроками, 1 — с Amount 1.

### Другие вызовы `sub_5340B0` с `a4 = 0` (проверено)

| вызов | почему дефекта нет |
|---|---|
| `Recv_UserPrimiumGaChaReward@0x4F72B0` (6581) | только `+36 == 3` (экипировка, контейнер 1) |
| `Recv_UserPrimiumSum@0x536EE0` (2533) | награды `PrimiumSumTable.txt` (26 кодов) все нестопочные |
| наш P16 `GachaPrizeToInven` (DB 2601) | тот же шаблон → P98 приводит его через `P98_FixPremiumRecord` (P16 сейчас `Enabled=0`) |

### Замечено, не входит в P98

Нестопочный расходник контейнера 2 (`+35 == 0`, например 20634) из премиум-почты приходит с весом 0 (та же формула
`+14 = a4 · вес`). Amount 0 у нестопочных — штатный. Вес по заданию не трогаем; решение — за владельцем.

## Исправление — AsdaPatch P98 `[P98_PremiumStackAmount]` (GameServer, Indun_GameServer, Ch2_GameServer)

Одна площадка — трамплин (`jmp` в стаб, pushfd/pushad, C-функция, замещённая инструкция на продолжении).

| площадка | адрес, байты стока | когда | решение |
|---|---|---|---|
| S1 11006 | 0x4F8636 `8B 8D E0 FD FF FF` (`mov ecx,[ebp-220h]`) → 0x4F863C | цель единственного `je` 0x4F85A3 после `cmp [ebp-228h],1` за `call sub_5340B0`: шаблон готов, ячейки не выбраны, ничего не отправлено | `P98_OnPremium` |

Почему здесь, а не перед отправкой 2604: шаблон один на все ячейки, а между его постройкой и отправкой он только копируется
(тело 2604 — тот же буфер). Точка сразу после успеха `sub_5340B0` — единственная на успешном пути, достигается только с
готовым шаблоном и раньше любой его копии. Тело `sub_5340B0` не меняем: остальные её вызовы (`a4 = 1`) складывают штуки в стопку
правильно.

Правило (`FixRecord`): код — item_list (`sub_532A90`) и равен коду шаблона; шаблон `+4 == 2`; строка Item_Table `+35 != 0`; тип
`+26 != 10` (колчаны/наживка — своя логика количества). Тогда шаблон `+9 := 1`, `+14 := вес штуки` (`+5`, u16). Каждая ячейка
доставки — отдельная стопка из 1 шт. (Count ячеек = Count штук, как задумано стоком). Если шаблон уже 1 шт. с весом штуки
(существующая стопка из 1) — без изменений. Нестопочные, контейнер 1, самоцветы, особые предметы — как сток.

Кадр 11006: `this` = `[ebp-238h]`, `pUser` = `[ebp-218h]`, `v36` = `[ebp-224h]` (+0 Order, +4 код, +8 Count u8, +9 BuyType u8),
шаблон = `[ebp-5Fh]`, `userNum` = `[ebp+8]`.

P98 до записи сверяет площадку и 17 соседей (продолжение, `cmp/je`, `call sub_5340B0` и его аргументы, кадр, Count, контейнер
шаблона, тело и `push 57h; push 0A2Ch`, пролог и ветка «стопка» `sub_5340B0`, пролог `sub_532A90`); не сошлось — площадка не ставится.

## Ремонт БД — `tools/deploy_p98.py` (при остановленной стойке)

`Joy1.dbo.Item`: строки кодов правила P98 (список строится из ЖИВОЙ `item_table.txt`, одинаковой во всех GameServer; 1 163 кода)
с `Amount <= 0` → `Amount = 1`, `Weight = вес штуки` (u16 побитно в smallint, как `dbo.fn_W16`). Перед UPDATE — снимок строк в
журнал `dbo.AsdaP98AmountFix` (`RunUtc`, ключи строки, `AmountBefore/WeightBefore/AmountAfter/WeightAfter`, `GainDate`), одна
транзакция; `snap ≠ upd` или больше 50 строк — откат и СТОП. На 30.10: 9 строк (20946 ×3, 20952 ×2, 20936 ×2, 23229 ×1, 75521 ×1;
учётки 1, 75207, 75211 ×2, 75215, 75221, 75223, 75224, 75230). `Charinfo.Weight` не трогаем — `UPCharInfo` пересчитывает текущий вес
как `SUM(Item.Weight)` при входе.

Сухой прогон (без ключа) — SQL-стенд: копия всех строк стопочных кодов во временную `#stand` (tempdb), тот же снимок + UPDATE в
транзакции, сверка (`left=0`, строки вне журнала совпадают с Joy1, строки журнала — 1 / вес штуки), ROLLBACK; тексты ремонта и
отката — компиляция `SET NOEXEC ON`. Joy1 при этом только читается. SQL уходит в `sqlcmd` через stdin (файлы на сервер не пишутся),
копии текстов — в `tools/run_p98_20261030_deploy/`.

## Проверки

- `tools/verify_p98.py` — образы (сток + 3 живых), площадка и соседи, границы инструкций, сплошной перебор переходов, окна ±32 б;
  вторым методом — дизасм 11006, `sub_5340B0`, `sub_4F89D0` и DBManager `sub_43F3E0` (смещения @Amount/@Weight); DLL (стаб,
  экспорты, P16, реестр, ini, тексты 150–152, чужие площадки); таблицы стойки.
- `tools/stand_p98` — настоящие 11006 и ответ БД `sub_4F89D0` на настоящей item_table, сценарии A (75521 новая) / B (20936 ×3) /
  C (стопка N=5 → дюп) / D (стопка из 1) / E (нестопочный) / F (колчан) / G (экипировка) / H (путь P16); режимы
  on / journal / full (вместе с P96 и P97, как на стойке) / off / mismatch.

## Выкладка и откат

- Выкладка (координатор, с объявлением): `py -3.13 restart_stack.py --deploy deploy_p98.py --expect P98_PremiumStackAmount`;
  после старта `py -3.13 deploy_p98.py --check-started`.
- Откат DLL: `deploy_p98.py --rollback` (стойка остановлена) или `[P98_PremiumStackAmount] Enabled=0` + рестарт GameServer.
- Откат ремонта БД: `deploy_p98.py --rollback-sql` — строки последнего прогона, не менявшиеся с него, к прежним Amount/Weight.
