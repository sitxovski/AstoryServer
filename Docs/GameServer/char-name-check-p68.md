## Правила клиента-оригинала (эталон AsdaStory.exe 13 344 768 б)

- `validateStringByLocale@0x956090` по локали сборки `CObj_GetField14(&g_hMainWnd)`: case 2/6 `isValidNameCharAscii@0x9570A0` = A-Z a-z 0-9 (русский эталон порта); case 7 `isValidNameCharCyrillic@0x957250` = + байты ≥ 0xC0, 0xA8, 0xB8; case 8 `isDelimiterChar@0x957610` (мисней — арабская) = + байты ≥ 0xC0 кроме 0xD7.
- `Chat_MatchBannedWord(…, 1)@0xBB2830`: режим 1 = `validateStringByLocale`, затем A-Z → a-z и поиск подстрок слов `system\CurseTable.BIN` (int32 длина + байты−1, строки `\n`; 192 слова: 58 ASCII, 134 EUC-KR; файл одинаков у русского и арабского клиента, md5 `9e672cdd…`). Слова НЕ понижаются — «Dick», «Slut», «OKAYGOODS» не срабатывают никогда. ★ Дизасм 0xBB2A95: при несовпадении на позиции с байтом ≥ 0x80 функция сразу возвращает «запрещено» — у оригинала смена имени на не-ASCII имя (кроме последнего байта) невозможна; 0x7F — «запрещено».
- Создание (CaraMake, AsdaStory_game.c:534790): поле LimitText 18 (0x534255), `validateStringByLocale` + запрет `'` → 9583. CurseTable при создании не проверяется.
- Сервер создания (LoginManager `Send_CreateChar`): `CCurse` — заглушка `sub_401110` (всегда 0), `sub_406790` — запрет 28 знаков (`' @ $ & - _ % ^ * \` [ ] , < > / . \ " ~ | + = { } : ; ?`); пробел, `! # ( )`, управляющие и байты ≥ 0x80 проходят. `UPUseNick`: LewdWordList + занятость.
- **Проверки GM-префикса нет нигде** (строк нет в клиенте, LoginManager, GameServer — кроме имени обработчика `GM Recv_CharBlock`, DBManager) — P68 её не добавляет.

## Что проверяет P68

`P68_NameVerdict(поле 20 б, charset)` (та же функция у всех площадок, экспорт для стенда): **1** пусто; **2** нет нуля в 20 б (длина > 19 — тогда `'%s'` DBManager читает за поле, а `CUser+0x178` остаётся без терминатора); **3** байт 0x01..0x1F / 0x7F; **4** символ вне правил:
- `NameCharset=0` (умолчание): A-Z a-z 0-9 — эталон и решение владельца 08.10 (порт `asda.Text.NameLocale 0`);
- `NameCharset=1`: (А) байты A-Z a-z 0-9 / ≥ 0xC0 / 0xA8 / 0xB8 (локали 7 и 8 оригинала); (Б) маркер порта 0x98 + байты по (А) (арабица, кодек провода порта); (В) строгий UTF-8 из A-Z a-z 0-9, кириллицы U+0410..U+044F/U+0401/U+0451 и букв cp1256 ≥ 0xC0 кроме 0xD7 (ветка UTF-8 порта, «РЁ…»). Ставить вместе с `asda.Text.NameLocale 1` в порту и `Charset=1` в SQL A13.

Причуду 0xBB2A95 (не-ASCII при смене имени) P68 НЕ навязывает: правило символов — объединение локалей, чтобы честное имя порта (NameLocale 1) не попало под отказ. Слова CurseTable/LewdWordList и занятость — в SQL A13, где лежат данные.

Вид **54** (`Require6138Before6140=1`): 6140 с именем, не совпадающим (до нуля) с последним 6138 этой сессии, или без 6138 вовсе. Честный клиент шлёт в 6140 тот же буфер, что проверял 6138; иначе — обход UPNickCheck (занятость, LewdWordList). Состояние — по слоту `userNum` с привязкой к charId (смена учётки в слоте сбрасывает).

**KeepNameOnDbFail=1** (дефект стока, от Mode не зависит): в 2453 копия нового имени в `CUser+0x178` только при флаге БД 1 — как сток снимает предмет (0x55DECB). Без правки честный член клана (флаг 2/3), предмет на аукционе (4), ошибка/отказ A13 (0) — имя в БД прежнее, предмет на месте, а в памяти сервера до перезахода новое имя. Строка Log_Item `P68 CharNameGuard: 2453 flag N - rename not stored, in-memory name kept`.

## Решение владельца 13.10: операторы освобождены (SQL a13b применён; P68 — сделано integ3)


**Реализовано (integ3, 13.10.2026).** `[P68_CharNameGuard] OperatorExempt=1` (умолчание 1): на 6138 и 6140 первым делом `P47_IsGmUser(this обработчика, userNum)` — общая точка P47 (`Patches.h`), тот же вызов `sub_52ED50 == 1`, что у гейта операторских опкодов; поле `CUser+0x40B9F` в P68 не читается. Оператор → сток как есть: ни правила (вид 53), ни сверки с последним 6138 (вид 54), ни отказа, имя 6138 не запоминается; счётчик `P68_GetOperatorExempt`. `this` 6138 = `[ebp-4Ch]`, 6140 = `[ebp-0ECh]` (сосед `0x55D9AD mov ecx,[ebp-0ECh]` уже сверяется при установке). `KeepNameOnDbFail` (2453) от исключения не зависит.

**Источник признака (для SQL — тот же):** `CUser+0x40B9F` пишет только `sub_560160` GameServer по DB-ответу **2801** {UserIndex, флаг}, если UserIndex = `CUser+0x174`; 2801 шлёт DBManager при загрузке персонажа (`DBM_CHARINFO_RES`, после `UPCharFameProgress`) по `EXEC UPCharGMInfo <UserIndex>`: `SELECT @GMFlag = GMFlag FROM Joy1.dbo.CharGmInfo WHERE Userindex = @Userindex` → 1, если строка учётки есть и `GMFlag` не NULL (само значение не важно), иначе 0. Признак учётки, не персонажа; до DB-логона 0 (`ClearUserMemory`).

**6138 после a13b.** `UPNickCheck` учётку не знает — его проверка выключена для всех (`CheckNickCheck=0`), поэтому **правило имени на 6138 проверяет только P68** (в журнале на 6138 — только вид 53 от GS, вида 55 нет); на 6140 и при создании — P68 (6140) и SQL A13 (UPCharRename/UPCreateChar, операторы освобождены там же). Двойная запись «53 от GS + 55 от SQL» остаётся только для 6140.
