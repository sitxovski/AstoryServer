## 1. ЗАЧЕМ (симптом → диагноз)

**Симптом.** Приз премиум-гачи не выдаётся: в ответе **6578** контейнер `0`, слот `−1`;
любой последующий **6581** получает **6582 со статусом 10**.

**Диагноз (по байтам).** Пакет 6578 отправляет `sub_4F7D10@0x4F7D10`
(`RecvDB_InsertPremiumItem`, ответ БД на 2601), а не `PrimiumGaCha@0x4F70B0`, как считалось
раньше. В ветке «гача» (`0x4F7DF3 movzx ecx,[ebp-0x27]; cmp ecx,3`) он заполняет тело 6578
только статусом, кодом предмета и балансом; остальные 57 байт записи остаются такими, какими
их сделал конструктор `sub_40A9F0@0x40A9F0`:

```
0040AA18  C6 42 04 00         mov byte [edx+4],0        ; контейнер = 0
0040AA1F  66 C7 40 05 FF FF   mov word [eax+5],0xFFFF   ; слот      = −1
```

Причина маршрута: наши **P05** (запрос к GP7, код 105) и **P06** (DB-пакет 2601) провели гачу
по пути ПРЕМИУМ-ШОПА, который по замыслу авторов кладёт покупку в «премиум-список» БД, а не в
инвентарь. Стоковый путь гачи (DB 2553 → 2554 → `PrimiumGaCha`) авторами не дописан:
**ссылок-отправителей 2553 (`0x9F9`) в образе нет** — сплошной скан не нашёл ни одного
вхождения ни в `GameServer.exe`, ни в `DBManager.exe` (контрольные `0x9FA`/`0x9FB`/`0xA29`
находятся). Возрождать 2553 нельзя: он тянет хранимую процедуру `UPGotChaCashItemBuy`
(32 параметра) и повторное списание кэша, который уже списал GP7.

## 2. ЧТО ДЕЛАЕТ ПАТЧ

Достраивает маршрут **формулой рабочей ветки этого же сервера**
`Recv_PremiumItemToInven_Req@0x4F8340` (проверена живым логом
`Log_MGamePremium/MoveToInven_20260806.txt`: `ItemIndex 68432 BuyType 3 → Pos 25, Result 1`):

1. `sub_5340B0@0x5340B0` — строит 57-байтовую запись предмета и назначает **контейнер**;
2. классификация кода (`sub_532A90` / `sub_532AE0` / `sub_532B10`) → `iType` и байт «состояние»;
3. **`sub_4D6740@0x4D6740`** — подбор свободного слота (по одному на каждую единицу `count`,
   старт с −1); `−1` = инвентарь полон → ничего не отправляем, приз остаётся в списке;
4. `sub_5646C0(0x7E0538, 2604, 87, seq, &запрос, userNum)` — запрос в БД;
   ответ приходит **ТЕМ ЖЕ опкодом 2604** и обрабатывается **стоковым** `sub_4F89D0@0x4F89D0`
   (★ ИСПРАВЛЕНО 2026-08-18: раньше здесь было «ответ 2605» — опкода 2605 не существует,
   DBManager отвечает `push 0x57; push 0xa2c` @ `0x43F81A`; разбор — `Reports/elite_mailbox_re.md` §3.0);
   он же кладёт запись через
   `sub_4D63F0` и шлёт клиенту 11007);
5. дополнительно вписывает готовую запись (с контейнером и слотом) в тело ещё не отправленного
   6578 — чтобы клиент увидел ячейку приза и чтобы 6581 (`sub_4D61E0`) находил предмет.

**Отличие от оригинала (осознанное).** Стоковый цикл слотов
(`for (i = 0; i < count; ++i)`, `count` — байт из пакета, массив на 7 элементов,
`0x4F8846 mov [ebp+eax*2-0x25],cx`) пишет за границу кадра при `count > 7`.
Патч зажимает `count` в 1..7 и пишет предупреждение в лог.

**Безопасность площадки.** Полный перебор кодировок rel8/rel32/jcc32 по всей `.text` плюс скан
всех DWORD образа: переходов и ссылок ВНУТРЬ `0x4F7E41…0x4F7E46` — **ноль**.

## 3. ДИАГНОСТИКА В ЖИВОМ ЛОГЕ

Пишется в `GameServer\Log\Log_MGamePremium\MoveToInven_<дата>.txt` (категория 38):

```
GaChaPrizeToInven success   Order N  ItemIndex N  Count N  iType N  Container N  Pos a, b, ...
GaChaPrizeToInven failed    ... BuildItemRec N | no free slot in container N | ItemIndex N invalid
GaChaPrizeToInven clamp     ... Count N -> 7
```

## 4. КАК ОТКАТИТЬ

1. Мягко: `ConfigSet\patches.ini` → `[P16_GachaPrizeToInven] Enabled=0`, рестарт стойки.
   Поведение вернётся к текущему: приз ложится в премиум-список, игрок тянет его вручную.
2. Полностью: вернуть предыдущую `AsdaPatch.dll` (MD5 `5262bfabb0ff3635181544ef397eb792`,
   170 496 б) — на живом лежит как `AsdaPatch.dll.new_nop09_20260817` / `…bak_pre_d1fix_20260817`
   (сверить MD5 перед подменой), рестарт стойки.

## 5. РИСКИ И ЧТО НЕ ПРОВЕРЕНО

* В бою не проверялось — сервер локально не запускается (жёсткий запрет). Проверка сделана
  дизассемблированием живых образов, сверкой с живыми логами и разбором сгенерированного
  компилятором кода трамплина.
* Хранимая процедура пути 2604 (запрос и ответ одним опкодом) на живой БД **работает** (лог `MoveToInven_20260806.txt`,
  `Result 1`, в т.ч. на призе гачи `BuyType 3`). При отказе БД сценарий деградирует безопасно:
  приз просто остаётся в премиум-списке, как сейчас.
* Слот, который патч вписывает в 6578, вычисляется тем же `sub_4D6740` и тем же контейнером,
  что позже применит `sub_4F89D0`; расхождение возможно только если инвентарь персонажа
  изменится между нашим вызовом и приходом ответа БД (обработка пакетов одного пользователя
  последовательна, поэтому практически исключено). Расхождение не теряет предмет — теряется
  лишь возможность обменять приз на вариант через 6581 до перезахода.
* Связанное: P05 (@0x4F7084) и P06 (@0x4F6CA5) остаются как есть — P16 их не заменяет, а
  завершает открытый ими маршрут. Порядок установки в `Registry.cpp`: P16 идёт последним.
