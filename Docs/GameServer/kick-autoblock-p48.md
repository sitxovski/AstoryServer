## 1. Как работает
- Площадка — вход `Send_DisConnectType sub_52EDB0@0x52EDB0` (6 б `55 8BEC 83EC08`; единственная функция, отправляющая 4101 с причиной).
- Считаются типы `CountTypes`: 3 — `CheckDisConnectUser` (Secret/MD5/NotKnow/Hack Packet, в т.ч. отказы GM-гейта P47 и кик P49),
  6 — `sendSpeedHackDisConnect` (NpcServer). Не считаются: 1 пинг, 2 повторный вход, 5 ошибки логона (там UserIndex заявлен клиентом).
- **Только сессия, вошедшая в мир** (`CUser+0x2E == 1`, ставят `CharMake`/`CharPortalMake` после DB-логона, сверенного P50):
  до входа UserIndex не подтверждён — кик нельзя приписать учётке.
- Счёт — файл ini (общий для GameServer и Indun: у обоих путь разрешается в `v2\GameServer\ConfigSet\`) под межпроцессным
  мьютексом `Local\AsdaPatch_P48_KickCounter`. Окно `WindowHours` от первого кика.
- На пороге — штатный DB-запрос **2271** (как GM-блок 6094 `sub_55A510` / `Recv_CharBlock`): `{u16 userNum, i32 UserIndex, u8 слот,
  u8 группа, i32 часы}` → DBManager `sub_432950` → `EXEC UPHackBlock UserIndex, часы` (`us_block=5` + строка `BlockList`).
  Счёт обнуляется только после отправленного запроса (сбой отправки — повтор на следующем кике).
- Журналы: `Log_Operator` (`P48 KickCount…`, `P48 AutoBlock…`), `Log\Log_Patch\PatchLog_*.txt` (`[P48] …`).
  или `EXEC AsdaStoryOP.dbo.OPBlockDel 'sitxovski'` / `'Rimy'`.

## 2. Откат
`[P48_KickAutoBlock] Enabled=0` + рестарт, либо прежняя DLL (`AsdaPatch.dll.bak_20261012_ac0`). Файл счётчика можно удалить при
остановленной стойке.

## 3. ★ ac0r (2026-10-12) — вход соулмейтом: кик и блок на учётку сессии (СРЕД-1 ревизии А0/А2)
**Было.** При входе в чужое расшаренное тело (LoginManager 1016 режим 2) сессия GameServer несёт UserIndex хозяина
персонажа (B, CUser+0x174), а играет вошедшая учётка (A). P48 засчитывал кики и слал `UPHackBlock` учётке B.
**Где сервер держит A (декомпил + asm, сверено по живому `e7b4ac38…`):**
- `CUser+0x182D3` — байт SoulState: 0 свой, 1 «душа», 2 вход соулмейтом (`sub_52EE40@0x52EE40`:
  `cmp [ecx+182B9h],0` / `movzx eax, byte [edx+182D3h]; cmp eax,2`);
- `CUser+0x182C6` — DWORD iMateUserIndex блока соулмейта (база `+0x182B9`, смещение 13): `charLogonCommunityRes`
  копирует 0x5C б DB-ответа 2145 в `CUser+99001` и логирует «sSoulMateInfo.iMateUserIndex < 0» по тому же байту тела;
  источник — `UPCharSoulMate @Userindex = B` → `SoulMate.Ouserindex` (= A) — та же строка, по которой `UPCharSoulState`
  закрыл запись входа A и открыл запись B State 2. Блок свежий на каждую сессию (`ClearUserMemory sub_4A2DC0` копирует
  инициализированный блок 0x188 б в `CUser+99001`).
**Стало (решение координатора).** При SoulState == 2 счёт и тело 2271 — на `CUser+0x182C6` (учётка сессии входа A);
учётка-хозяин B не трогается. Если `CUser+0x182C6 ≤ 0` — кик не засчитывается никому (строка в `Log_Operator`/PatchLog).
DBManager для 2271 берёт из тела только UserIndex и группу (`sub_432950` → `EXEC UPHackBlock UserIndex, часы`).
SoulState 1 («душа») — свой персонаж, счёт как прежде на CUser+0x174. Снятие истёкшего блока — тоже по учётке сессии:
Ключ `SoulMateSessionAccount=0` — прежнее поведение. Проверка: стенд `stand_ac0 gs` — соулмейт-сессия 5 киков → 2271 с
UserIndex сессии; своя сессия хозяина после этого — 4 кика без блока (счёт хозяина не тронут); без MateUserIndex —
6 киков не засчитаны; «душа» — своя учётка.

## 4. ★ autoban (2026-10-14) — общие точки с P69
- Логика «чья учётка у сессии» вынесена в общую точку `P48_IdentityOf` (в мире `CUser+0x2E == 1`; соулмейт — `iMateUserIndex
  CUser+0x182C6`), путь блока — `P48_SendHackBlock` (тот же 2271). Их зовёт P69 «ступенчатый автоблок за нарушения целостности
  пакетов» ([integrity-autoblock-p69.md](integrity-autoblock-p69.md)). Поведение счёта киков P48 не менялось.
- Кик, назначенный самим P69 после его автоблока (`KickOnBlock`: штатный счётчик Hack Packet → тип 3), P48 **не засчитывает**:
  метка на учётку сессии (`P69_TakeKickMark`), строка `ac.kick_block` с `not_counted_reason` «кик после автоблока P69 (нарушения
  пакетов) — не засчитан» (код 5). Иначе одно нарушение-ступень давало бы и блок P69, и шаг к блоку P48.
- Ключи `[P48_KickAutoBlock]` не менялись. AsdaPatch Version 39 `6f77e7f2…` — не выложено.

## ★ sec2 (15.10.2026) — кик за поддельный/битый пакет не засчитывается (решение владельца 14.10)
За поддельный/битый пакет наказывают только ступени P69. Пути, где нарушение P55/P61 даёт кик, который считает P48 (только
Send_DisConnectType тип 3 из CheckDisConnectUser@0x526C20 — 4 счётчика CUser, сверено дизасмом на стоке/живом/Indun):
| счётчик | растит | кик (адрес возврата) | путь нарушения P55 |
|---|---|---|---|
| Secret +0x04, > 20 | sub_524390 (немонотонный токен) | 0x526D10 (стаб P49 обнуляет счётчик до вызова) | Mode=0: короткий кадр до обработчика |
| MD5 +0x08, > 5 | sub_523F00 (MD5 тела не сошёлся) | 0x526D4F | Mode=0: у короткого кадра MD5 считается по чужим байтам |
| NotKnow +0x1E, > 5 | sub_5244B0 (default диспетчера) | 0x526D8E | Mode=0: кадр < 10 б с неизвестным опкодом |
| Hack +0x22, > 5 | sub_524540 | 0x526DCD | Mode=1 + HackPacketOnRefuse=1 (P55 сам +1); P69 KickOnBlock (код 5, как было) |

P61 (канал) кика через Send_DisConnectType не даёт: нарушение канала рвёт соединение `GetConnectFlag + DisConnect` (поток в
обработчики не уходит); вызовов sub_52EDB0 — 22, все в обработчиках логики (типы 1/2/3/5/6/14/15), ни одного на пути разрыва.
**Правка:** P55 на каждом пакете слота приписывает прирост этих 4 счётчиков предыдущему кадру (кадр P55 1/2/4 — «целостность»,
иначе — «прочее»; свой +1 к Hack и +1 отказа P47 — сразу; 20000 и любой кик — сброс). P48 на кике тип 3 спрашивает
`P55_KickAttribution`: прирост «целостности» > 0 и без него порог не превышен (прочее ≤ порога) → **не засчитан, код 6**
(`ac.kick_block.not_counted_reason` «кик за нарушения целостности пакетов P55 — наказывает только P69, не засчитан», строка
PatchLog `[P48] … НЕ засчитан: счётчик вырос из-за нарушений целостности пакетов P55 (N из них, прочих M ≤ порога)`). Прочие
кики (типы 6, 3 с превышением порога «прочим», P55 выключен) P48 считает как раньше. Стенд `tools/stand_p48s` (3 образа).

## ★ sec2c (15.10.2026) — атрибуция кика без гонок нитей карт (ревизия SEC2 Н-3/Н-4/Н-5)
`CheckDisConnectUser@0x526C20` зовёт `RunProcess` объекта нити карт (`sub_4C0EA0` из `sub_4BEDF0`), нитей несколько, а учёт
атрибуции sec2 местами держал состояние «на процесс». Три редких окна (наносекунды; последствие — кик за битые пакеты засчитан
или не засчитан ошибочно) закрыты, вызов P48 `P55_KickAttribution(…, kcWhich==0 ? P49_TakeSecretPre(user) : −1, …)` не менялся:
- **Н-3** (P49): значение Secret до сброса — в таблице по указателю CUser (открытая адресация 1024 слота, CAS захвата), а не одной
  парой на процесс: стаб другой нити больше не перетирает значение до того, как P48 нити кика его возьмёт.
- **Н-4** (P47 → P55): +1 к Hack от отказа P47 объявляется «прочим» под замком учёта (`pendingOther`) ДО инкремента; прирост,
  кто бы его ни снял, сначала гасит объявленное. Сбой `sub_524540` (SEH) снимает объявление.
- **Н-5** (P55): «не засчитан» — только если **база + прочее ≤ порога** (база — значение счётчика на начале учёта; порог стока
  применяется к полному значению). Сток обнуляет 4 счётчика при старте (`sub_4A1FF0`) и в ClearUserMemory (`sub_4A2DC0`) —
  декомпил + дизасм стока, поэтому на 20000 база обычно 0. Строка PatchLog «прочих M» теперь = база + прочее.
Стенд `tools/stand_p48s` — 29 проверок (новые З/И/И2/К/К2); на прежней DLL v42 `d5243b5d` З, И, К провалены (дефекты воспроизводятся).
AsdaPatch Version 43, без новых ключей. Отчёт `Reports/anticheat/wave_SEC2c_20261015.md`.
