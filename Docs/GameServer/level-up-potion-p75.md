## 2. Что делает P75 (ред. 2)
| площадка | было | стало | зачем |
|---|---|---|---|
| U `0x004EDDC7` (Char_FunctionItem_Use) | `E8 24 4A 00 00` — `call 0x4F27F0` | `E8 rel32` → `StubUseGate` | шаг 1: решение до БД |
| S `0x004EF02E` (Char_FunctionItem_Use, LABEL_145) | `E8 8D 56 07 00` — `call 0x5646C0` (2140 «Use») | `E8 rel32` → `StubDbSend` | ★ ред. 2: замок «в пути» |
| D `0x004EF606` (sub_4EF270, ответ БД) | `E8 35 30 00 00` — `call 0x4F2640` | `E8 rel32` → `StubDbUse` | шаг 2: начисление |
| `0x004CBFEC` (exp_1) | `E8 FF 68 FF FF` — `call 0x4C28F0` (4036 себе) | `E8 rel32` → `StubLvSelf` | 4036 один раз |
| `0x004CC009` (exp_1) | `E8 C2 26 06 00` — `call 0x52E6D0` (4036 сектору) | `E8 rel32` → `StubLvSect` | 4036 один раз |
| `0x004CC08D` / `0x004CC27E` (exp_1) | `E8 FE 96 FC FF` / `E8 0D 95 FC FF` — `call 0x495790` | `E8 rel32` → `StubJar` | кувшин от зелья — нет |
| `0x00527374` (ClearUserMemory) | `E8 77 2A 04 00` — `call 0x569DF0` | **если P63 держит площадку (SessionClear) — не трогается**, P75 зовётся из `P63_OnUserClear`; иначе `E8 rel32` → `StubClear` | ★ ред. 2: замок снимается на выходе |

* **Шаг 1** (`P75_UseGate`, для кода `ItemCode`): отказ — как у штатных проверок: `[ebp-0x121] = 0`, общий выход `0x4EF0C3` → 5451 код 0
  (плашка 12837), в БД ничего не уходит, **предмет цел**. Причины: уровень ≥ `TargetLevel`; потолок imm8 `0x4CBB63` (P29) < цели; ExpTable не
  годна (нет строки цели / не растёт / опыт ≥ цели); запись Function_Table не та (категория ≠ `RequireCategory`, цель ≠ 1, `+25 == 3`, списание
  не 1/2); **★ замок «зелье в пути» этого персонажа**. Иначе — штатный `sub_4F27F0` и дальше сток. Перед пропуском `+37: 2 → 0` **в памяти**
  (бафф не ставится; файл таблицы не правится; без DLL — снова сток). Строки в FuncLog при пропуске нет (★ ред. 2, ревизия М1): дальше ещё
  штатные проверки.
* **★ Замок «зелье в пути»** (по образцу P63): ставится на площадке S, когда 2140 с кодом зелья уходит в БД (все штатные проверки шага 1
  пройдены), — на слот, с персонажем из тела 2140 (Userindex + Charidx) и тактом; FuncLog `[P75] LevelUpPotion DB_SEND`. Снимается: в шаге 2
  (начислено или нет); на выходе сессии (`ClearUserMemory`; общая точка P63 или своя площадка); по тайм-ауту `LockTimeoutMs` (15 с — как
  P63); замок другого персонажа в том же слоте не действует. Второе 558 при активном замке — тот же отказ 5451 код 0 (`Reason:7`).
* **Шаг 2** (`P75_AfterDbUse`): цикл штатных вызовов `Recv_BattleServerFromCharParamExp_1(mgr, num, 0, E[70] − опыт, 1, 1.0f)` — по уровню за
  вызов до 70, итог ровно `E[70]`, все уровневые последствия стоковые на каждом уровне. Если нужный опыт ≤ 0 / уровень уже ≥ цели к ответу БД
  — **только журнал** (`NO_GRANT`), опыт не трогается, предмет уже списан БД (сток доведёт до 5451 успеха). При замке этот случай невозможен
  (второго 558 в полёте нет, сам персонаж до 70 за миллисекунды ответа БД не дойдёт) — кроме ответа БД дольше `LockTimeoutMs`.
  Исключение внутри штатной функции (★ ред. 2, М2): процесс не падает, в PatchLog и FuncLog — громкая строка `EXCEPTION` с уровнем/опытом до и
  после и «рекомендован рестарт».
* **Сведения клиенту**: `SingleLevelUpPacket=1` — 4036 себе и сектору один раз, на последнем уровне (тело стоковое: абсолютные уровень, опыт,
  **очки навыков** +11, статы 36 + 68 б); обрыв цикла при подавленных 4036 → резервный 4036 той же раскладки. `SuppressSoulJar=1` — кувшин души
  от зелья не наполняется. Подавление — только внутри начисления P75 на этой нити (TLS).
* **«Один раз на персонажа»** — гейт уровня шага 1: после успеха персонаж ≥ 70, уровень не убывает (§1). Отдельной отметки нет (★ ред. 2,
  решение координатора по В2 ревизии): если связь/процесс оборвались между уходом 2140 и ответом 2141 (предмет списан БД, опыта нет) или
  начисление осталось частичным — новое зелье можно применить снова (уровень < 70), в отличие от SQL-отметки ред. 1, которая запирала зелье
  навсегда. Общая процедура списания всех функциональных предметов не трогается.
* Журналы: PatchLog `[P75] …`; FuncLog сервера канал 8 — `[P75] LevelUpPotion REFUSE / DB_SEND / GRANT / GRANT_SHORT / NO_GRANT / EXCEPTION`
  рядом со стоковыми `[REQUEST]/[DB_SEND]/[USE]`; LevelUp-лог стока (канал 39). Журнала античита нет.

### Почему так
* **Ловим код на штатных вызовах, где он — аргумент или поле тела** (`sub_4F27F0(num, код)`, `sub_4F2640(num, код)`, тело 2140 +7): только
  подмена цели `call`. Смена категории в файле опаснее (часть категорий отказывает на шаге 2 после списания в БД) — DLL требует категорию 6.
* **Таблицу не правим**: +37 → 0 в памяти и только у 558; без DLL — сток.
* **Штатная функция повышения по уровню за вызов** — все последствия уровня стоковые; итог ровно `E[70]`.
* **Замок, а не отметка в БД**: закрывает гонку двух кликов (второй запрос до ответа БД), не запирает зелье навсегда при обрыве, не меняет
  `UPSkillItemSpend`.
