## Зачем

Решение владельца 2026-09-12: поднять потолок числа карт, чтобы хватило места будущим картам
(FlammioPlain, Aquaton и др.) и чтобы у карты 23 `^MineWar^` появился слот.

## Что в оригинале (по дизассемблеру ЖИВОГО образа)

Почти всё, что связано с картами, у GameServer **динамическое**:

| Источник | Как читается | Предел |
|---|---|---|
| `MapData_Info\MapInfo.txt` | первое число N → `new(236*N+4)`, `dword_5F5EE8` / `dword_5F5E18` | нет |
| `MapData_Info\MapWarpCost.txt` | первое число N → матрица N×N в куче | нет |
| `NpcServer\ini\MapInfo.ini` | `MapCount` → `new[68*N+4]`, `byte_4DBF46` (байт) | 255 |
| `ChannelManager` | `MaxMapCount` из ini, массивы `MapStartX/Z` в куче (`[esi+0x5664]`) | 255 |

Жёстко зашит **ровно один** массив — «карта открыта + её имя» из `MapData_Info\OpenMapInfo.ini`:
**23 записи по `0x33` б** (1 б `Use` + 50 б `Name`), статически по VA `0x0060A880` в `.bss`.
Конструктор — `sub_582670@0x582670`:
`vector constructor iterator(0x60A880, 0x33, 23, sub_4BE660)`.

Именно он и есть потолок номеров карт: у карты без записи нет ни признака «открыта», ни потока.

## Почему нельзя просто «растянуть» массив

Массив лежит впритык: `0x0060A880` … `0x0060AD14` (23·51 = 1173 б), а с `0x0060AD18` начинается
объект `CThreadManager` (`mov ecx,0x60AD18; call LoadFameInfo` в `sub_582690@0x582690`) —
зазор **три байта**. Перед массивом, на `0x0060A87C`, тоже объект (`sub_5826B0`).
Ещё одна запись затёрла бы указатель на таблицу виртуальных функций `CThreadManager`.
⇒ массив обязан **переехать**.

★ Прецедент: чужой мод, который когда-то попал в нашу базу IDA (секция PE `.mapext`, архив
`RE/ida/archive_gameserver_2026-08-30/`), делал ровно это — переносил массив на `byte_68BF000`
в добавленной секции. Мы повторяем идею, но **без правки самого exe**: буфер живёт в нашей DLL.

## Чем лечим

Буфер `g_mapOpen[30*51]` в `.bss` самой `AsdaPatch.dll` (нули — ровно то, что делает поэлементный
конструктор `sub_4BE660`: `*this = 0; memset(this+1, 0, 0x32)`).
`DllMain` работает **до** `EntryPoint` хоста, то есть до `_initterm`, где вызывается `sub_582670` —
к моменту конструирования массива и база, и счётчик уже наши.

В шести площадках правится только абсолютный адрес (`disp32`/`imm32`), в пяти — только `imm8`
со счётчиком. **Длина и кодировка команд не меняются** (проверено оффлайн-подстановкой с
дизассемблом: все 11 площадок декодируются в одну команду прежней длины).

## Потолок 30 и почему не больше

Второй, **независимый** предел — массив `Total_PortalConfig.Ini` внутри `CUserManager`:

```
sub_522550@0x522550:
  vector constructor iterator(this+2656, 0x1F, 30, sub_530530);
  memset(this+2656, 0, 0x3A2);          // 0x3A2 = 930 = 30*31
```

Он индексируется **номером карты напрямую** — `RecvContinent_PortalMove`:
`this + 31*mapId + 2656`, а проверяется только `mapId >= 0 && mapId < dword_5F5EE8`
(число строк `MapInfo.txt`). Сразу за массивом, на `this+3588`, лежит DWORD-флаг, а на `this+3596` —
массив 550 записей игроков по `0x231` б. ⇒ номер карты **30 и выше = разбор чужой памяти**.

Поэтому **30 — жёсткий предел P30**. Дальше потребуется переносить и этот массив, а он адресуется
от регистра `this`, простой правкой операнда не обойтись (нужен трамплин — отдельная работа).

Прочие естественные потолки (в 30 не упираются, но зафиксированы):
* `m_iOpenMapCount` (`byte_5F5EF7`) — **байт**, и сравнение `cmp eax,imm8` знаковое ⇒ ≤ 127;
* NpcServer `byte_4DBF46` — байт, часть сравнений знаковые ⇒ ≤ 127;
* ChannelManager `MaxMapCount` — байт со знаковым сравнением ⇒ ≤ 127;
* 8 порталов на карту (`this+2324`, `0x29`×8) — к числу карт отношения не имеет.

## Второй зажим: число строк MapInfo.txt

Цикл раздачи потоков для каждого `j < cap` читает `Use[j]` и, **только если он не ноль**, — тип карты
из `dword_5F5E18 + 236*j + 63`. В массиве `MapInfo.txt` ровно `dword_5F5EE8` записей. Значит `cap`
выше числа строк `MapInfo.txt` безопасен лишь пока у лишних секций `MAP_k` стоит `Use=0`.
★ Это **дефект оригинала** (он существует и при 23 слотах, если `MapInfo.txt` короче).

Чтобы мины не было вовсе, DLL при установке сама читает первое число
`MapData_Info\MapInfo.txt` и зажимает `cap` им же:

```
cap = min(MaxMaps, 30, строк_в_MapInfo.txt);  если cap <= 23 — патч не ставится вовсе
```

Файл не прочитался — патч **НЕ ставится** (лучше 23, чем чтение за концом массива), в `PatchLog`
строка с `!`. Дополнительно в лог пишется предупреждение, если `MapWarpCost.txt` описывает
меньше карт, чем `cap`.

**Следствие для владельца:** потолок сам следует за `MapInfo.txt`. Сейчас там 24 строки ⇒
после установки будет **24 слота (номера 0…23)**, то есть слот у `^MineWar^` появится сразу.
Чтобы получить 25-й и далее (до 30) — сначала дописать строку в `MapInfo.txt`.

## ⚠ Чего этот патч НЕ делает

**Он сам по себе НЕ оживляет карту 23 `^MineWar^`.** Слот и признак «открыта» она получит, но:

1. её тип карты в `MapInfo.txt` = **6**, а поток создаётся только для типов **0, 1 и 3** —
   проверка `test edx,edx / cmp edx,1 / cmp edx,3` @`0x4A53AB`…`0x4A53E6`. Тип 6 сервер знает
   (7 мест в обработке порталов/варпа трактуют его как «особый»), но потока ему не даёт;
2. на живом сервере **нет ни одного её файла**: `MapData_Info\^MineWar^.sim`,
   `MonsterData_Info\^MineWar^.svr`, `NpcData_Info\^MineWar^.npc`,
   `PortalIP_Info\^MineWar^_PortalConfig.Ini`, `ConnectIP_Info\^MineWar^_ConnectIP.ini` — проверено
   поиском по имени и по содержимому;
3. NpcServer о ней не знает: `ini\MapInfo.ini` `MapCount = 23`, то есть карты 0…22;
   `SectorInfo.ini` — 23 секции.

Оживление `^MineWar^` — **отдельная работа по данным** (+ решение владельца, менять ли её тип
карты на 0/1/3 или добавлять тип 6 в набор «получают поток»).

## Как установить (делает владелец)

1. Остановить `GameServer` и `Indun_GameServer` (DLL занята процессом — подмена на ходу невозможна).
2. В **обеих** папках (`v2\GameServer\`, `v2\Indun_GameServer\`) переименовать текущую
   `AsdaPatch.dll` → **`AsdaPatch.dll.bak_pre_p30_20260912`** (это обязательный бэкап; текущая
   MD5 `2e9001ba…`, 285 184 б) и положить новую из
   `@@ASTORY_DEV_ROOT@@\AstoryServer\Patches\AsdaPatch\out\AsdaPatch.dll` (MD5 `725ddd4c…`, 294 912 б).
   `GameServer.exe` и `patches.ini` **не трогать** — секцию `[P30_MapSlots]` DLL допишет сама.
3. Запустить процессы.

**Проверка** — `GameServer\Log\Log_Patch\PatchLog_<дата>.txt` последнего старта:
* строка `P30: MapInfo.txt строк 24, MapWarpCost.txt N=23, жёсткий предел 30`;
* 11 строк `P30: @0x004A043E …` / `@0x004A04FD …`;
* итог `P30: слотов карт 23 -> 24 (номера 0…23); массив перенесён 0x0060A880 -> 0x…`;
* `[OK] P30_MapSlots`;
* в `ConfigSet\patches.ini` — `Version=14` и новая секция `[P30_MapSlots]`.

Если в логе `MISMATCH P30 @0x…` — патч не поставлен, сервер работает как раньше (23 слота);
ничего откатывать не нужно, сообщить нам байты из строки.

## Откат

* Быстрый: `[P30_MapSlots] Enabled=0` в `patches.ini` обоих процессов + рестарт (23 слота, массив
  остаётся стоковым на `0x0060A880`).
* Полный: вернуть `AsdaPatch.dll.bak_pre_p30_20260912` + рестарт.
* ⚠ Перед откатом убрать из `OpenMapInfo.ini` `Use=1` у карт с номером ≥ 23 и вернуть игроков с этих
  карт — иначе персонаж останется записанным на карту, которой у сервера больше нет.

## Риски

1. **Массив живёт в нашей DLL.** Если DLL не загрузится (а без неё не работает ни один патч),
   массив останется стоковым — поведение вернётся к 23 слотам, не к падению.
2. **Порядок инициализации.** Патч опирается на то, что `DllMain` выполняется до `_initterm` хоста.
   Так работают все наши патчи с 04.08; ошибка здесь проявилась бы сразу при старте.
3. **Карты 30+** — за пределом `Total_PortalConfig`; DLL сама не даёт зайти дальше 30.
4. **Рассинхрон данных.** Номер карты обязан совпасть в `MapInfo.txt`, `OpenMapInfo.ini`,
   `Total_PortalConfig.Ini`, `ChannelManager\ini\MapInfo.txt`, NpcServer и в клиенте
   (`map_table.csv` / `DT_MapTable`). Ошибка ломает вход на карту.
5. **`^MineWar^` — см. раздел «Чего этот патч НЕ делает».**
