# P106_FriendAcceptNotify: принявший дружбу получает 4151 при флаге 2 `UPFriendAdd`

- **Дата:** 2026-11-05 (сессия friend-accept; решение владельца «дефекты оригинала исправляем»)
- **Статус:** собрано и проверено, **НЕ ВЫЛОЖЕНО** (выкладка только с разрешения владельца, через координатора)
- **Процесс и файлы:** `@@ASTORY_SERVER_ROOT@@\Working_ASDA\v2\{GameServer,Ch2_GameServer,Indun_GameServer}\AsdaPatch.dll`
  (папки берутся из `stack_layout.GS_FOLDERS`), `ConfigSet\patches.ini` (секцию дописывает сама DLL)
- **Тип:** [ИСПРАВЛЕНИЕ] дефекта оригинала, байтовый участок в памяти процесса (DLL AsdaPatch). `GameServer.exe` на диске не меняется.
- **Протокол:** не меняется (4151 тот же, 32 байта; 2215/2216 те же)
- **DLL:** AsdaPatch **v63** `9862a5deb2ddb25616ba2a7f6272c468`, закреплена в `tools/p106_data/AsdaPatch_v63_9862a5de.dll`.
  Собрана поверх v62 `f2476bf0` (P100 EchoAllCodes, сессия p100-postbox-2604-reply), поэтому содержит обе правки.
  На стойке сейчас v60 `7cb74110`.


1. Принявший (B) шлёт 0x1039. `Recv_UserFriendOK@0x537BF0` (GameServer.c:118977) отправляет в DB 2215.
   Заголовок: userNum = пригласивший (A). Блок 16 байт: +2 userIndex A, +6 charIdx A, +7 i16 userNum A,
   +9 i16 userNum B, +11 userIndex B, +15 charIdx B.
2. DBManager `sub_42AD80` (`RE/ida/db_work/DBManager.exe.c:19285`) выполняет `EXEC UPFriendAdd @Userindex=A, @Charidx=A,
   @Fuserindex=B, @Fcharidx=B` и возвращает блок обратно; байт 0 = Flag.
3. Флаги `UPFriendAdd` (Joy1; снимок `Docs/_Common/P45_multilang_text/snapshot/joy1_proc_defs_2026-10-08.json`):

   | Flag | Значение | Вставленные строки |
   |---|---|---|
   | 1 | обе строки добавлены | A→B и B→A |
   | 2 | у A уже был B | **B→A** (список B пополнился) |
   | 3 | у B уже был A | A→B |
   | 4 / 5 / 6 | полон список A / B / обоих | — |
   | 7 | оба уже друзья | — |
   | 0 | ошибка | — |

4. Ответ 2216 (0x8A8) обрабатывает `sub_406370@0x406370` (GameServer.c:2542). При флагах 1/2/3, если оба в сети,
   4151 код 1 с записью B уходит пригласившему A (`0x40651B`). Затем `if (flag == 1 || flag == 3)` (`0x406520…0x406530`):
   4151 код 1 с записью A уходит принявшему B (`0x406618`).

## Дефект

При флаге 2 в БД появляется строка B→A, но B не получает 4151. Сообщения «добавлен в друзья» нет, а записи A
в списке B нет до перезахода. При флаге 3 сток, наоборот, шлёт B запись A, которая у него уже была. Это безвредно: клиент порта
обновляет запись по ключу (`UAsdaCommunityFriendSubsystem::OnPlayerMenuResult`, upsert по CharId+ClassKey).

## Что сделано (байты «было → стало»)

Участок `0x406520`, 22 байта:

```
было:  0F B6 45 CC  83 F8 01  74 0D  0F B6 4D CC  83 F9 03  0F 85 E7 00 00 00
       movzx eax,[ebp-34h]; cmp eax,1; je 0x406536; movzx ecx,[ebp-34h]; cmp ecx,3; jne 0x40661D
стало: 0F B6 45 CC  48  83 F8 02  0F 87 EF 00 00 00  0F 1F 84 00 00 00 00 00
       movzx eax,[ebp-34h]; dec eax; cmp eax,2; ja 0x40661D; nop dword [eax+eax+0]
```

Теперь ветка принявшего выполняется при флаге 1…3. Флаг проверяется явно и не зависит от проверки на входе в ветку успеха.
Новые значения eax/ecx после участка записываются раньше, чем читаются (`0x406545` / `0x406548`).

- Исходник: `AstoryServer/Patches/AsdaPatch/src/patches/p106_friend_accept_notify.cpp`. Реестр: `src/patches/Registry.cpp`.
- Ключ: `[P106_FriendAcceptNotify] Enabled` (1 по умолчанию; 0 = сток). Config `Version` 62 → 63 (см. `Config.h`).
- Журнала ac.other нет: событие штатное. В PatchLog пишется строка «P106: ответ дружбы 2216…».

## Проверка

- `tools/verify_p106.py` (в `run_checks.py`, группа verify) проверяет:
  - 6 участков и сток на 4 образах (сток, GameServer, Indun, Ch2);
  - что участок лежит на границах инструкций и что извне в него нет переходов;
  - эмуляцию участка в Unicorn для флагов 0…7: сток идёт в ветку принявшего при {1,3}, P106 — при {1,2,3};
  - что остальные 213 инструкций функции не изменились;
  - строки DLL и что других площадок патчей в функции нет.
- Живой тест на dev (после выкладки): A приглашает B, когда B уже есть в списке A (флаг 2: например, B удалил A у себя).
  B принимает, и B должен увидеть плашку 221 и строку журнала. Затем A появляется в его списке без перезахода.

## Выкладка (только координатор, с разрешения владельца)

★ 05.11 решение владельца: v62 (P100 EchoAllCodes) и P106 выкладываются ВМЕСТЕ одним перезапуском — общей DLL v63 `9862a5de` поверх
живой v60. Команда:

```
set ASDA_P106_FROM_V60=1
py -3.13 tools/deploy_p106.py
py -3.13 tools/restart_stack.py --deploy deploy_p106.py --expect P106_FriendAcceptNotify --expect P100_ChargeStack
py -3.13 tools/deploy_p106.py --check-started
```

Переменную нужно задать до всех трёх команд: `restart_stack` передаёт скрипту только `--apply`.
`deploy_p100_echo.py` в эту выкладку **не запускать**: его WANT — v62 `f2476bf0`, поверх v63 он откажет с кодом 8 и ничего не тронет.
После выкладки проверку старта делает только `deploy_p106.py`: и P106, и P100 (EchoAllCodes дописывается DLL, `Config.cpp` MergeMissing).

0. Порядок. Если v62 уже выложена, P106 идёт обычным путём. Если на стойке ещё v60, есть два пути:
   - сначала выложить v62, затем P106;
   - выложить v63 прямо поверх v60 одним рестартом: перед шагами 1–2 задать `ASDA_P106_FROM_V60=1`
     (или передать `--from-v60` в ручном вызове). Без этого скрипт остановится с кодом 10.
     Тогда на стойку приходят и P100 EchoAllCodes, и P106, а откат вернёт v60.
1. `py -3.13 tools/deploy_p106.py` — сухой прогон (только чтение по SSH), ожидается «всё готово к --apply».
   Проверено 05.11 11:54: с `ASDA_P106_FROM_V60=1` — «всё готово к --apply» (3 папки); без него — СТОП 10 «v62 ещё не выложена».
2. `py -3.13 tools/restart_stack.py --deploy deploy_p106.py --expect P106_FriendAcceptNotify` — объявление, остановка,
   `--apply` во всех `GS_FOLDERS`, паритет, старт.
3. `py -3.13 tools/deploy_p106.py --check-started` — «[OK] P106_FriendAcceptNotify» в блоке последнего запуска каждого GS.

## Откат

- **Быстрый, без замены DLL:** `[P106_FriendAcceptNotify] Enabled=0` в `patches.ini` всех GS (UTF-16LE, одна строка), затем рестарт GS.
- **Полный:** стойку остановить, выполнить `py -3.13 tools/deploy_p106.py --rollback` (DLL из `.bak_20261105_p106`, только поверх WANT)
  и запустить стойку. Прежняя DLL сама понизит `Version`, а секция P106 останется в ini и будет проигнорирована.
- Рестарт: нужен (DLL читается при старте GS). БД не меняется.
