## 2. ЧТО именно меняется — адреса и байты «было → стало»

Все VA даны для `ImageBase = 0x400000`; в файле образа смещение = `VA − 0x400000` (секция `.text`
отображается 1:1). Правки живут в памяти процесса, файл на диске не меняется.

### D4 — `FixKeepingDupe` (ДЮП, приоритет №1)
> **★ Поправка 15.10.2026 (разбор `Reports/anticheat/re_itemkeeping_hidden.md`):** условие ветки «CharItemKeeping(11)» — ячейка лотка 45,
> количество 8 и **стопка того же предмета на складе ровно 8** (`[ebp-0x84] == 8`, а не «тип 8»); флаги `+0x51AC..+0x51B0` — поля **объекта потока
> карты `CThread` (`*(CUserManager+4)`)**, а не `CUser`. Эта ветка — **шаг 5 кодовой комбинации закладки**, взводящей затирание базового блока
> персонажа у всех 550 слотов (RunProcess 10024). D4 стоит ПОСЛЕ взведения и закрывает только дюп; закладку обезвреживает **P72**
> ([hidden-wipe-disarm-p72.md](hidden-wipe-disarm-p72.md)). Ниже — текст на момент написания (условие описано неточно).

| VA | было | стало |
|---|---|---|
| `0x0050A6E6` (5 б) | `E8 05 82 FB FF` — `call 0x4C28F0` | `E9 <rel32>` — `jmp` на трамплин в DLL |

Трамплин (12 б в DLL, проверен дизассемблером в собранной DLL):
```
call  dword ptr [ptr] -> GameServer 0x004C28F0   ; тот же самый вызов, что и был
jmp   dword ptr [ptr] -> GameServer 0x0050ACBB   ; ← недостающий return (эпилог функции)
```
Регистры и стек не трогаются: `ecx` (this) и шесть уже уложенных аргументов пакета 5009
доходят до `sub_4C28F0` нетронутыми, стек чистит она сама (`ret 0x18`), `ebp` цел.

### D2 — `FixPageRange4050` (чтение чужой памяти)

Верхняя граница остаётся стоковой и работает сама: `30 * pageNo > ёмкость` при `pageNo >= 10`.
Новых веток не появляется — уходим в СУЩЕСТВУЮЩУЮ ветку «SlotCount Error» @0x529F1A.

### D13 — `FixMoveCapacity` (предмет в невидимой ячейке)

| VA | было (6 б) | стало |
|---|---|---|
| `0x004CE7FD` (источник) | `81 FA 0E 01 00 00` — `cmp edx, 270` | `E9 <rel32>` + `nop` — `jmp` на трамплин |
| `0x004CE9D1` (приёмник) | `81 F9 0E 01 00 00` — `cmp ecx, 270` | `E9 <rel32>` + `nop` — `jmp` на трамплин |

Трамплин (вариант «источник»; «приёмник» отличается только регистром ячейки и адресом возврата):
```
push eax / push ecx / push edx          ; ячейка (edx) сохранена
movzx eax, word [ebp+8]                 ; userIndex
push eax
mov  ecx, [ebp-0x2D8]                   ; CUserManager* (this функции CharItemMove)
call [ptr] -> 0x005324A0                ; sub_5324A0(mgr, idx) -> CUser*, стек чистит сама
test eax,eax / jz  Fallback
movsx eax, word [eax+0x1AE]             ; ёмкость склада в ячейках
test eax,eax / jle Fallback             ; страховка от порченого поля
cmp  eax,0x10E / jle Have
Fallback: mov eax,0x10E                 ; стоковый потолок массива 270
Have:     pop edx
          cmp edx, eax                  ; ← флаги ровно для следующего `jl`
          pop ecx / pop eax             ; pop флаги НЕ меняет
          jmp [ptr] -> 0x004CE803        ; `jl 0x4CE850` (для приёмника: 0x004CE9D7)
```

### D15 — `FixMoveSilentReject` (сервер молчит, UI клиента залипает)

Шесть переходов на `0x4D12BB` (`xor eax,eax` перед эпилогом, БЕЗ пакета) переводятся на
**LABEL_220** — штатный отказ этой же функции «5001, код 2». Компилятор размножил LABEL_220
по функции; используются две его копии: `0x4CF186` и `0x4D1273`.

| VA | было | стало | когда сюда попадаем |
|---|---|---|---|
| `0x004CF0EC` | `E9 CA 21 00 00` | `E9 95 00 00 00` → `0x4CF186` | источник 3, приёмник не 1/2 |
| `0x004CFC99` | `E9 1D 16 00 00` | `E9 E8 F4 FF FF` → `0x4CF186` | **источник 1 (инвентарь), приёмник не 1/3 — сюда попадает приёмник 5 (склад)** |
| `0x004D09BE` | `E9 F8 08 00 00` | `E9 C3 E7 FF FF` → `0x4CF186` | **источник 2, приёмник не 2/3 — сюда попадает приёмник 5 (склад)** |
| `0x004D0E4F` | `E9 67 04 00 00` | `E9 32 E3 FF FF` → `0x4CF186` | источник 4, приёмник не 4 |
| `0x004D0E5E` (6 б) | `0F 85 57 04 00 00` | `0F 85 22 E3 FF FF` → `0x4CF186` | источник вообще не 1..5 |
| `0x004D1271` (2 б) | `EB 48` | `EB 00` → `0x4D1273` | источник 5 (склад), приёмник не 5 |

★ Для `0x004D1271` под переход отведено всего 2 байта, но прямо следом (`0x4D1273`) лежит
своя копия LABEL_220 — поэтому там достаточно «прыжка на следующий байт».

## 3. ЗАЧЕМ — симптом → диагноз

* **D4 (дюп).** *Симптом:* при вкладе на склад клиент получает «неудача», предмет остаётся в
  лотке, а следом приходит второй ответ 5009 с кодом «успех»; инвентарь и склад расходятся.
  *Диагноз:* ветка-ловушка (условие: ячейка лотка 45, количество 8, тип 8, флаги
  `CUser+0x51AC..0x51AF == 1` и `CUser+0x51B0 == 0`) отправляет 5009 с кодом 5 и **забывает
  `return`**. Выполнение продолжается по общему хвосту и доходит до DB-запроса **2029** —
  предмет реально уезжает в базу, хотя клиенту сказано «отказ». Рабочий вектор на дублирование.
  *Лечение:* сделать ровно тот `return`, которого не хватает (уйти в эпилог 0x50ACBB).
  *Штатный путь не затронут:* адрес `0x50A6EB`, куда ведут восемь `jne` при НЕвыполнении условия
  ловушки, остаётся нетронутым.

* **D2 (чтение чужой памяти).** *Симптом:* собранный вручную пакет 4050 с номером страницы 0
  заставляет сервер прислать 1710 байт памяти `CUser` (диапазон `CUser+4632 … CUser+6341`).
  *Диагноз:* номер страницы читается `movzx` (0..255) и проверяется только сверху; при 0
  нижняя граница цикла становится −30. *Лечение:* отклонить страницу 0 существующей веткой отказа.

* **D9 (порча памяти из БД).** *Симптом:* битая строка в базе пишет 57 байт по произвольному
  смещению внутри (и за пределы) `CUser`. *Диагноз:* `&&` вместо `||` — условие невыполнимо,
  проверки нет вообще. *Лечение:* перевернуть первое ветвление.

* **D13 (предмет пропадает).** *Симптом:* игрок с ёмкостью склада 30 перекладывает предмет и
  тот исчезает насовсем. *Диагноз:* `CharItemMove` пускает ячейку до 269 (потолок массива), а
  `Send_ClientStoreHouseItemInfo` отдаёт только страницы в пределах ёмкости — ячейка становится
  невидимой и недоступной. *Лечение:* сверять с реальной ёмкостью `CUser+0x1AE`.

* **D15 (залипший интерфейс).** *Симптом:* после неудачной попытки перетащить предмет окно
  инвентаря/склада перестаёт отвечать до перезахода. *Диагноз:* клиент на 5000 ставит UI-замок
  (`sub_922033(g_pUIManager,1)`) и снимает его только по 5001, а сервер в шести сочетаниях
  типов молча возвращает 0. *Лечение:* отвечать штатным отказом «5001, код 2».

* **D18 (залипший склад).** *Симптом:* после отказа на 4050 склад перестаёт открываться и
  работать до перезахода. *Диагноз:* флаг «запрос в полёте» (`CWarehouseWnd+22328`, байт 0)
  снимается только приходом 4052, а ветка отказа не шлёт ничего. *Лечение:* прислать штатный 4052.

Ссылка на полный реверс подсистемы: `Reports\warehouse_net_server.md`
(§4 — 4050, §6 — 5008/5010, §12 — дефекты, §16 — перемещение 5000).

## 4. D17 (близость к NPC-кладовщику) — подтверждён, но НЕ закрывается. Почему

Проверка близости на сервере **сломала бы штатный предмет игры**: «свиток вызова склада»
(`Property == 0x70`) в `Char_FunctionItem_Use` обрабатывается так (`GameServer.c:92692`):
```c
case 0x70:
    v85 = 0;          // код успеха
    goto LABEL_143;   // предмет расходуется, уходит 5451 «успех»
```
То есть сервер по замыслу авторов **не делает ничего**, окно склада открывает клиент, и
предмет существует ровно для того, чтобы пользоваться складом ИЗ ЛЮБОЙ ТОЧКИ МИРА.
Любая проверка «стой рядом с кладовщиком» обесценит этот предмет и сломает уже купленные.

Кроме того, GameServer не располагает нужными данными: позиции NPC живут в NpcServer, а
никакой из четырёх складских обработчиков не обращается ни к позиции, ни к карте, ни к NPC.

**Решение за владельцем.** Возможные варианты (ни один не реализован):
запрет склада в боевых/PvP-зонах по типу карты; ограничение по списку карт; таймаут
«сессии склада», открываемой только диалогом с NPC или свитком. Все три требуют новых данных
и меняют штатное поведение, поэтому в P18 не входят.

## 5. Включение / выключение — `GameServer\ConfigSet\patches.ini`

Секция дописывается DLL автоматически при первом старте (существующие значения администратора
не затираются; версия формата ini поднята 3 → 4). Каждый дефект — свой ключ, можно включать по одному.

```ini
[P18_WarehouseDupeAndBounds]
Enabled=1                  ; главный выключатель секции
FixKeepingDupe=1           ; D4  — ДЮП: недостающий return в CharItemKeeping(11)
FixPageRange4050=1         ; D2  — страница 0 в 4050 -> отказ (закрыто чтение чужой памяти)
FixReply4050OnReject=1     ; D18 — при отказе на 4050 слать штатный 4052
FixDbSlotBounds=1          ; D9  — три мёртвые проверки границ (`&&` -> `||`)
FixMoveCapacity=1          ; D13 — граница склада из ёмкости игрока, а не зашитые 270
FixMoveSilentReject=1      ; D15 — шесть немых `return 0` -> штатный отказ 5001 код 2
```

Порядок установки: патч сверяет **все включённые площадки ДО первой записи**. Если хотя бы
одна не совпала — не ставится НИЧЕГО (`MISMATCH` в `PatchLog`), сервер работает как раньше.

## 8. Как ОТКАТИТЬ (пошагово)

**Мягкий откат, без подмены файлов и без рестарта DLL-сборки** — по одному дефекту:
1. Остановить `GameServer`.
2. В `GameServer\ConfigSet\patches.ini` в секции `[P18_WarehouseDupeAndBounds]` поставить `0`
   у нужного ключа (или `Enabled=0` — снимет все шесть исправлений сразу).
3. Запустить `GameServer`. В `Log\Log_Patch\PatchLog_<ГГГГММДД>.txt` строк P18 не будет.

**Полный откат DLL:**
1. Остановить `GameServer`.
2. Заменить `\\…\v2\GameServer\AsdaPatch.dll` на `AsdaPatch.dll.bak_pre_p18_20260827`
   (сверить MD5 `44AB0602…`).
3. Секцию `[P18_WarehouseDupeAndBounds]` из `patches.ini` можно оставить — старая DLL её
   просто не читает.
4. Запустить `GameServer`.

`GameServer.exe` в откате не участвует ни в одном из вариантов.

## 10. Риски и связанное

* **Изменение штатного пути — только одно, и оно осознанное:** при отказе на 4050 сервер теперь
  ОТВЕЧАЕТ (4052) там, где раньше молчал (D18), и при шести неподдержанных сочетаниях типов в
  5000 отвечает «5001 код 2» вместо молчания (D15). В обоих случаях отправляется пакет, который
  сервер и так умеет слать по другим веткам; ни одна ранее РАБОТАВШАЯ операция не затрагивается.
* **D4** срабатывает только внутри очень узкого условия (ячейка лотка 45 + количество 8 + тип 8 +
  конкретная комбинация флагов `CUser+0x51AC..0x51B0`), в норме эта ветка не выполняется вовсе.
  ⚠ Не установлено, была ли эта ветка задумана как «ловушка, которая помечает нарушителя и всё
  же пропускает операцию» (она выставляет `CUser+0x51B0 = 1` и пишет `GetTickCount` в
  `CUser+0x51B4`). Пометка нарушителя сохраняется — патч убирает только продолжение операции
  после отправленного отказа.
* **D13:** если поле ёмкости `CUser+0x1AE` окажется испорченным (≤ 0 или > 270), трамплин
  откатывается на стоковые 270 — то есть на текущее поведение, а не на отказ.
* **D9:** охватывает не только склад, но и два соседних контейнера (инвентарь 30, второй мешок 60) —
  дефект в них дословно тот же. Если нужен только склад, оставить лишь ту площадку нельзя ключом:
  ключ `FixDbSlotBounds` общий на три (это один класс дефекта в трёх соседних функциях).
* **D17 не закрыт** — см. §4. Склад по-прежнему работает из любой точки карты; это соответствует
  наличию в игре свитка вызова склада.
* **D1, D3, D5, D6, D7, D8, D16, D19** из отчёта в P18 НЕ входят (в задании их не было);
  часть из них — клиентские или требуют решения по игровому балансу.
