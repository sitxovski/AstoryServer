## ЗАЧЕМ (симптом → диагноз)

**Симптом.** 24 звания с id 256…279 получить невозможно ничем: ни игрой, ни командой оператора.
Свободных номеров ниже 256 не осталось — заняты все 256.

**Диагноз.** Маска славы — **ровно 256 бит** и у клиента, и у сервера. У сервера это два поля
`CUser` по 4 qword, и **нарастить их на месте нельзя**: между ними лежит указатель.

| адрес | размер | что |
|---|---|---|
| `CUser+0x174` (372) | i32 | charId (сверено: `0x54BD7F  mov edx,[ecx+0x174]`) |
| `CUser+0x178` (376) | — | имя персонажа (`0x54AA52  add ecx,0x178`) |
| `CUser+0x17DD0` (97744) | i32 | очки славы |
| `CUser+0x17DD8` (97752) | i32 | троттл смены звания (60 с) |
| `CUser+0x17DDC` (97756) | **32 б** | маска «ПОЛУЧЕНО» |
| `CUser+0x17DFC` (97788) | ptr | ★ массив записей званий по 44 б — **лежит МЕЖДУ масками** |
| `CUser+0x17E00` (97792) | **32 б** | маска «НАЙДЕНО» |

с id ≥ 256 нельзя было ни надеть, ни удалить, даже когда оно получено.

★ `cmp …, 0x100` во всём тракте **ровно один** — №1. Размер выделения таблицы
(`96*count`, `0x4A19DE…0x4A19F3`: `mov edx,0x60; mul edx; call operator new`),

★ Загрузчик `FameInfo.txt` — **`sub_4A18F0@0x4A18F0`**; «`LoadFameInfo@0x49F410`» из
прежнего отчёта — ВЫЗЫВАЮЩАЯ его функция инициализации (миснейм, исправлен).

### Где живут биты 256…511
В `CUser` места нет, поэтому старшая половина обеих масок положена **в хвост массива записей
званий**: он выделяется на игрока как `operator new(44 * N)` и адресуется через `CUser+0x17DFC`.
Наш аллокатор берёт на 64 байта больше и обнуляет добавку:

```
записи[0 … 44*N-1]              — как в стоке
хвост[0  … 31]                  — биты 256…511 маски «получено»
хвост[32 … 63]                  — биты 256…511 маски «найдено»
```

Хвост живёт и умирает вместе с массивом — отдельных таблиц, индексов и поиска по указателю не нужно.
Размер `44*N` запоминается в DLL при первом выделении; если вдруг придёт другой размер, старшая
половина **отключается** (лучше отказ, чем чтение чужой памяти).

### Почему стоковый путь не может пострадать
Трамплины стоят **на ВХОДЕ** функций. При `id < 256` трамплин доигрывает вытесненный пролог
(`push ebp; mov ebp,esp; sub esp,X`) и уходит в оригинальный код — байт в байт как было.
Новый код исполняется ТОЛЬКО для id ≥ 256.

### Схема совместимости клиент ↔ сервер
★ **Формат самоописателен по длине тела, расширение дописано В ХВОСТ:**

| пакет | старое тело | новое тело | где хвост |
|---|---|---|---|
| 6066 «маска получено» | 42 б | **74 б** | `[42..73]` = биты 256…511 |
| 6086 «маска найдено» | 38 б | **70 б** | `[38..69]` = биты 256…511 |

Старая часть не сдвинута, поэтому **не обновлённый клиент** читает свои фиксированные
`0x2A`/`0x26` байт (`netOnCharEquipUpdate@0xE9A6F0` и `netHandler_OnCharData32@0xE9A7D0`
копируют ровно `0x20` байт маски) и хвост просто не замечает — рукопожатие не нужно.
**Обновлённый клиент** смотрит на длину тела и понимает оба формата
(`UAsdaTitleSubsystem::ParseMaskBody`, откат `asda.Title.Mask512 0`).
Обратное направление (C→S 6067/6069) **не менялось вовсе**: там `titleId` уже i16.

Второе доказательство, что приёмник клиента длиной не ограничен: опкод **2255** той же системы
ходит ПЕРЕМЕННОЙ длины (`6 + 46·N`) через тот же читатель.

## ⚠ ЧЕГО ПАТЧ НЕ ДЕЛАЕТ (обязательно к прочтению)

1. **Биты 256…511 НЕ сохраняются в базу.** Маска ездит в БД пакетами **2256** (82 б, выдача),
   **2257** (54 б, снятие) и **2266** (40 б, «секрет открыт») — во всех трёх ровно 4 qword,
   и принимает их **DBManager**, а не GameServer. Поэтому на «высоком» пути мы НАМЕРЕННО
   не шлём эти три пакета: id ≥ 256 для DBManager вне диапазона (у него свой контроль
   `RecvDBUserFameInfo … iFameIndex Error`).
   **Следствие:** звание с id ≥ 256, выданное в сессии, после перезахода персонажа пропадёт.
2. **Одного кода мало — нужна ТАБЛИЦА.** На живом `ConfigSet\FameInfo.txt` содержит **251**
   запись (id 0…250), а гейт `id < число записей` стоит во всех трёх функциях. Чтобы звания
   256…279 вообще существовали на сервере, таблицу надо дорастить минимум до 280 записей.
   Это правка **ДАННЫХ**, а не кода; строки 251…279 сами не выдумываем (авторитет — сервер).
3. Патч не трогает `Indun_GameServer` (решение владельца от 2026-08-04 — работаем только с
   основным GameServer).
