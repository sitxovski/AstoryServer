## ЗАЧЕМ (симптом → диагноз)

**Симптом.** Рейтинговое звание («максимальный уровень на сервере», «…среди воинов /
лучников / магов», «больше всех золота») остаётся у игрока навсегда: когда лидером
становится другой, у прежнего оно не снимается.

**Диагноз — ЧЕТЫРЕ дефекта оригинала, все в одном тракте.**

Рейтинговые звания — записи `FameInfo` с `Group == 1`, id **65…69**. Выдаёт их приёмник
межсерверных опкодов **3404…3408** `sub_54D710@0x54D710` (вызов из
`ConnectSocketMsgProcess@0x42FAB0`, ветки `case 0xD4C…0xD51`).
Тело пакета: заголовок 9 б + N записей по 13 б, `N = (len − 10) / 13`, остаток обязан быть 0:

| смещение в записи | размер | что |
|---|---|---|
| +0 | i32 | значение (ранг/очки; используется только веткой 3409) |
| +4 | i32 | **UserIndex** — индекс АККАУНТА (`CUser+0x174`), не персонажа |
| +8 | i16 | userNum (+2 байта не используются) |
| +12 | i8 | **флаг — в стоке МЁРТВЫЙ** |

### D1 — снятия нет вовсе

Единственный вызов `SubFameBit@0x54AD00` во всём образе идёт из
`DeleteFameInfo@0x54CE30` — по **клиентскому** пакету 6069 «удалить звание».
А звание с `Group == 1` клиент удалять не даёт
(`questItem_ValidateSelection@0xE99C30`, нотис 2428). Итог: выданное рейтинговое
звание не снимается ничем.

★ Второй метод (закон `false-negatives-method`): сплошной поиск отправки опкодов
3404…3408 по `DBManager.exe`, `LoginManager.exe`, `NpcServer.exe`,
`ItemRelayServer.exe` — **ни одной отправки**. То есть в оригинале рейтинговые звания
никто и не выдавал: приёмник есть, отправителя нет. Отправитель — наш P23.

### D2 — одна ненайденная сессия рвёт весь пакет

```
0054D86F  cmp  dword [ebp-0x24],0
0054D873  jne  0x54D889
0054D875  mov  dword [ebp-4],-1
0054D87C  lea  ecx,[ebp-0x38]
0054D87F  call 0x49BF20
0054D884  jmp  0x54D950            ; ★ ВЫХОД ИЗ ВСЕЙ ФУНКЦИИ, не `continue`
0054D889  mov  eax,[ebp-0x24]
0054D88C  mov  ecx,[eax+0x174]     ; UserIndex
0054D892  cmp  ecx,[ebp-0x34]
0054D895  je   0x54D8AB
0054D897  …                        ; ★ и здесь тоже ВЫХОД
```
Один офлайновый (или переподключившийся) игрок в списке съедал бы выдачу всем,
кто стоит в пакете после него.

### D3 — `SubFameBit` немой для клиента

`SubFameBit` снимает бит, обнуляет запись, вычитает очки и шлёт в базу 2256 / 2257
(и 2266, когда взводит бит «найдено») — но **клиенту не шлёт ничего**.
А маска 6066 уходит клиенту **ровно в одном месте** — `recvDBUserFameBitInfo@0x54BD10`,
то есть только при входе персонажа в игру. Без правки снятое звание висело бы у
клиента до перезахода.

### D4 — плашка над головой не обновляется

`DeleteFameInfo`, снимая **надетое** звание, обнуляет активный слот, снимает бонусы и
шлёт в базу 2258 — но **6068 не рассылает**. Для сравнения, `ChangeActiveFame@0x54C820`
при обычной смене звания шлёт 6068 и себе (`sub_4C28F0`), и окружающим (`sub_52E6D0`).

**Всё это — дефекты оригинала. Чиним и помечаем** (закон `fix-original-defects`).

## КТО ИНИЦИИРУЕТ СНЯТИЕ И ПОЧЕМУ ИМЕННО ТАК

**Инициатор — ОТПРАВИТЕЛЬ (P23 в `DBPatch.dll`), а не этот приёмник.** Доводы, каждый
сам по себе решающий:

1. **GameServer не знает прежнего держателя.** Поля «текущий владелец звания 65…69»
   в образе нет: сплошной проход по тракту славы дал только маски на игрока
   (`CUser+0x17DDC` «получено», `CUser+0x17E00` «найдено») и таблицу `FameInfo`
   (`0x7DFFD4` число записей, `0x7DFFD8` указатель). Записи «кто носит» нет нигде.
2. **Прежний держатель может быть офлайн или на другом процессе** (Indun_GameServer,
   соседний канал). У этого процесса нет ни его `CUser`, ни его маски.
3. **Маска хранится в базе** (`dbo.CharFameBank`, процедуры `UPCharFameBankUp` /
   `UPCharFameProgressUp`). Единственный, кто может снять звание у офлайнового игрока, —
   сторона базы. Она же ведёт `dbo.FameRatingHolder` и потому уже знает и прежнего, и
   нового держателя.

### Разделение ответственности (согласованный контракт)

| кто | что делает |
|---|---|
| **P23** (`DBPatch.dll`, DBManager) | ведёт `dbo.FameRatingHolder`; при смене лидера **ВСЕГДА** пишет базу — снимает бит у прежнего и ставит новому (и, если снятое звание было надето, чистит активный слот прежнего); затем шлёт 3404…3408 **всем подключённым GameServer**'ам ради живых сессий |
| **P24** (здесь) | применяет присланное к тем, кто **сейчас онлайн здесь**, и доводит до клиента немедленно |

Порядок безразличен, операция **идемпотентна**: снятие у уже снятого — тихий выход
(«звание … уже снято» в `PatchLog`), а `SubFameBit` со своей стороны тоже отправит в
базу 2256/2257 с тем же результатом.

★ **Снятие у офлайнового игрока делает база, и это структурная необходимость,**
а не деление работы: у GameServer для офлайнового UserIndex нет ни `CUser`, ни маски, ни
DB-пакета, который не адресуется живой сессией (`userNum`). Когда такой игрок войдёт,
`recvDBUserFameBitInfo` пришлёт ему уже урезанную маску — штатным стоковым путём,
править для этого нечего.

## КАК ОТЛИЧИТЬ «ВЫДАТЬ» ОТ «СНЯТЬ»

★ **Новых опкодов не заводится.** В записи уже есть флаговый байт (+12), который сток
читает и никуда не девает:

```
0054D859  8A 4A 0C   mov cl, byte ptr [edx+0xC]
0054D85C  88 4D D4   mov byte ptr [ebp-0x2C], cl     ; ★ и БОЛЬШЕ НИГДЕ
```
Проверено сплошным дизассемблированием всей функции `0x54D710…0x54D960`: обращение к
`[ebp-0x2C]` **ровно одно, и оно на запись**. Значение байта назначаем:

* **0 — ВЫДАТЬ** (стоковый блок повторён байт в байт);
* **1 — СНЯТЬ**.

Почему так, а не новым опкодом: снятие у прежнего и выдача новому едут **одним пакетом,
в одном порядке**, без второй площадки в диспетчере — его эпилог `0x43462B` уже занят
P21 (приём ответа 2332).

### userNum отправителю знать необязательно

`UserIndex (i32) ≠ userNum (i16)`: userNum — номер **живой сессии**, свой у каждого
GameServer, меняется при каждом входе; стороне базы он неизвестен. Поэтому приёмник
ищет игрока сам, по UserIndex: таблица сессий — `менеджер + 0x40 + 4*userNum`
(сверено в `sub_5324A0` @`0x5324CC  cmp dword [edx+ecx*4+0x40],0`), предел `0x226` = 550
(`sub_5328F0` @`0x5328FF  cmp ecx,0x226`; совпадает с cap 550 LoginManager).

**★ ИСПРАВЛЕНО 30.08.2026. Договора `userNum = 0xFFFF` НЕ СУЩЕСТВУЕТ** — это была ошибка
документа. Константа `kUserNumUnknown = 0xFFFF` в коде объявлена, но **нигде не
используется**: поиск по `UserIndex` (`ResolveFameUser` → `FindUserByUserIndex`) включается
по факту «стоковый указатель не подошёл», а не по значению `0xFFFF`.

**Как на самом деле.** `sub_5328F0` пропускает только `0 ≤ (i16)userNum < 0x226`, то есть
**0…549**. Значение `0xFFFF` (= −1) проверку НЕ проходит: `sub_5324A0` вернёт `nullptr`,
а `sub_54D710` сделает `break` и **выбросит весь остаток списка записей**, а не пропустит
одну. Поэтому запись с негодным `userNum` слать нельзя вовсе.

Признак «слать нельзя» — **`-1`** (его же отдаёт представление в базе). Отправитель P23
фильтрует такие записи тремя рубежами и для этих игроков правит маску прямо в базе
(`UPCharFameBitDis`), пакет не отправляя.

### Почему стоковый путь не может пострадать

* ветка «выдать» повторяет вытесненный блок **дословно**, включая `push` регистров с
  мусором в старшем слове (обе функции принимают i16) — при флаге 0 поведение прежнее;
* оба трамплина заходят по `jmp`, кадр вызывающей функции не трогается, `ebp` тот же;
* SEH-состояние `[ebp-4]` не меняется: при пропуске записи мы идём в обычный конец
  цикла, а деструктор кадра (`0x49BF20`) вызывается ровно один раз на нормальном
  выходе `0x54D941` — как и раньше;
* сплошной скан переходов внутрь площадок: единственный — `0x54D873 jne 0x54D889`,
  и он целиком внутри заменяемой площадки A;
* пока отправителя (P23) нет, опкоды 3404…3408 не приходят вовсе и патч бездействует.

### Прочее

* `Hook.cpp`: буфер `WriteRel32` поднят 32 → 128 байт. Площадка A — 60 байт, при
  прежнем пределе `WriteJmp` молча возвращал `false`. Размер ограничивает только длину
  затираемой площадки; на существующие патчи не влияет.
* `p21_title_mask_512.cpp`: наружу выведены три обёртки (`P21_FameOwned`,
  `P21_SendFameMask6066`, `P21_SendFameMask6086`) — общая точка, чтобы P24 не
  дублировал логику старшей половины маски (закон `port-shared-points`).
  Поведение P21 не изменено.

## ★ МИСНЕЙМ ИСПРАВЛЕН: `CUser+0x174` — это **UserIndex**, а не charId

Поле `CUser+0x174` (372), которое возвращает `sub_5324F0` и которое сверяет приёмник
3404…3408, документ P21 называет `charId`. Это **миснейм** (закон
`false-negatives-method`: имена врут). Строки журнала самого сервера:

```
ClanMemberLeaveReq(3) BaseUserIndex=%d ServerUserIndex=%d BaseCharIndex=%d ServerCharIndex=%d
        ← аргументы: *(DWORD*)v8, *(DWORD*)(pUser + 372), BaseCharIndex, *(BYTE*)(pUser + 396)
Recv_User_Notice_Read(2) Server_UserIndex=%d Packet_UserIndex=%d   ← *(DWORD*)(result + 372)
```
⇒ `CUser+372` = **UserIndex** (индекс аккаунта), `CUser+396` = индекс персонажа в
аккаунте (0…2). Клиент сверяет это же поле как `InventoryBag->userIdx`.
Отправитель P23 берёт его из SQL-колонки `Userindex` — совпадает.

На поиск по этому полю миснейм не влияет: у одного аккаунта в игре одновременно
только одна сессия, значит совпадение всё равно единственное.

**Доработка (площадка A).** Порядок разбора записи: точное совпадение
`UserIndex` + слот персонажа (`CUser+0x18C`, `sub_532530@0x53255D`) → подсказка `userNum`
из пакета (принимается только при совпадении `UserIndex` и, если слот задан, слота) →
совпадение по одному `UserIndex` **только когда слот не задан**. Если слот задан, а
точного совпадения нет — запись не применяется.

Слот берётся из «резервных» байт записи **+10…+11**: сток читает их в старшее слово
`[ebp-0x30]` и не использует. Договор с P23: `0` — «слот не задан», иначе `Charidx + 1`.

**Новая площадка C — `0x54D710`, 5 байт (`55 8B EC 6A FF`), ключ `LogRecv`.**
Трамплин на входе приёмника пишет диагностику в **штатный** журнал сервера через
`sub_569DF0(25, …)` — то есть в `Log/Log_Title/Title_ГГГГММДД.txt`:

```
P24 RECV  op= len= N= rem= pkt=            ← ДО всех гейтов функции
P24 REC #n title= flag= userIdx= slotRaw= userNum= val= -> exact|hint|userIdx|off|no …
P24 GRANT title= userNum=
```
Строки ASCII-транслитом намеренно: журнал пишется как есть, а `.cpp` собирается с
`/utf-8`. Если `GRANT` есть, а `Add Before Title` нет — отказал сам `AddFameBit`.
