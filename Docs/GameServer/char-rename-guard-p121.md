# P121_CharRenameGuard: предмет смены имени не тратится через 5450 + P68 в режиме отказа

AsdaPatch (номер Config — от координатора: v73 занят P120, параллельно идёт P118), 09.11.2026, пачка 20, баг 8. Решение владельца: «Да, P121».
Исходник: `Patches/AsdaPatch/src/patches/p121_char_rename_guard.cpp`. Разбор всего потока смены имени: `Reports/batch20/rename/REPORT.md`.
Проверка: `tools/verify_p121.py`. Выкладка: `tools/deploy_p121.py` (DLL) + `tools/deploy_p68_mode1.py` (ini, вызывается из него).

## Причина

Предмет смены имени — Function_Table категория 111 (`Special_ItemList` 357 «Character name change item», премиум).
Оригинальный клиент шлёт для него не 5450, а пакеты окна 7900: 6138 (проверка имени) и 6140 (смена). Клиент порта до alpha-7.0.0
включительно подтипа 111 не знает и шлёт 5450:

| Шаг | Где | Что делает сток |
|---|---|---|
| 5450 | `Char_FunctionItem_Use@0x4ED780`, `switch(категория − 15)` @0x4EDEB3…0x4EDEE5 | категория 111 → индекс 96 → байт 11 → `default` 0x4EE5A1 (LABEL_69) |
| БД | DB 2140 (`0x5646C0`, `UPInvenUse`) | предмет списан, строка в `JoyLog1.dbo.UseFunctional`; имя не меняется |

Живой журнал dev: 4 траты 357 через 5450 (20.10 Userindex 75211, 03.11 Userindex 2 ×2, 08.11 Userindex 75215), записей
`CharEvent 'Rename'` — ни одной.

## Правка 1 — отказ 5450 для категории 111 (код)

Площадка `0x4EDEB3`, 6 байт `89 85 04 FD FF FF` (`mov [ebp-2FCh],eax`; eax = категория +8 строки Function_Table, загружена
`0x4EDEAE movzx eax, byte [edx+ecx+8]`) → заглушка `St_RenameGate`. Категория == `Subtype` (ini, по умолчанию 111):
`[ebp-121h] = RefuseCode` (ini, по умолчанию 0), переход на общий выход отказа `0x4EF0C3` — 5451 длиной 68. В DBManager ничего
не уходит, предмет цел. Иначе — та же инструкция и продолжение `0x4EDEB9`.

- **Клиент:** код 0 в 5451 → нотис 12837 «Не удалось использовать инструмент» / «Failed in using a Functional Item»
  (оригинал `netRecvItemBuffApply@0xF23C60` case 0; порт — `AsdaInventorySubsystem_Net.cpp` таблица `{0x00, 12837}`, есть в alpha-7.0.0).
  Следующий выпуск клиента 5450 для 111 не шлёт вовсе (поток окна 7900, ключ `asda.Rename.Flow`).
- **Журнал:** строка `[P121]` в `Log_Func` (канал 8) на каждый отказ, ключ `FuncLog`.
- **Откат:** `[P121_CharRenameGuard] Enabled=0` и рестарт, либо прежняя DLL.
- ★ **22.11.2026 — общая точка с P129** (журнал и заглушка чата, [chat-log-p129.md](chat-log-p129.md) §2). Площадка `0x4EDEB3`
  ставится и при `Enabled=0`, если включён P129 (`[P129_ChatLog] Enabled=1`, `ShoutItemHook=1`); тогда P121 возвращает «выключен»,
  проверка категории 111 не действует, но заглушка стоит. Для категорий 0x31/0x32 (крик предметом) `P121_Gate` спрашивает
  `P129_ShoutRequestGate`: заглушка чата и `Mode=1` → тот же отказ `0x4EF0C3` с **общим** `RefuseCode` (по умолчанию 0 → нотис
  12837), предмет цел; строка `[P121]` в FuncLog на этот отказ не пишется (журнал — `joylog1.chat.message`). Без площадки совсем —
  `Enabled=0` у P121 и P129 выключен (или `ShoutItemHook=0`).

## Правка 2 — P68_CharNameGuard в режим 1 (ini)

Проверка имени до DB-агента уже есть с 13.10 — P68 (`p68_char_name_guard.cpp`): 6138 `0x55D8CE`, 6140 `0x55DC6C`, 2453 `0x55DFDF`;
правило — как у создания персонажа (A-Z a-z 0-9 при `NameCharset=0`; пусто, без нуля в 20 б, управляющие байты — отказ;
апостроф, кавычки, пробел не проходят). Но на стойке `Mode=0` — только журнал. P121 ставит `[P68_CharNameGuard] Mode=1`:
6138 → 6139 флаг 3 (клиент: 109404), 6140 → стоковый хвост 6141 код 0 (клиент: 109411), «6140 только после 6138 с тем же
именем» — тоже отказ. Операторы (GM-флаг, как P47) — без проверки (решение владельца 13.10).
Журнал P68 на dev 09.11: событий 53/54/55 в `joylog1.ac.other` — 0, строк `P68 CharNameGuard` в Log_Item — 0: честных игроков
режим 1 не задевает (alpha-7.0.0 6138/6140 не шлёт; новый клиент шлёт 6138 и 6140 с одним именем по тому же правилу).
Откат: `deploy_p68_mode1.py --rollback` (Mode=1 → 0).

## SQL-подстановка в DB-агенте (аудит)

`DBManager.exe.c`: 25 мест `EXEC … '%s'`, 24 берут строку из тела пакета (UPNickCheck, UPCharRename, UPCharIntroUp,
UPSoulMateNoteInput, UpClanNoticeUp, UPClanMemoUp, UPPetRename, UpCharLocationSave/Rename, UPCashitemBuy, клановые и др.).
Все закрыты живым DBPatch **P28_SqlArgEscape** (`DBManager\ConfigSet\dbpatch.ini` Enabled=1, PatchLog 09.11 `[OK]`): апостроф
внутри `'…'` меняется на обратную кавычку на входе сборщика `sub_447720`. Единственный `%s` вне кавычек —
`EXEC UPSMSkillCoolTimeUP %d, %d, %s` (sub_42EF80) — собирается только из чисел. Новых мест для P121 нет.

| P117 | 0x4ED9CF (чтение), 0x4EE25B (case 120) | нет; категория 120 проходит P121, case 120 после switch |
| P97 | 0x4EE218 / 0x4EE221 | нет (после switch) |
