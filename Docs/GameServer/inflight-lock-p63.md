# P63 — общий замок «запрос в БД в полёте» (InFlightLock)

Волна A7 античита «экономика / предметы / рыбалка-лут-квесты», 2026-10-12. Механизм L2 плана (`00_PLAN.md` §8), приоритет A6;
находки `02_parts/economy2_handlers.md` «Топ-5» п.5, `02_parts/fishing_loot_quests.md` FISH-2 / FISH-5 / QUEST-3.
Код: `AstoryServer/_archive_waves/AsdaPatch_w60_p63/src/patches/p63_inflight_lock.cpp`. Проверка: `tools/verify_p63.py`, стенд `tools/stand_p63/`.
Логи прогонов: `Reports/anticheat/wA7_logs/p63_verify.txt`, `p63_stand_mode0.txt`, `p63_stand_mode1.txt`.
[СЕРВЕР-ДОРАБОТКА] — протокол не меняется, новых пакетов и кодов нет.

## 1. Дыра

У 25 обработчиков состояние меняется только в приёме ответа DBManager; сам обработчик проверяет память и шлёт запрос
(`sub_5646C0`). Пока ответ в пути, повтор того же пакета проходит все проверки заново и даёт второй запрос в БД
(двойная покупка/разборка/награда/смена имени/…). Свой замок в стоке есть только у 5018/5020 (`gap_145[11]`),
5033/6500 (`gap_145[15]`) и 6504 (P33 N-2). Честный порт шлёт один запрос до ответа (`FAsdaReplyLatch` у питомцев,
`asda.Disassembly.SingleInFlight` и т. п.) — замок на честном пути не срабатывает (стенд: 50 запросов/ответов, 0 срабатываний).

## 2. Что делает

Таблица `g_lock[слот 0..0x225][семья]` = (UserIndex, такт). Привязка к UserIndex: другая учётка в слоте — замок чужой, не действует.
Тайм-аут `LockTimeoutMs` — потерянный ответ БД не запирает семью навсегда.

## 4а. Цепочка P62 → P63 на общих площадках (интеграция integ2, 2026-10-12)

**Конфликт.** P62 и P63 перехватывают ОДИН И ТОТ ЖЕ `call sub_5646C0` (E8 rel32, отправка в DBManager) в пяти обработчиках:
6096 @`0x55AE4F`, 6506 @`0x501A5C`, 6549 @`0x535202`, 6555 @`0x5376F3`, 6112 @`0x4590C7`. До integ2 P62 ставился первым
(по реестру), P63 видел изменённый rel32 → `MISMATCH P63 @0x0055AE4F: ожидалось [e8 6c 98 00 00]` → все 25 семей P63 не ставились.

**Решение — общая точка в `Patches.h`** (как цепочка L06→L03 в LoginPatch):
* у стаба P62 на каждой из шести площадок отправки (5018 + пять общих) — свой слот «следующий вызов» (`g_next*`, по умолчанию
  `sub_5646C0`); на проходе стаб уходит в него **хвостовым `jmp`** (раньше — вложенный `call` с копией 5 аргументов): стек,
  `ecx` = CUserMoveManager, `ebp` = кадр обработчика и **адрес возврата в обработчик** — побайтно как у стоковой `call`;
* P63 при установке видит rel32 → стаб P62 **этой** площадки (`P62_SendStubAt(va)`), байты не пишет, исходные сверяет по
  таблице P62 (`P62_SendOrigAt(va)` = его `sendBytes`), кладёт `St_Send` в слот (`P62_ChainSend(va, St_Send)`);
* P62, если ставится ПОСЛЕ P63 (rel32 → `St_Send` P63, `P63_SendStubAt(va)`, исходные байты таблиц совпали), забирает
  площадку себе и кладёт `St_Send` в слот — порядок в рантайме тот же;
* выключен один из двух (или площадка ключом `Sell5018…PetUnion6112` / `Lock<op>`) — второй ставит площадку сам по стоковым байтам.

**Порядок в рантайме: P62 (уникальность) → P63 (замок) → `sub_5646C0`.** Отказ P62 (Mode=1) уходит в стоковое тело
отказа обработчика — до P63 управление не доходит, замок «в полёте» НЕ ставится (иначе семья была бы заперта до тайм-аута
без ответа БД — правило «не защёлкивать состояние заранее»). `St_Send` площадку по адресу возврата не определяет: семья — по
опкоду БД `[esp+4]`, слот — `[esp+20]`, `this` — из кадра `ebp`; вход через P62 и напрямую одинаков.

Экспорт для стендов: `P62_GetSendNext(va)` — цель слота «следующий вызов» (0 — площадка не у P62). Лог установки:
P62 — «цепочек с P63 при установке N» (N>0 только если P63 встал раньше), P63 — «из них через P62 5» и по строке
«<обработчик> (<op>) — цепочка через P62 @0x…: P62 → P63 → sub_5646C0» на каждую общую площадку.

**Проверено:** `stand_map` на трёх образах — P63 Applied (48 своих диапазонов + 5 через P62 = 53 площадки), записей двумя
патчами 0, пересечений байт 0, `CHAIN` ×5 = `St_Send`, 5018 → `sub_5646C0`; прогон «без каждой записи по очереди» — общих VA
только P62/P63 (5, цепочка) и P53/P57 (2, известная цепочка). `verify_p63.py` §5 — unicorn с инструкции `call` обработчика:
через P62 (чисто+пропуск / чисто+подавление / отказ) и напрямую, стек/регистры/адрес возврата, `P63_OnSend` видит один и тот
же вход — 5/5. `stand_p63 <Mode> both|rev|p62|p63` — оба порядка установки, только P62, только P63, Mode 0 и 1: нарушение
уникальности в Mode=1 → тело отказа, замок не поставлен, следующая честная заявка без «дубля»; Mode=0 → журнал P62, замок
поставлен и снят ответом. Логи `Reports/anticheat/wINTEG2_logs/`.

  в тот же слот и успела поставить замок той же семьи до прихода запоздалого ответа A — замок B снимется раньше (одно лишнее окно

  кванте таймера — замок казался просроченным. У P63 исправлено (`tick = now ? now : 1`); у P33 N-2 та же ловушка осталась
  (дубль в пределах одного кванта 15 мс проходит) — отдельная правка P33.
