**Симптом (юзер, 2026-08-06).** Успешная заточка анонсируется, **неудачная не показывается
нигде** — ни в HERO_NOTICE, ни в дубле в ленте чата.

**Звено, на котором рвётся: СЕРВЕР.** Клиент пакет с тегом 5 не получал ни разу.

[15.06.52] LogAsdaNet: 6131: 'GM_sitxovski' предмет 66618 (src=4 ступень=8 процент=70)

### 1.2 Сервер: хук СРАБОТАЛ, но отсёкся порогом

`Log\Log_Item\ItemLog_20260806.txt` (диагностика P11):

18:06:00 ServerNotice OK Src 4 …                     ← зелёный анонс ушёл
18:06:00 Refine ARM  User 1 Code 66618 Plate 1 Slot 17 Lv 7

Управление до нас доходит (`Refine IN`, `Ok 0`), код/plate/слот прочитаны верно, но
**`Lv 0 Pct 0`** ⇒ проверка `level < RefineThresholdLevel(6)` отбрасывает анонс.

### 1.3 ПОЧЕМУ ноль — из декомпила (корень)

Функция `sub_4FEE50` = `Recv_User_ShellItemUpgrade` (`RE/ida/server_work/GameServer.c:98627+`).
`v33[60] @ [ebp-0x220]` — 57-байтовая запись предмета; отсюда `[ebp-0x208] = rec+24` (ступень),
`[ebp-0x205] = rec+27` (процент) — это **поля той же записи**, а не отдельные локалы.

Ветка НЕУДАЧИ (`if (v38 <= v71)`, вход `0x4FFFC5`) **обнуляет предмет**:

```
0x004FFFC5  c68538feffff08       mov  byte  [ebp-0x1C8], 8      ; результат «неудача»
0x004FFFCC  …                    ; ++rec+25 (счётчик попыток)
0x00500009  c685f8fdffff00       mov  byte  [ebp-0x208], 0      ; ★ rec+24 СТУПЕНЬ := 0
0x00500010  66c785fbfdffff0000   mov  word  [ebp-0x205], 0      ; ★ rec+27 ПРОЦЕНТ := 0
0x00500019  c685f9fdffff00       mov  byte  [ebp-0x207], 0
```

(в C: `GameServer.c` — `v33[26]=…; v33[24]=0; *(_WORD*)&v33[27]=0; v33[25]=0;` в ветках
`v17 == 2` и `v64 == 1 && itemtable+36 == 3`).

Наш хук стоит **ПОСЛЕ** этого — на `0x500602`, куда сходятся обе ветки. Значит на неудаче он
по определению читает уже обнулённые ступень и процент.

#### ⚠ ПОПРАВКА К ТЗ (проверено дизассемблером при реализации 2026-08-06)

Первая редакция этого документа утверждала «при неудаче предмет сбрасывается в +0» без оговорок.
На самом деле **сброс происходит НЕ всегда** — он стоит в двух под-ветках:

| условие | адреса сброса | смысл |
|---|---|---|
| `0x004FFFDC cmp dword [ebp-0x2C0], 2` | `0x004FFFE5…0x00500031` | вид улучшения **2** — «купон» (`sub_532B10`, задаётся на `0x004FF5B5`) |
| `[ebp-0x151] == 1` **и** `ItemTable(0x5F5E98)[+0x24] == 3` | `0x0050005C…0x005000A8` | вид **1** — свиток-предмет (`sub_532A90`, `0x004FF4D5`), и только когда счётчик попыток `item+25` дошёл до предела `ItemTable(0x7DFFC4)[+0x92]` (флаг взводится на `0x004FFBFF`) |
| иначе | `0x005000AB mov byte [ebp-0x271], 1` | сброса НЕТ, ступень/процент остаются прежними |

Для патча это безразлично: снимок берётся ДО любой из под-веток, а в «несбрасывающем» случае
`preLevel == level`. Живой тест 2026-08-06 попал в сбрасывающий случай (`Lv 0 Pct 0`).

Показывать надо значение **ДО попытки** — то, что игрок потерял (в `Reports/hero_notice_format.md §3`
записано «процент остался прежним» — неверно для сбрасывающего случая). Клиент уже поправлен под
это (комментарии `asda.Hero.Announce.FailShowPercent`), формат пакета не меняется.

## 2. ЧТО СДЕЛАТЬ

### 2.1 Новая площадка — вход ветки НЕУДАЧИ, `0x004FFFC5` (7 байт)

| адрес | сток | стало |
|---|---|---|
| `0x004FFFC5` (7 б) | `C6 85 38 FE FF FF 08` → `mov byte [ebp-0x1C8], 8` | `E9 xx xx xx xx` + 2 × `90` → `jmp` в трамплин DLL |

Возврат — `0x004FFFCC`. Трамплин обязан выполнить вытесненную инструкцию
(`mov byte ptr [ebp-0x1C8], 8`) перед возвратом — ровно тем же приёмом, что уже применён у
`kRefineSuccess` (7-байтовая площадка `0x500602`).

**Безопасность площадки (перепроверено при реализации — перебор ВСЕХ кодировок `rel8`/`rel32`/`jcc`/`loop`
по `.text` `0x401000…0x583000` стока `4e20f0ad…` + скан ВСЕХ DWORD по всему образу):**

* ссылок ровно на `0x4FFFC5` — **две**, обе на первый байт: `0x4FFF16 jl` и `0x4FFF2A jbe`
  (это две половины 64-битного сравнения `v38 <= v71`, третьих входов в ветку нет);
* внутрь `0x4FFFC6…0x4FFFCB` — **ни одного** перехода. Единственное срабатывание байтового
  сканера (`0x50003D → 0x4FFFCA`) — ложное: этот байт является операндом `jne 0x5000B2`
  инструкции `0x50003C` (`75 74`), проверено дизассемблированием;
* абсолютных ссылок / записей таблиц переходов на диапазон — **0**;
* область функции `0x4FEE50…0x5007F0` в живом `GameServer.exe`, в стоке
  `GameServer.exe_before_mine_patch.exe` и в `RE/ida/server_work/GameServer.exe` —
  **байт-в-байт идентична** (живой отличается от стока всего 85 байтами, все в области
  инъекции импорта `0x1A5800+` и в `DataDirectory`).

**★ Доказательство, что снимок всегда «свой» (проверено при реализации):**

1. CFG-обход функции `0x4FEE50…0x5007F0` от входа: `0x500602` достижим; при «перерезании»
   ОБЕИХ веток исхода (`0x4FFF30` успех / `0x4FFFC5` неудача) — **НЕдостижим**
   (1313 инструкций → 856). Ранние отказы уходят `jmp 0x5007C0` до хука.
2. Обратных рёбер (циклов) в функции — **0** ⇒ одна попытка улучшения на один вызов.
3. Записи во флаг `ok` `[ebp-0x112]`: `0x4FEEE8 := 0` (пролог) и `0x4FFF3A := 1` (только успех).

⇒ `ok == 0` в хуке ⟺ управление прошло ровно через площадку снимка.
Проверки ключа `code/plate/slot` и окна времени оставлены как защита от единственного пути,
где ветка неудачи взведена, а до хука не дошли: `0x5000B2 → 0x5000BE jl → лог + 6505 + выход`.

### 2.2 Что делает трамплин

`pushad` → прочитать по `ebp` (кадр функции цел, `ebp` наш):

| данные | адрес |
|---|---|
| запись предмета (57 б) | `lea eax, [ebp-0x220]` |
| **ступень ДО попытки** | `movzx eax, byte  [ebp-0x208]` |
| **процент ДО попытки** | `movzx eax, word  [ebp-0x205]` |
| userNum (индекс игрока) | `movsx ecx, word ptr [ebp+8]` (`arg_0`) |

→ положить в статический массив снимков на `0x226` записей по `userNum` (та же граница, что у
`g_arm`; без аллокаций), поля: `code`, `plate`, `slot`, `preLevel`, `prePct`, `tick`, `valid` →
`popad` → выполнить вытесненную инструкцию → `jmp 0x004FFFCC`.

### 2.3 Правка `AsdaOnRefine` (хук `0x500602`, существующий)

В ветке **неудачи** (`ok == 0`):

1. взять снимок `g_pre[userNum]`; считать его действительным только если `code/plate/slot`
   совпадают с текущей записью и `GetTickCount() − tick` мал (хватит того же
   `RefineFailWindowSec`); иначе — писать строку `Refine PREMISS …` и использовать текущие
   (обнулённые) значения, как сейчас;
2. **проверку порога** `level < g_thresholdLevel` вести по `preLevel`, а не по прочитанному в
   хуке `level`;
3. в тело 6131 класть `preLevel` (`+25`) и `prePct` (`+26`);
4. после выдачи анонса — `valid = false`.

Ветка **успеха** не меняется (там `[ebp-0x208]/[ebp-0x205]` уже содержат новые значения, и это
верно: анонсируем достигнутую ступень).

### 2.4 Диагностика (в `Log_Item`, к существующим строкам)

| строка | когда |
|---|---|
| `Refine PRE User %d Code %d Plate %d Slot %d Lv %d Pct %d` | снимок сделан (вход ветки неудачи) |
| `Refine PREMISS User %d pre(code %d plate %d slot %d) vs cur(…)` | снимок не подошёл |

Строку `Refine IN` дополнить: печатать и снимок, чтобы «до/после» было видно в одной строке.

### 2.5 Ключи ini — новых НЕ требуется

Действующие значения на живом уже подходят: `RefineEnabled=1`, `RefineThresholdLevel=6`,
`RefineFailEnabled=1`, `RefineFailRequiresPriorSuccess=0`, `RefineFailWindowSec=600`.

⚠ Отдельно (к этому патчу не относится, но видно в логе установки): файла
`ConfigSet\announce_codes.txt` на живом **НЕТ** (проверено 2026-08-06) ⇒ источники

## 2bis. ЧТО РЕАЛЬНО СДЕЛАНО (реализация 2026-08-06)

**Номер патча НЕ менялся** — это доработка **P11**: та же секция `[P11_ServerAnnounceSources]`,
тот же флаг `RefineFailEnabled`, новых ключей нет. Отдельный `Enabled` тут был бы вреден:
снимок без потребителя бесполезен, а потребитель без снимка — это ровно текущий баг.

**Изменённые файлы:**

| файл | что |
|---|---|
| `AstoryServer/Patches/AsdaPatch/src/SrvApi.h` | `Hooks::kRefineFailEntry = 0x004FFFC5` + разбор безопасности площадки; `Frame::kRefinePct/-Tries/-Result/-UserId`, `kItemRecPct` |
| `AstoryServer/Patches/AsdaPatch/src/patches/p11_announce_sources.cpp` | `struct Pre` + `g_pre[0x226]`; `AsdaOnRefinePre`; `RefineFailPreTrampoline`; правка ветки неудачи `AsdaOnRefine`; 5-я площадка в списке сверки и установки; форматы `Refine PRE` / `Refine PREMISS`; строка `Refine IN` расширена полями `PreLv/PrePct/PreValid` |
| `AstoryServer/Patches/AsdaPatch/src/dllmain.cpp` | якорь `P11 вход неудачи заточки` в паспорте образа |
| `AstoryServer/Patches/AsdaPatch/src/patches/Registry.cpp` | комментарий: этап 8 = доработка P11 |
| `AstoryServer/Patches/AsdaPatch/tools/verify_dll.py` | трамплин `P11-5` + площадка `P11e 0x004FFFC5` |

**Собранный трамплин (дизасм из готовой DLL, `verify_dll.py`):**

```
pushal
pushfd
movzx eax, word ptr [ebp - 0x205]      ; процент ДО броска
push  eax
movzx eax, byte ptr [ebp - 0x208]      ; ступень ДО броска
push  eax
lea   eax, [ebp - 0x220]               ; запись предмета (код/plate/слот)
push  eax
movsx ecx, word ptr [ebp + 8]          ; userIdx
push  ecx
call  AsdaOnRefinePre                  ; __stdcall, ret 0x10 — стек сбалансирован
popfd
popal
mov   byte ptr [ebp - 0x1c8], 8        ; вытесненная инструкция стока
jmp   dword ptr [...]  -> GameServer 0x004FFFCC
```

**Чем гарантируется, что успешная ветка не сломана:**

* площадка `0x4FFFC5` физически лежит в ветке НЕУДАЧИ; ветка успеха идёт `0x4FFF30…0x4FFFC0 jmp 0x5000B2`
  и площадку не пересекает;
* трамплин `AsdaOnRefinePre` только пишет в `g_pre[]`, ничего не рассылает;
* в `AsdaOnRefine` при `ok != 0` снимок **не читается** — анонсируются `level/pct` из кадра,
  как раньше; снимок гасится (`p.valid = false`), чтобы не тянуть хвост от давней неудачи,
  не дошедшей до хука;
* при `RefineFailEnabled=0` пятая площадка **вообще не ставится** (`wantPre = g_refine && g_refineFail`),
  байты стока в этом месте остаются нетронутыми;
* `Config::kVersion` **не поднимался** (новых ключей нет) — грабля «Version не поддерживается,
  все патчи выключены» не воспроизводится; `dllmain.cpp` и так сверяется с `Config::kVersion`.

**Сверка байтов:** пятая площадка добавлена в тот же `VerifyAllSites(L"P11", …)`. Несовпадение →
`P11` получает `Mismatch` и НЕ ставится, остальные 10 патчей ставятся штатно (поведение каркаса).

## 3. КАК ПРОВЕРИТЬ ПОСЛЕ ПРИМЕНЕНИЯ

1. `Log\Log_Patch\PatchLog_<дата>.txt` — `установка патчей (13 в реестре)`, тринадцать `[OK]`
   (как и в запуске 2026-08-06 08:55:39); в паспорте образа якорь
   `0x004FFFC5  P11 вход неудачи заточки  c6 85 38 fe ff ff 08`; после строки параметров P11 —
   `P11: снимок ступени/процента ДО броска (0x004FFFC5) — ПОСТАВЛЕН…`;
   и (если положен файл кодов) `P11: таблица кодов загружена: …\ConfigSet\announce_codes.txt, диапазонов 609`;
2. заточить предмет до ступени ≥ 6 → зелёная строка (как сейчас);
3. **сорвать следующую попытку** → в `Log_Item`: `Refine PRE … Lv 8 Pct 70`, затем
   `Refine IN … Ok 0 … Lv 0 Pct 0 PreLv 8 PrePct 70 PreValid 1` и
   `ServerNotice OK Src 5 … Lv 8 Pct 70`; в клиенте — `6131: … (src=5 ступень=8 процент=70)` и
   **красная** строка в HERO_NOTICE + дубль в ленте чата;
4. проверить, что предмет действительно упал в +0 (сброс — штатное поведение оригинала для
   вида улучшения 2 / исчерпанного счётчика попыток), а в строке показан процент ДО срыва;
5. строк `Refine PREMISS` быть не должно — если появились, снимок к попытке не привязался
   (смотреть напечатанные `pre(...)` vs `cur(...)`).
