# P123 — GM-прыжок на другую карту по клетке (AsdaPatch Config v77, 09.11.2026, пачка 20)

**Статус:** внесено в общий src поверх живой v76 (5330a12a); собрана кумулятивная **v77 = `475e0c071d433c2e54e47346ce1799b8`** (P01…P122 + P123),
закреплена `tools/p123_data/AsdaPatch_v77_475e0c07.dll`. **Не выложено** — выкладка координатором: `tools/deploy_p123.py`
(сухой прогон, `--apply`, `--rollback`, `--check-started`). Данных и SQL нет.
Решение владельца «Да, P123». Просьба: GM Ctrl+ЛКМ по карте мира или мини-карте — перенос на любую карту в любую точку.
Разбор стока и клиента: `Reports/batch20/gm_teleport/README.md`.

## Как было (сток GameServer e7b4ac38 = Indun = Ch2)
- 6010 `CharJumpCommandPosition@0x54EF50`: тело 4 б (i16 X, i16 Z), гейты слот / `sub_52ECF0` (UserIndex 0…5000) / анти-повтор / MD5 по 4 б;
  `IsCheckPosInMaxPos` → ближайшая проходимая клетка спиралью `sub_41EC30` → 4056. **Только своя карта.**
- 6014 Meet — перенос к игроку (Relay 6016/6017 → 6015); 6084 — смена канала на своей карте и клетке. Переноса «карта + клетка» нет.
- Живой dev: `OperatorLog_20261101.txt` — `CharJumpCommandPosition() Send Ok` и `Send_MeetCommand() Send Ok` работают.

## Что делает P123
Площадка `0x54EF50` (9 б пролога `push ebp; mov ebp,esp; sub esp,80h`) → заглушка `St_Jump` → `P123_OnJump(mgr, userNum, кадр)`:
- **признак формы P123** — тело 8 б: i16 X, i16 Z, i16 карта, u16 метка `0xA123` на месте `кадр+39`; кадр ≥ 42 б. Всё прочее (в том числе
  стоковая 6010 с паддингом клиента 0…19 б, кадр 38…57 б) — **сток без изменений**: пролог исполняется в заглушке, возврат на `0x54EF59`.
  ⚠ По длине формы различать нельзя: паддинг клиента делает стоковый кадр 40…57 б; в паддинге — нули, поэтому метка там не совпадёт.
- гейты формы P123: слот; `sub_52ECF0` (UserIndex 0…5000) **и** GM-флаг `sub_52ED50 == 1` (как P47 `kOperator`, повторно — чтобы не зависеть
  от P47); анти-повтор `sub_524390`; MD5 тела по 8 б `sub_523F00`. Не оператор / нет флага / конверт — молча (как у стока).
- ⚠ Список ниже — v77; в v79 сняты отказы «очередь отряда/RoseWar» и «закрыта в OpenMapInfo» (см. раздел v79).
- отказы (строка `P123: … refused …` в Log_Operator, ответа клиенту нет — у стоковой 6010 его тоже нет): карта = своя (для неё стоковая форма);
  GM в очереди отряда/RoseWar (3 слота `CUser+0x3F43C`, как 6014); своя карта — RoseWar; карта вне MapInfo; тип карты не 0/1/3/6; закрыта
  в OpenMapInfo; нет записи Total_PortalConfig; нет активного потока этой карты в процессе; клетка вне карты назначения или рядом нет проходимой.
- клетка проверяется **на CMapManager карты назначения**: поток карты ищется так же, как `SearchThreadInfo` (менеджер потоков `0x60AD18`,
  `sub_4A83A0`, активность `[TM+18h]`, карта потока `[TM+1D569Ch]+2Ch·i+11h`, поток `[TM+8]+13851C8h·i`, CMapManager `поток+0Ch`,
  ширина/высота `+8/+0Ah`) и проходится той же спиралью `sub_41EC30`, что даст `CharPortalMake` на прибытии (за краем карты она даёт −1,
  и `CharPortalMake` персонажа не ставит — поэтому проверка до отправки обязательна).
- успех: **5055 код 1** (53 б, раскладка `sub_40DE70` 1:1, как P120): IP и порт из Total_PortalConfig[карта], номер карты, клетка прибытия =
  найденная проходимая. Клиент штатно: 5056 старой карте, 5058 новой с клеткой → `CharPortalLogonReq` → `CharPortalMake`. Строка
  `P123: CharJumpCommandPosition(Map) Send Ok …` в Log_Operator. Точку возврата (DB 2235) не пишем — GM, не вход на спецкарту.
- Соседи: P41 сверяет `0x54EF59` и ставит `0x54F2F6` — не пересекаются; P47 (гейт диспетчера) и P55 (6010: 38…57 б) кадр 42 б пропускают.

## Ревизия (09.11.2026): блокеров нет; мелкие ограничения (не исправлялись — решение за координатором)
1. Заполненность карты назначения не проверяется (сток `SearchThreadInfo`: MapInfo+0x38 ≤ число игроков → вход отклонён). При полной карте
   GM уже ушёл со старой (5056) и попадёт на экран входа. Стоковый `RecvContinent_PortalMove` тоже не проверяет; предел 1000 — на dev недостижим.
2. Карта типа 6 (шахта) доступна только при включённом P120: без него у неё нет постоянного потока, P123 отказывает («no active thread»).
3. Состояние GM перед уходом не проверяется (мёртв, обмен, лавка) — как у стокового портала; функция только для операторов.
4. Два Ctrl+щелчка через > 250 мс дают два 5055; клиент после первого уходит со старого соединения — вреда не ожидается, не проверено.
5. Точка возврата (DB 2235) намеренно не пишется; RoseWar как цель запрещён.
Не проверено: приём клиентом незапрошенного 5055 код 1 после 6010 на живом (раскладка та же, что у P120 и стока) и работа с двумя каналами.

## ★ v78 (09.11.2026): живой отказ v77 и исправление — `de6f269397c4a2d6df8ee851091422c6`
- **Симптом.** Выкладка v77 в 16:35. В 18:29 GM_sitxovski (UserIndex 1, карта 0, клиент alpha-7.2.0) дважды отправил Ctrl+клик → карта 3 (46,240) и (62,238). Журнал клиента: «→6010 … карты 3 (P123) -> OK». На сервере ни одной строки P123 (ни Send Ok, ни refused); Hide того же GM в 18:28:36 прошла.
- **Причина.** `sub_52ED50` — `char __thiscall`: на `0x52ED98` выполняется `mov eax,[ebp-8]` (указатель CUser), затем `mov al,[eax+…]`, и старшие 24 бита `eax` — мусор. P123 v77 объявлял его как `int` и сравнивал с 1, поэтому у любого настоящего GM срабатывала ветка «не оператор» — молча, без журнала. Стенд не поймал ошибку: заглушка возвращала чистый `int`.
- **Правка.** GM-флаг берётся через общую точку `P47_IsGmUser` (`char`, SEH; та же у P68/P69/P73). Отброшенные кадры (не оператор, анти-повтор, MD5) пишут строку в Log_Operator. Клиенту ответа по-прежнему нет: текст причины не шлём (решение владельца). Config v78, новых ключей нет.
- **Стенд.** Заглушка `sub_52ED50` возвращает `0x0B7A5Exx`, как живая функция. v77 на ней даёт 25/7 (живой отказ воспроизведён), v78 — on 32/0, off 10/0, mismatch 3/0 на трёх образах. `verify_p123` 31/0.
- **Выкладка.** `tools/deploy_p123r2.py` (сухой прогон, `--apply`, `--rollback` / `ASDA_P123R2_ROLLBACK=1`, `--check-started`). Прежняя версия = живая v77; DLL закреплена в `tools/p123r2_data/`.

## ★ v79 (09.11.2026): «не пускает на элитные карты» — снят ложный гейт очереди
- **Симптом (v78, живой Log_Operator).** В 19:36:11 прыжок 0 → 3 прошёл (`Send Ok`). Все следующие с карты 3 — на 16 (Fireway Forest) в 19:42 и на 7 (Flammio) в 19:44 — получили отказ «registered in a squad/RoseWar queue».
- **Причина.** `CharPortalLogonReq@0x52CBE0` переписывает 3 байта `CUser+0x3F439` и 3 слова `CUser+0x3F43C` из байтов 12…20 тела 5058. Оригинальный клиент (`net_sendSpawnFieldSelect`) кладёт туда состояние CampWar по слотам (`g_pCampWarClan`, без записи −1). Порт-клиент `SendCharPortalLogonReq` оставляет нули. После первого же перехода слоты становятся 0, и гейт P123 «≥ 0 — в очереди» (взят с 6014 Meet) отказывает на любую карту. Тип карты ни при чём: Queen 8, Chess 9, t_ 10/11, Mountain 12, Desert 14, Dragon 15, Fireway 16, Chaos 17 и Inferion 18 — типа 0 или 3, открыты, есть в Total_PortalConfig.
- **Правка (только путь P123).** Гейт очереди снят: стоковый портал эти слоты тоже не проверяет. Закрытая в OpenMapInfo карта GM-у не запрет, строка `Send Ok` помечает это. Закрытые карты (20 eventfield, 21 fieldofhonor, 22 quizstage; 19 battlefield режется по типу 4) не получают потока при старте (`SetUserInfo_ThreadID_Mapping@0x4A538F` их пропускает), поэтому обычно для них отказ «no active thread». ⚠ Ревизия: поток может появиться позже — `SearchThreadInfo@0x4A8450` при входе 20000 на карту типа 0/1/3 без потока создаёт его, OpenMapInfo там не смотрит. С этого момента P123 пустит GM и туда; на прибытии открытость никто не проверяет. Для операторского пути это сочтено допустимым. Шахта 23 — только при P120.
- **Запрет сохранён:** RoseWar (тип 4, battlefield 19), и как цель, и как текущая карта. На прибытии `CharPortalMake` для типа 4 ведёт ветку RoseWar (DelSquadUserInfo, DB 2461, `sub_467620` < 0 → персонаж не ставится), так что вход вне сценария события ломает его. Инстансы (тип 2) не тронуты — таких карт в MapInfo нет.
- **Не тронуто:** обычные порталы, вход игроков, NPC-телепорты, 6014 Meet. У 6014 тот же ложный отказ после перехода — это сток, отдельный вопрос.
- **Дефект порт-клиента (за рамками задачи, решение за владельцем).** 5058 шлёт нули в слотах CampWar вместо состояния регистрации или −1. Сервер после каждого перехода считает любого игрока записанным в слот 0 очереди CampWar/отряда.
