## Симптом → диагноз

`NpcServer` и `Indun_NpcServer` — это **один и тот же бинарь**, запускаемый `start.bat` в **одной интерактивной сессии**. Оба создают именованные waitable-таймеры с **одинаковыми** именами:

| Имя | Где создаётся | Сколько объектов |
|---|---|---|
| `AI_ProcessThread ServerIndex %03d, MapIndex %03d` | `sub_456300 @0x456300` (`NpcServer.exe.c:57643,57647`), `SetWaitableTimer(..., period=30 ms)` | по числу AI-потоков (21) |
| `WaitableTimer` | Manager-поток `sub_44D620` и Queue-поток `sub_44E550` (`:52047`, `:52556`) | 2 |

Имя формируется из `GameServerThreadIndex` и `MapIndex` (подтверждено по декомпилу `sub_456300`) — **не** из `Channel_Index`. У обоих процессов `ini\AIInfo.ini` → `ConnectThreadCount = 21` и одинаковый набор карт, значит индексы совпадают полностью (различие `Channel_Index` 0 vs 1 в имя НЕ попадает).

Безымянные объекты ядра без префикса живут в `\Sessions\<N>\BaseNamedObjects`, т.е. **общие для обоих процессов**. `CreateWaitableTimerA` с существующим именем возвращает **тот же объект ядра**; таймер создан как **auto-reset** (`bManualReset = 0` в `sub_456300`), а auto-reset будит **ровно один** ждущий поток. Итог: два процесса делят период 30 мс пополам → **каждому фактически 60 мс**, частота AI вдвое ниже проектной.

`GameServer.exe` этих строк не содержит (проверено по обоим билдам) — коллизия только между двумя NpcServer.

## ЧТО изменено (адреса и байты) — только в копии `Indun_NpcServer`

Длины строк сохранены байт-в-байт, поэтому смещения ничего не сдвигают.

| Смещение | Было | Стало |
|---|---|---|
| `0x00075A70` | `AI_ProcessThread` (16 симв.) → полная строка `AI_ProcessThread ServerIndex %03d, MapIndex %03d` | `Indun_AIProcThrd` (16 симв.) → `Indun_AIProcThrd ServerIndex %03d, MapIndex %03d` |
| `0x00072794` | `WaitableTimer\0` (14 байт) | `IndunWaitTmr\0\0` (14 байт) |
| `0x000727D8` | `WaitableTimer\0` (14 байт) | `IndunWaitTmr\0\0` (14 байт) |

Формат-спецификаторы `%03d` сохранены на местах — `sprintf` работает как раньше.

## Почему именно так, а не «другая сессия»

Отчёт предлагал развести процессы по сессиям (`psexec -s` / отдельная учётка). Проверено и отклонено как более инвазивное:

- `BaseNamedObjects` — **пер-сессионное**, а не пер-пользовательское пространство. Запуск от другого пользователя в **той же** сессии коллизию НЕ снимает. Помогла бы только другая сессия (напр. session 0 через задачу планировщика как SYSTEM).
- Session 0 = **нет окна/консоли**: администратор теряет визуальный контроль над `Indun_NpcServer`, плюс `start.bat` пришлось бы разделять на два разных механизма запуска.
- Правка 3 строковых литералов **в отдельном файле-копии** даёт тот же результат детерминированно, не трогает архитектуру запуска, `start.bat` остаётся единым, откат = возврат одного файла.

## Проверка безопасности

- `OpenWaitableTimer*` в бинаре **отсутствует** — имена используются исключительно при создании, никто по ним объекты не ищет. Межпроцессной синхронизации по этим именам нет.
- Имена таймеров нигде не логируются и не сравниваются со строками-константами.
- Ограничение: правка применена **только к копии Indun**; main-копия сохраняет старые имена, что и требуется (разводим пару).
