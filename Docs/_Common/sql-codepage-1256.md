## Симптом

Любой русский текст, который серверная часть пишет в базу, сохранялся как `????`:
подпись игрока («Написать о себе»), сообщения чата в журнале, имена персонажей при
создании, названия, девизы и объявления кланов, клички питомцев, заметки соулмейта.

## Диагноз

Базы игры имеют **арабскую** кодировку (`Arabic_CI_AS`, кодовая страница 1256) — сервер
изначально арабский. Запросы строятся подстановкой текста в шаблон вида
`EXEC UPCharIntroUp %d, %d, '%s'`, то есть текст едет **обычным литералом**, без пометки
«это Юникод». Дальше:

```
vsprintf в CHAR[4100]
  -> MultiByteToWideChar(CP_ACP, …)        ← кодовая страница МАШИНЫ (1251)
  -> ICommandText::SetCommandText (UTF-16)
  -> SQL Server приводит литерал к varchar по кодировке БАЗЫ (1256)
```

Русские байты становились кириллическими символами, а обратного пути в 1256 у кириллицы
нет — каждый символ превращался в `?`. Порча происходила **до** входа в хранимую
процедуру, поэтому ни процедуры, ни типы столбцов ни при чём. Арабский ввод, к слову,
сейчас гибнет ровно так же.

**Что проверено до правки:**

* кодовая страница машины сервера — 1251 (реестр `…\Nls\CodePage`: `ACP=1251`);
* кодовая страница 1256 **обратима для всех 256 байт** (проверено программно; у 1251,
  для сравнения, один байт круговой путь не переживает);
* обратный путь (чтение) чист: строковые колонки идут байт в байт
  (`DBTYPE_STR` из `DBCOLUMNINFO.wType`, у DSN стоит `AutoTranslate = No`) — подтверждено
  и кодом, и живой пробой: с байтами `0xF2E5F1F2` в столбце игра показала «тест»;
* прикладной вызов `MultiByteToWideChar` в каждом образе **ровно один** — остальные
  сайты принадлежат библиотеке времени выполнения;
* все **23** шаблона запросов начинаются со слова `EXEC`.

## Что делает патч

Подменяет кодовую страницу ровно в этом вызове: 1256 вместо системной. Круговой путь
становится точным, и байты, присланные клиентом, доходят до столбца нетронутыми. Клиент
читает их своей кодировкой и видит правильный русский; арабский тоже начинает доходить
целым.

**Базу, схему, хранимые процедуры и уже записанные данные патч не трогает** — ни одного
байта не переписывается и не переосмысляется.

### Как устроено

Косвенный вызов `call dword ptr [слот]` (6 байт) заменён на `call <площадка>` + `nop`,
а в нулевом хвосте секции `.text` появилась площадка из 28 байт:

```asm
push eax                        ; сохранить
mov  eax, [esp+16]              ; lpMultiByteStr — сам текст запроса
cmp  dword ptr [eax], 'CEXE'    ; начинается с EXEC?
pop  eax                        ; (pop флаги не меняет)
jne  дальше                     ; нет — кодовая страница остаётся прежней
mov  dword ptr [esp+4], 4E8h    ; да — подставить 1256
дальше:
jmp  dword ptr [слот]           ; хвостовой прыжок в настоящую функцию
```

Стек не сдвигается, адрес возврата на месте, настоящая функция снимает свои 24 байта
сама — вызывающий код ничего не замечает. Проверка `EXEC` — страховка на случай, если
через ту же точку когда-нибудь пойдёт посторонний текст.

### Адреса

Якорь перед правкой — десять байт `6A 00 6A 00 FF 15 <слот>` (два нулевых аргумента:
флаги и кодовая страница `CP_ACP`, затем сам вызов). Сверен на живых копиях всех образов.

## Почему не через DLL

Механизм `AsdaPatch.dll` (инъекция в таблицу импорта) здесь не сработал: у всех пяти
образов в хвосте секции `.rdata` **нет места** под новый блок дескрипторов импорта —
`inject_import.py` отказывается. Реализация на C++ написана и компилируется
(`AstoryServer/Patches/AsdaPatch/src/patches/p17_sql_codepage.cpp`), но в реестр патчей не включена;
если инъекцию в эти образы когда-нибудь удастся сделать, патч включается одной строкой.

Попутно в загрузчик добавлен отбор патчей по образу-хозяину (поле `hosts` в `PatchEntry`):
без него патчи GameServer, попав в чужой процесс, давали бы ложные несовпадения.

## Порядок применения

1. **Бэкап.** Скопировать каждый оригинал рядом с ним как `<имя>.exe.bak_cp1256_20260824`.
2. Остановить процессы: `DBManager`, `RelayServer`, `Indun_RelayServer`, `LoginManager`,
   `OperationServer` (проще — остановить сервер целиком через `stop_servers.bat`).
3. Скопировать готовые файлы из `AstoryServer/Patches/AsdaPatch/out/p17/` поверх оригиналов:

   | Файл | Куда |
   |---|---|
   | `DBManager.exe` | `DBManager\` |
   | `RelayServer.exe` | `RelayServer\` **и** `Indun_RelayServer\` |
   | `LoginManager.exe` | `LoginManager\` |
   | `1LoginManager.exe` | `LoginManager\` |
   | `OperationServer.exe` | `OperationServer\` |

4. Запустить сервер.

## Как проверить

1. Сохранить подпись «о себе» русским текстом → в базе
   `SELECT CONVERT(VARBINARY(128), Intro) FROM dbo.CharIntroduce` должны лежать байты
   cp1251 (для слова «тест» — `0xF2E5F1F2`), а не `0x3F3F3F3F`.
2. Написать русское сообщение в чат → таблица журнала чата (`UPUserChat`, RelayServer).
3. Создать персонажа с русским именем (LoginManager).
4. Убедиться, что **старые арабские строки** читаются клиентом ровно как до патча —
   обратный путь не менялся, но подтвердить стоит.
   базе: если найдётся текстовый столбец с кодировкой **не** `Arabic_*`, на нём патч не
   подействует (при записи в столбец происходит ещё одно приведение) — такому столбцу
   нужен точечный обход.

## Откат

Вернуть 6 байт по адресу вызова из таблицы выше (столбец «Было») либо просто подменить
exe из резервной копии `*.bak_cp1256_20260824`. Площадка в хвосте `.text` сама по себе
безвредна: если вызов не переправлен, она никогда не исполняется.

## Риски

* Совпадение таблиц кодовой страницы 1256 у Windows и у SQL Server проверено только со
  стороны Windows (обратимость всех 256 байт) — сторона сервера проверяется пунктом 1.
* Столбец с чужой кодировкой (пункт 5 проверки).
* Логи серверов пишутся напрямую, без перекодировки, и остаются в 1251 — SQL-текст в них
  по-прежнему читается как кириллица. Это правильно и ничего не ломает.
* GameServer, NpcServer, ChannelManager и OverlapCheckServer в базу не ходят и не
  затронуты. `ItemRelayServer` ходит, но текста игрока в его запросах нет — не трогаем.
