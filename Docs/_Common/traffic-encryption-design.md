## 1. Схема (по образцу TLS, решения владельца)

```
  Клиент UE                         Прослойка в серверной DLL            Старый под-сервер
  ─────────                         ─────────────────────────            ─────────────────
  ClientHello  ───────────────────▶ ServerAccept (подпись ECDSA)
  (эфемерн. ECDH-ключ, nonce)       ServerHello (эфемерн. ключ,
                                     nonce, ПОДПИСЬ закрытым ключом)
  ClientFinish ◀───────────────────
  (проверка подписи вшитым
   открытым ключом сервера)
       ├─ ECDH → общий секрет ──────────── ECDH → тот же секрет
       └─ HKDF-SHA256 → ключи c2s/s2c, базовые IV ─┘
  ── AEAD-кадры (AES-256-GCM, seq) ──────▶ расшифровка → старый кадр FB..FE ──▶ CopyToWriteBuffer
  ◀─ AEAD-кадры ─────────────────────────  шифрование ◀── старый кадр из Ciocp::Send ◀──
```

1. **Долговременная пара сервера — ECDSA P-256.** Закрытый ключ только в файле рядом с DLL
   (`server_private.key`, формат `ASDAKEY1` + d(32) + XY(64) = 104 б), в код НЕ попадает,
   подгружается при старте DLL. Открытый ключ вшит в клиент (`server_public.h`, вывод `keygen`) —
   клиент проверяет подпись `ServerHello` и этим подтверждает подлинность сервера (защита от посредника).
   (Исходная идея «RSA-пары с закрытым ключом в клиенте» владельцем отклонена: ключ в клиенте извлекаем.)
2. **Эфемерный ECDH P-256 на КАЖДОЕ подключение.** Обе стороны генерят временную пару, обмениваются
   открытыми точками, `BCryptSecretAgreement` даёт общий секрет; на диск он не пишется.
3. **AEAD — AES-256-GCM** с номером пакета (`seq`) против повтора. Отдельные ключи направлений
   (c2s, s2c) и базовые IV, выведенные HKDF-SHA256 из общего секрета, обоих nonce и обоих ключей.
4. **Прослойка в нашей DLL** для каждого под-сервера принимает зашифрованный поток, проверяет,
   расшифровывает и отдаёт старому серверу текущий протокол без изменений; исходящий — наоборот.

### Привязка подписи
Сервер подписывает `(клиентский ePub ‖ серверный ePub ‖ идентификатор под-сервера)`. Это привязывает
подпись к конкретному рукопожатию (нельзя переиграть старую запись) и к под-серверу (ключ логина не
годится для подмены игрового сервера, хотя пара одна — под-сервер входит и в подпись, и в HKDF-info).

## 2. Форматы

| Структура | Размер | Поля |
|---|---|---|
| ClientHello | 84 б | magic=0xA5(1) ver(1) subServer(1) flags(1) ePubXY(64) nonce(16) |
| ServerHello | 148 б | magic=0x5A(1) ver(1) subServer(1) flags(1) ePubXY(64) nonce(16) sig_r‖s(64) |
| AEAD-кадр | 28+N б | len:u32(=N+16) seq:u64 ciphertext(N) tag(16) |

- **IV кадра** = базовый IV(12 б) XOR big-endian(seq) в младшие 8 байт. seq уникален → IV уникален
  (требование GCM: nonce не повторяется под одним ключом).
- **AAD** = `len‖seq` (12 б) — заголовок кадра под защитой тега, подмену длины/номера тег поймает.
- **Anti-replay**: TCP упорядочен, поэтому принимающая сторона требует `seq == rxSeq+1`. Повтор,
  перестановка и потеря кадра → отказ (канал закрывается). Окно битовой маски не нужно.
- **Накладные байты**: ровно **28 на кадр** (12 заголовок + 16 тег). Рукопожатие — разовые 84+148 б.

## 3. Криптография — только Windows CNG (bcrypt.dll)

Требование владельца: серверные DLL собираются `/MT` без внешних зависимостей, та же библиотека
работает в UE-клиенте под Windows. Никаких OpenSSL/libsodium.

| Назначение | CNG |
|---|---|
| ECDH P-256 | `BCryptOpenAlgorithmProvider(ECDH_P256)`, `BCryptSecretAgreement`, `BCryptDeriveKey(RAW_SECRET)` |
| ECDSA P-256 | `BCryptOpenAlgorithmProvider(ECDSA_P256)`, `BCryptSignHash`/`BCryptVerifySignature` |
| HKDF-SHA256 | вручную на `BCryptCreateHash(SHA256, HMAC)` (RFC 5869) — не зависит от наличия `BCRYPT_HKDF` в старой ОС сервера |
| AES-256-GCM | `BCryptOpenAlgorithmProvider(AES)` + `BCRYPT_CHAIN_MODE_GCM`, `BCryptEncrypt`/`BCryptDecrypt` с `BCRYPT_AUTHENTICATED_CIPHER_MODE_INFO` |
| RNG | `BCryptGenRandom(RNG)` |

API библиотеки без исключений (коды `AsdaSecure::Err`); провайдеры открываются один раз на процесс.

## 4. Точки врезки (реверс декомпилов, подтверждён на образах)

Проверка: `AstoryServer/Patches/AsdaSecure/tools/verify_sites.py` — байты всех точек ОДИНАКОВЫ на стоке, деплое,
живом образе и Indun (точка стабильна). Декомпилы: `RE/ida/login_work/LoginManager.c`,
`RE/ida/server_work/GameServer.c`.

### LoginManager (15001 → `LoginPatch.dll`)
Рабочий поток IOCP `IoWorkerThread @0x4161E0` крутит `GetQueuedCompletionStatus`. Данные читаются
`ReadFile` в буфер сокета (`sub_416870`), по завершении `NumberOfBytesTransferred` байт лежат по
`&Overlapped[1].Offset`.

| Точка | VA | Роль врезки |
|---|---|---|
| приём, клиентский под-сервер (<10000) | вызов `sub_415600(&ovl[1].Offset, nBytes, num)` в `IoWorkerThread` | **расшифровка**: байты из ReadFile → `ServerChannel::OnRecv` → в `CopyToWriteBuffer` |
| приём, межсерверный (10000..10099) | вызов `sub_415830(...)` там же | то же для соединений между под-серверами |
| `CCircleQ::CopyToWriteBuffer @0x418C00` | `558bec6aff68c8d64200…` | единая функция разбора кадра — расшифрованный поток подаём сюда |
| отправка `Ciocp::Send @0x413AB0` | `558bec6aff6888d44200…` | **шифрование**: единственный choke-point перед `WriteFile`; `Src,nBytes` = готовый кадр FB..FE |
| `Ciocp::SendTemp @0x4141D0` | `558bec6aff68b8d44200…` | дослание остатка буфера — шифровать так же |
| `MakeHeaderSend @0x415860` | `558bec81ece40200…` | сборщик кадра, зовёт `Ciocp::Send` (точку выше не дублировать) |
| `Ciocp::SetConnectFlag @0x4144A0` (accept/disc) | `558bec6aff68e8d44200…` | сюда `ServerChannel::Reset()` на новое соединение и разрыв |

★ У LoginManager BSS в хвосте `.data` (память `loginpatch-dll`): FirstThunk/новые данные класть в `.rdata`.

### GameServer (15601 → `AsdaPatch.dll`), тот же образ — Indun

| Точка | VA | Роль |

Способ врезки — детур площадок по образцу `AstoryServer/Patches/AsdaPatch/tools/verify_ac0.py`
(трамплин: `jmp dword ptr [..]` + вызов C-функции внутри DLL). Состояние канала — массив на 550 слотов
(как `41150*slot`), слот = номер сокета Ciocp.

### Клиент UE
Файл `AstoryClient/Source/AsdaNet/Private/AsdaConnection.cpp` (в этой волне НЕ трогаем). Транспорт —
сырой `FSocket`; приём копится в `RecvBuffer`, кадры выбирает `PacketFrame::Parse` (де-XOR), отправка —
`PacketFrame::Build` (XOR) → `FSocket::Send`. Три точки (см. `client/AsdaSecureClient.h`):
1. `Connect()` после `bConnected=true` → `Start()`, `ClientHello` шлём прямо в `Socket->Send`.
2. `SendPacket()`: собранный `frame` → `OnSend` → в сокет шифротекст (до готовности копится).
3. `Tick()`: принятые байты → `OnRecv` → расшифрованный поток в `RecvBuffer`, дальше `DrainFrames` без изменений.
XOR-слой (`ChannelCipher`) остаётся — шифрование поверх него.

## 7. Риски
- **Производительность**: 0.37 мкс (64 б) … 1.59 мкс (1500 б) на кадр (стенд, см. отчёт) — на фоне
  IOCP-обработки пренебрежимо; память канала ~ (ключи + накопитель) на слот.
- **Совместимость**: пока оба клиента в ходу — Legacy по первому байту; риск только если старый кадр
  начнётся не с `0xFB` (не бывает — маркер фиксирован).
- **Ротация ключа**: новый keygen → новый `server_public.h` → пересборка клиента; на период ротации
  сервер может принимать две долговременные пары (список открытых ключей в проверке подписи) — заложить
  в волне врезки.
- **BSS-хвост LM `.data`**: данные прослойки в DLL/`.rdata`, не в хвост `.data` (память `loginpatch-dll`).
- **Переупорядочивание из-за фрагментации TCP**: не риск — поток байтовый, `Feed/Next` собирают кадр
  из любой нарезки (стенд: побайтовый приём проходит).
