## Восемь правок

### N01_AttackTimer32 — «то атакует, то не атакует»
**VA** `0x45F5A4` (20 б), `0x460151` (17 б), `0x460169` (3 б). Замена байтов.

Античит скорости атаки ХРАНИТ момент последнего удара 32-битным, а СРАВНИВАЕТ по младшим 16.
После паузы дольше ~65 с разность переполняется, удар **молча отбрасывается** (единственный такой
случай в боевом пути), счётчик нарушений растёт, при 30 — отключение игрока. Поле «момент
последнего удара» в ветке отказа не обновляется, поэтому отбрасывается целая серия.

Вычисление переведено в 32 бита. Порог, допуск 100 мс и счётчик нарушений не тронуты.
Разбор: `attack-speed-timer-16bit.md`.

### N02_HateClearDamage — возрождение чистит накопленный урон
**VA** `0x43E42F` (18 б). Замена байтов.

Список угрозы: 20 записей по 16 б с `+31352`; поле `+12` — накопленный урон, им решается, кому
опыт и добыча. Возрождение обнуляло `+0/+4/+8`, а `+12` оставляло от прошлой жизни.
Добавлено обнуление; уложилось в те же 18 байт за счёт снятого выравнивания и `dec` вместо `sub`.
Разбор: `hate-list-stale-damage.md`.

### N03_HateWinnerEntry0 — пустая запись не выигрывает поиск владельца
**VA** `0x437A6C` (6 б). **Врезка.**

Поиск победителя сравнивает самую первую запись **без проверки занятости** (у записей 1..19
проверяет). Пустая запись с мусором могла выиграть → некорректный владелец → терялись опыт,
добыча и квестовый прогресс. Реальное срабатывание: `Exception_20260803.txt:705`.
Пусто — стартуем с заведомо проигрышного значения; занята — как в оригинале.

### N04_DeadMobNoBattle — монстр не бьёт после смерти
**VA** `0x4486E3` (5 б). **Врезка с хвостовым переходом.**

Перед раздачей награды сервер держит секундную задержку и уводит обработку на ветку ЖИВОГО
монстра целиком — вместе с боевым ИИ. Восстановление здоровья там защищено своим признаком
смерти, а вызов боевого ИИ — нет.
★ Аргумент передаётся на стеке и снимается вызываемой функцией (`ret 4`, после вызова нет
`add esp,4`). Поэтому живой путь — хвостовой `jmp`, мёртвый — `ret 4`.

### N05_Hp8202SubtractAccum — здоровье в пакете 8202
**VA** `0x45FEF2` (6 б). **Врезка.**

Приведено к формуле соседнего канала: `здоровье − накопитель`, зажим в 0. См. N08.

### N06_HateSearchOob — поиск по списку угрозы читал за границей
**VA** `0x43D539`, `0x43D5ED`, `0x43D6CC` (по 15 б). **Врезка, три площадки.**

Порог сравнения обновлялся на каждом шаге, включая тот, когда кандидата ещё нет. Тогда адрес
считался на 16 байт РАНЬШЕ начала массива, и порогом становилось чужое поле. Если там большое
число — вытеснять некого, и 21-й участник боя в список не попадал: без опыта и добычи.
Порог обновляется только при найденном кандидате. Одна площадка на все три места: регистры и
признак «кандидата нет» (`cx == 0xFFFF`) везде одинаковы.

### N07_AccumOverkill — пустая полоса у живого монстра
**VA** `0x4427E7` (2 б). Замена байтов.

Первые ~2 с боя урон копится в `+34376`, здоровье `+30853` не меняется. Если удар покрывает весь
остаток, сервер должен записать в накопитель ровно остаток — но там **сложение вместо
присваивания**, и пишется `здоровье + урон`. Накопитель заведомо больше здоровья, разность уходит
в минус, зажимается в 0 — клиент честно рисует пустую полосу у живого монстра.
`add ecx, eax` → `mov ecx, eax`.

### N08_Hp8005SubtractAccum — отскоки полосы вверх
**VA** `0x440F93` (6 б). **Врезка.**

Сервер шлёт здоровье монстра ТРЕМЯ каналами, и они расходились:

| канал | было | стало |
|---|---|---|
| 8204 → 4029 (боевой) | `здоровье − накопитель`, зажим | без изменений |
| 8202 → 4027 | сырое | исправлено N05 |
| 8005 → 4015 (движение) | сырое | исправлено N08 |

Канал движения приходит десятки раз в секунду и в окне накопления тянул полосу обратно вверх.
Теперь все три несут одну величину.

## Модель урона сервера (то, к чему всё сводится)

`CMonster::DamageAndHateCheck` (`sub_4423C0`, `NpcServer.exe.c:47219`):

```c
if ( mob[34368] == 1 && (!mob[34369] || a7 == 1) )   // НАКОПЛЕНИЕ, первые ~2 с боя
{
    v22 = mob[30853];  v23 = a5;
    if ( v22 - a5 <= 0 ) { v23 = v22; }              // ← после N07 (было v22 + a5)
    mob[34376] += v23;
}
else
{
    if ( mob[30853] - a5 > 0 ) mob[30853] -= a5;
    else { …смерть… }
}
```

**Слив накопителя** — `ProcessState` (`:49995`), через 2000 мс: `v12 = здоровье − накопитель`;
`< 0` или равно → смерть, иначе `mob[30853] = v12`.

**Клиенту всегда уходит `здоровье − накопитель` с зажимом в 0** — по всем трём каналам.

Ключевые поля записи монстра:
`+30853` здоровье · `+31288` максимум · `+34376` накопитель · `+34368/34369/34370` режим и флаги
накопления · `+34372` старт окна · `+34380` последний бивший · `+31352` список угрозы (20×16) ·
`+30292` биты состояния · `+36721` признак смерти · `+36722` момент смерти.

## Правила работы с этими правками

- **NpcServer правится только через `AddonNPC.dll`**, exe остаётся стоком. GameServer — через
  `AsdaPatch.dll`. Байтовые скрипты в этой же папке сохранены как запасной путь.
- **Ни одна правка не пишет байты, не сверив оригинал** (`VerifyAllSites`). Не совпало — не
  ставится, в журнал идут оба набора байт.
- ⚠ **Смещения во встроенном ассемблере — только через `#define`.** C++-константа в `[reg + имя]`
  даёт АДРЕС переменной; на этом 24.08.2026 упал живой сервер. Перед каждой выкладкой прогонять
  `tools/verify_trampolines.py` — он читает СОБРАННУЮ библиотеку и сверяет машинный код.
- **Первый запуск после смены exe — с `MasterEnable=0`**: отдельная проверка, что каркас
  поднимается.

## N09_ExpProbe — ДИАГНОСТИКА опыта (не правка)

**VA** `0x437DD1` (6 б, `mov edx, [ebp+7748h]`). **Врезка.** По умолчанию **ВЫКЛЮЧЕНА**.

Ничего не меняет в расчёте. На каждую выдачу опыта печатает в журнал четыре числа:
урон, записанный за игроком (поле `+12` его записи в списке участников); максимум здоровья
монстра (`+31288`); базовый опыт монстра; и что в итоге начислено.

Заведена по жалобе «иногда приходит опыт +1». Формула расчёта разобрана
(`Reports/exp_share_npcserver.md`):

```
опыт = (урон игрока / МАКСИМУМ здоровья монстра) × базовый опыт + 0.9
если разница уровней > 1: опыт −= опыт × (разница − 1) × 0.1
если разница уровней > 6: ветка не выполняется вовсе
```

Округление через `+0.9` превращает любую крошечную долю ровно в **1** — это и есть наблюдаемый
симптом. Замер покажет, какой множитель падает.

**Как снять замер**
1. Подменить `AddonNPC.dll` (md5 `39a7133cc8d9fa5324122e1fd6912134`). `NpcServer.exe` менять
   НЕ нужно — инъекция импорта в нём уже есть.
2. В `ConfigSet\patches.ini` в секции `[N09_ExpProbe]` поставить `Enabled=1`.
3. Перезапустить NpcServer, убить десяток монстров, включая случай с «+1».
4. Выключить обратно (`Enabled=0`) — записей много.

Строки в журнале выглядят так:
`[опыт] урон игрока=…, максимум здоровья=…, базовый опыт=… -> начислено …`

## N10_NormalAttackHateDamage — опыт за обычную атаку

**VA** `0x45FED5` (7 б, `mov cx, [ebx+7694h]`). **Врезка.** Включена по умолчанию.

Опыт делится по накопленному урону: раздача награды считает
`доля = урон игрока (поле +12 его записи) / МАКСИМУМ здоровья монстра × базовый опыт`
и округляет через `+0.9` — любая крошечная доля становится ровно 1.

Урон в список кладёт `sub_4423C0`, но получает его по-разному (сверено дизассемблером,
позиционный разбор декомпила здесь врёт — IDA показывает скрытый `this` не во всех вызовах):

| путь | адрес вызова | что кладётся вместо урона |
|---|---|---|
| навык | `0x004156FD` | `push edi` — настоящий урон |
| обычная атака | `0x0045F6E8` | `push 0` — **ноль** |

В теле `sub_4423C0` первым стоит `if (a5)`, поэтому при нуле пропускается и накопитель, и запись
урона: обычная атака регистрировала только агрессию. Отсюда «убил обычной атакой — опыт 1,
навыком — 56» при одних и тех же уровнях.

**Что делает патч.** Урон обычной атаки существует — он приходит пакетом `0x2009` и лежит на стеке
`Process_AttackToMonster` (`sub_45FCD0`) очередью из четырёх значений, тот же массив уходит клиенту
каналом 8202. Врезка перед отправкой дописывает сумму ПОЛОЖИТЕЛЬНЫХ значений в список участников
тем же вызовом, которым пользуется остальной сервер (отрицательные — это метки промаха и уклонения,
а не урон).

★ Величина УГРОЗЫ не трогается (первый аргумент = 0): она уже начисляется при регистрации агрессии,
и ранжирование списка остаётся прежним. Меняется только накопленный урон, по которому делится
награда.

**Соглашение вызова** `sub_43D2C0` снято с живого вызова `0x004429A2`:
`eax` = угроза · `ecx` = монстр · стек: номер игрока (i16), урон (i32), флаг (i8);
функция чистит стек сама (`ret 0Ch`).

**Регистры на площадке** (с дизассемблера): `ebx` = монстр, `ebp` = игрок (`[ebp+7864h]` = +30820),
очередь уронов `[esp+1Ch…28h]`.

★★ **ДВЕ ПЛОЩАДКИ** (уточнение того же дня: после первой правки «единица» изредка проскакивала).
Сразу за проверкой дальности обработчик расходится:

| ветка | что делает | площадка |
|---|---|---|
| `jne 0x45FE81` | отправляет здоровье каналом 8202 | `0x45FED5` |
| иначе | уходит в `Process_AttackedToMonster` и ВЫХОДИТ, минуя отправку | `0x45FE41` |

Обе идут ПОСЛЕ расчёта урона, очередь в них лежит по одному смещению.

⚠ Исходная инструкция второй площадки читает СТЕК (`mov cx, [esp+16h]`), а внутри врезки на его
вершине лежит адрес возврата от `call` — поэтому воспроизводится со сдвигом +4 (`[esp+1Ah]`).
У первой площадки инструкция регистровая, сдвиг не нужен.

Машинный код обеих площадок сверен: смещения остались литералами, адресов констант нет.
md5 сборки: `83fae5b8d5d0ba831251786e6f29d44d`.

### ★★★ N10 ред. 2 (26.10.2026, слот P90, волна exprate) — [ИСПРАВЛЕНИЕ НАШЕЙ ПРАВКИ]

**Дефект первой редакции (жил с 25.08 по 26.10).** Абзацем выше учтён адрес возврата для ИСХОДНОЙ инструкции
второй площадки, но НЕ для очереди: стабы читали `[esp+40h…4Ch]` = кадр + 1Ch + 24h, без 4 байт адреса возврата
`call`. Фактически в сумму шли `[кадр+18h…24h]`: первым — сохранённый `edi` (`0x45FCE8 mov [esp+18h], edi`) =
указатель `this` обработчика (~2·10⁸, положительный), дальше удары 1–3; удар 4 терялся.

Следствия на живом сервере (сверено по журналам 18–26.10):
- **отряд** (ветка `sub_437A30` без зажима, `0x437ECD`) — доля в тысячи раз больше базы, опыт за КАЖДОГО моба
  упирался в потолок GameServer 1/9 уровня. Случай владельца «неадекватно много опыта в Rain River»: Player14
  (Player15) + Player17, Rein, 19.10 23:27–23:29, StampBlade/GapeCrab — 1380/1756 вместо ~60; GameServer
  `Log_Exp`: `iExp 7010019 … fUpDown 4.52`; игрок шептал «the exp went from 100 to 1000»;
- **одиночка** — урон переваливал через 2³¹ → отрицательный → опыт 1 (`NpcServer\Error_Log\Experience_*`,
  60 записей `Exp -246771496`), иначе зажим до максимума → полный опыт любому, кто ударил хоть раз;
- **владелец добычи** (наибольший урон) решался числом пакетов обычной атаки, а не уроном.

**Исправление.** Очередь `[кадр+1Ch…28h]` = `[esp+44h…50h]` в стабе, все 4 удара; сумму считает
`N10_QueueSum` (насыщение на 7FFFFFFFh): > 0 — урон; −1…−6 и 0 — коды результата; < −6 — крит (бит 31 на
значении, как в 8202 и в стоковом `sub_4423C0`) → `& 7FFFFFFFh`. Ключ `CritHits` (1 по умолчанию; 0 — криты не
считаются, как в ред. 1). Ключа «прежнего чтения» нет сознательно (оно складывало указатель): откат — `Enabled=0`
(сток) или прежняя DLL. Проверки: `tools/verify_n20.py`, `tools/stand_n20` (режим `old` на прежней DLL ловит
дефект: 816 расхождений из 816), `tools/verify_trampolines.py` (запрещённая форма ред. 1).

## N20_PartyShareClamp — доля урона в опыте отряда зажата, как у одиночки (26.10.2026, слот P90) [ИСПРАВЛЕНИЕ]

**VA** `0x437ECD` (7 б: `mov edx,[esp+18h]` / `imul esi,esi,53h`). **Врезка.** Включена по умолчанию.

`CMonster::Process_MonsterDead` (`sub_437A30`, `NpcServer.exe.c:41287-41390`) делит опыт по записи списка угрозы:
`доля = урон (+12) / максимум здоровья (+31288 = +7A38h) × база (+30861) + 0.9`. Ветка ОДИНОЧКИ (`0x437DA6`)
зажимает урон сверху максимумом здоровья (`cmp [ecx],eax / jle / mov [ecx],eax`), ветка ОТРЯДА — нет: доля > 1
даёт опыт сверх базы, отрицательный урон — отрицательный вклад в сумму отряда. В стоке урон в список приходил
только из `sub_4423C0`, уже зажатым остатком здоровья, поэтому дыра почти не проявлялась; с N10 (обычная атака,
перебой последнего удара) и тем более с её ред. 1 — проявилась.

Патч ставит в ветке отряда ровно стоковый зажим одиночки (знаковое сравнение, запись обратно в поле), плюс ключ
`ClampNegative=1` — отрицательный урон → 0. Аномалии (урон < 0 или > 2 × максимума) — журнал `ac.other` **115**
(`item_code` = тип монстра +30808, `value1` = урон до зажима, `value2` = максимум здоровья, `opcode` 8306, `detail`
«N20 base B lvl L map M mob I»), **116** — исключение (поведение стока). Площадка с N09 (`0x437DD1`, ветка
одиночки) и N10 не пересекается; переходов внутрь `0x437ECE…0x437ED3` нет ни в одном из 4 образов.

Проверки: `tools/verify_n20.py` (образы сток `16c7a0af`, IDB `d292e4ec`, живой `c02486d6`, Indun `0de2c559`;
кадр; стабы DLL по `.map`), `tools/stand_n20` — 4 образа × `on/nocrit/noneg/off/mismatch/all` (+ `old`):
настоящий код площадки против модели и ВТОРЫМ МЕТОДОМ — против стокового зажима одиночки (352 точки, 0 расхождений).
Разбор: `Reports/exprate/MOB_EXP_AUDIT.md`. Выкладка: `AsdaPatch/tools/deploy_p90.py` (координатор).

## N21_RespawnFreeTile — монстр при появлении не встаёт в клетку другого монстра (26.10.2026, слот P93) [ИСПРАВЛЕНИЕ]

## N11_GmHideNpc (P39, 2026-09-27) — скрытый оператор невидим для монстров
