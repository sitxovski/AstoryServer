## ЗАЧЕМ (симптом → диагноз)

- **Симптом:** `Frame_Monster()` в `ProcessTime_*.txt` — **медиана 17 813 мс** при бюджете кадра 30 мс, при этом CPU сервера загружен на **2 %** и игроков онлайн 0–2. То есть процесс НЕ считает, а **стоит на блокировке**.
- **Диагноз:** `CAStar::Search @~0x452200` вызывает `OutputDebugStringA` **безусловно на 2 из 3 выходов** (`NpcServer.exe.c:55244` — исчерпан лимит 1000 узлов; `:55257` — «Don't move tile»). `OutputDebugStringA` захватывает **машинно-глобальный** мьютекс `DBWinMutex` и работает через shared-section + пару событий. 21 AI-поток NpcServer + 21 у `Indun_NpcServer` дёргают его сотни раз в секунду → **сериализация всех потоков всех процессов машины**. Это же объясняет `OnUserSearch1 1031 мс, Count 0` (поток просто не получал квант).
- **Почему `SetLastError`:** тот же `kernel32`, тот же `__stdcall`, ровно **1 DWORD-аргумент** → баланс стека идентичен, code-cave не нужен. Функция безвредна (пишет значение в TEB).

## Проверки, выполненные ПЕРЕД правкой

1. **Экспорт подтверждён на самом сервере:** `\\@@ASTORY_SERVER_HOSTNAME@@\c$\Windows\SysWOW64\kernel32.dll` (machine `014C`, 1603 экспорта) — `SetLastError` присутствует. Проверен именно 32-битный kernel32, т.к. `NpcServer.exe` — x86.
2. **Все 19 call-сайтов `OutputDebugStringA`** просмотрены в декомпиле (`RE/ida/npc_work/NpcServer.exe.c`, строки 3222, 4054, 4150, 4606, 4626, 4669, 4867, 5237, 5293, 6305, 6327, 6546, 14189, 14380, 16788, 17157, 55212, 55244, 55257). **Нигде** `GetLastError`/`WSAGetLastError` не читается ПОСЛЕ вызова так, чтобы значение было значимым: во всех сетевых местах код ошибки захватывается в `eax` ДО вызова логгера и передаётся в него по значению (`sub_406C50("...ErrorNo.%d", ...)`). Все `GetLastError` (строки 6118-6138, 10071-10424, 18916, 19968) — стартовые пути файлового I/O и FTP-дампа, читают ошибку сразу после провалившегося API.
   > Побочный эффект: осмысленный отладочный вывод (`SkillStart/SkillEnd`, `Disconnect gameserver`, `Preparation Accept Socket`, статистика A*) **пропадает** из DbgView. Файловые логи (`Error_Log\*`, `sub_408DC0`) НЕ затронуты — они пишутся отдельно.
3. **Нет `IMAGE_DIRECTORY_ENTRY_BOUND_IMPORT`** → нет залоченных адресов, перепривязка не нужна.
4. **PE CheckSum НЕ пересчитывался намеренно:** у оригинала он уже несогласован (`stored=0x00082F84`, реальный `0x00088C28`) — заводской дефект. Алгоритм пересчёта проверен на `kernel32.dll` (совпал бит-в-бит). User-mode загрузчик CheckSum не проверяет. Diff держим минимальным.
