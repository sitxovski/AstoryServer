# NpcServer — возрождение не чистит накопленный урон в списке угрозы

Дата: 2026-08-24. Скрипт: `patch_npc_hate_clear_damage.py`. Статус: **готов, на сервер НЕ применён.**
Накладывается **поверх** `patch_npc_attack_timer32`.

## Симптом

Изредка убийство монстра проходит «вхолостую»: монстр умер, а опыта, добычи и квестового
прогресса нет. Либо добыча достаётся не тому игроку.

## Механизм — два дефекта, работающие в паре

**Список угрозы:** 20 записей по 16 байт, начало `+31352`.

| смещение в записи | тип | смысл |
|---|---|---|
| `+0` | i16 | индекс игрока (`0xFFFF` = запись пуста) |
| `+4` | i32 | |
| `+8` | i32 | |
| `+12` | i32 | **накопленный урон** — им решается, кому награда |

**Дефект 1 — поиск победителя не проверяет занятость первой записи** (`NpcServer.exe.c:41195-41215`):
```c
v3 = 0;                              // победитель по умолчанию — запись 0
v4 = *(int *)(a1 + 31364);           // её урон, БЕЗ проверки занятости
v6 = (int *)(a1 + 31380);            // сравниваем с записями 1..19
do { if ( *((WORD *)v6 - 6) != 0xFFFF ) { … } … }   // ← занятость только у 1..19
```

**Дефект 2 — возрождение чистит запись не полностью** (`sub_43E300`, `NpcServer.exe.c:44956-44964`):
```c
v6 = (DWORD *)(a1 + 31356);  v7 = 20;
do { v6[1] = 0; *v6 = 0; *((WORD *)v6 - 2) = -1; v6 += 4; --v7; } while (v7);
```
Обнуляются `+0`, `+4`, `+8`. Поле `+12` (`a1 + 31364`) **не трогается** — переживает смерть.

⇒ В записи 0 остаётся мусор от прошлой жизни. Если он не меньше урона настоящих участников боя,
победителем объявляется пустая запись, сервер получает некорректный индекс владельца и уходит в
раннюю ошибку. Реальное срабатывание: `Exception_20260803.txt:705` («ItemOwnerIndex is invalid»).

## Правка

Чиним **дефект 2** — он и есть источник мусора. Поиск не трогаем: без мусора он на этом сценарии
перестаёт ошибаться, а переписывать его негде (см. «Почему не чинится поиск» ниже).

VA `0x43E42F`, 18 байт, размер сохранён:
```
было:  90                nop                      ; байт выравнивания
       89 70 04          mov  [eax+4], esi        ; esi = 0
       89 30             mov  [eax], esi
       66 89 78 fc       mov  word [eax-4], di    ; di = 0xFFFF
       83 c0 10          add  eax, 16
       83 e9 01          sub  ecx, 1
       75 ef             jnz  loop

стало: 89 70 04          mov  [eax+4], esi
       89 30             mov  [eax], esi
       89 70 08          mov  [eax+8], esi        ; ★ НОВОЕ — обнуление +12 записи
       66 89 78 fc       mov  word [eax-4], di
       83 c0 10          add  eax, 16
       49                dec  ecx                 ; короче на 2 байта
       75 ee             jnz  loop
```
Три нужных байта взяты из снятого `nop` (1) и замены `sub ecx,1` → `dec ecx` (2).
`esi` в этом месте уже равен нулю — им же обнуляются два других поля. `dec` не трогает флаг
переноса, а следующая за циклом инструкция (`mov eax, [ebp+8]`) флаги не читает.

Сверка: размер тот же, **17 байт в 1 группе** против текущего образа сервера,
**57 байт в 3 группах** против стока (вместе с правкой античита).

| файл | md5 |
|---|---|
| сток | `d292e4ec4edfd5040d8fb39382664eab` |
| после античита (сейчас на сервере) | `fbaacc45bd15335d9440218ddbec73ec` |
| **после этой правки** | `4fc231c8765b80ac9aa434ea3c8d8866` |

## Почему не чинится сам поиск

Добавить проверку занятости в поиск — значит вставить инструкции, а свободного места нет:
в отображаемой части `.text` NpcServer **нет ни одного нулевого или `int3`-участка длиннее
32 байт**. Врезка потребовала бы расширения секции — несоразмерно для работающего сервера.
Если площадка когда-нибудь понадобится для чего-то ещё, чинить стоит заодно и это.

## Применение (делает владелец)

1. Сохранить резервную копию текущего `NpcServer.exe` с датой в имени.
2. Подменить файлом `out/NpcServer.timer32_hate.exe`, перезапустить процесс.
3. Проверка — `Docs/Port/systems/COMBAT_FIX_VERIFICATION.md`, пачка 13.

**Откат:** вернуть резервную копию. Сток лежит в `out/NpcServer.PRE-timer32_d292e4ec.exe`.
