# S6 — «переполнение пула лотов аукциона» (100000): причина НЕ в размере пула

**Дата:** 2026-08-27
**Статус:** ⚠ **ОТКРЫТО. Патч НЕ делается — это дефект ДАННЫХ, лечится чисткой базы.** Диагноз доказан, лечение за владельцем
**Процесс:** `ItemRelayServer` (в декомпиле GameServer и в логах — «TransAction Server»)
**Полный путь образа:** `\\@@ASTORY_SERVER_HOSTNAME@@\h(@@ASTORY_SERVER_HOSTNAME@@_ns)\ASDA\Working_ASDA\v2\ItemRelayServer\ItemRelayServer.exe`
**Тип:** дефект программы + дефект данных; правок в бинарь и конфиг **не вносилось**
**Отчёт-первоисточник:** `Reports\npc_exchange_win_13000.md` §9.6, дефект S6
**Декомпил (сделан 2026-08-27):** `RE\ida\server_work\ItemRelayServer.c` (657 функций, отказов декомпиляции 0), `RE\ida\server_work\ItemRelayServer.exe.i64`

---

## 0. Что утверждал отчёт и что оказалось на самом деле

> Отчёт §9.6: «Пул `ItemTotalCount = 100000` забивается при загрузке лотов из БД, новые
> выставления в этот момент отклоняются. Лечится увеличением `ItemTotalCount` либо чисткой
> просроченных лотов».

**Симптом подтверждён, причина названа неверно.** Пул НЕ забит: на живом сервере лотов около
**1400–2050**, а не 100000. Пул опустошается не данными, а поиском в цикле загрузки, который
натыкается на «недостижимый» индекс в строке БД и вычерпывает весь свободный список за один заход.
Увеличение `ItemTotalCount` в общем случае **не лечит** и делает перебор только дольше.

---

## 1. Доказательства (всё — только чтение живого сервера)

### 1.1 Лотов ~1400, а не 100000

`Error_Log\ItemRelayLog0000_20260808.txt` — это лог самой загрузки из БД. Записей `Regist_Type`
за старт: **1410**, максимальный номер `ItemArray` — **2019** (номера с пропусками).
В `ItemRelayLog0000_20260725.txt` максимум `ItemArray` — **2045**.
⇒ пул на 100000 записей занят примерно на 2 %.

### 1.2 Ошибка возникает ТОЛЬКО в момент старта, внутри загрузки из БД

Файлы `CDirectLinkArray_*.txt` и `CItemManager_*.txt` идут строка в строку, 1:1
(17/17, 5/5, 3/3, 3/3, 4/4, 1/1, 1/1 по дням 25.07, 26.07, 01.08, 02.08, 03.08, 04.08, 08.08):

```
CDirectLinkArray:  ...Get_Empty_ArrayIndex(...) : don't enought array area...! call func (null)
CItemManager:      ...GetItemInfoEmptyPointer() iIndex is incorrect...! iIndex 100000
```

Каждой такой паре в `ItemRelayLog0000_<дата>.txt` соответствует строка
`Process_ItemRegistFromDB() pItemInfo is NULL...!`, и каждой из них предшествует строка `Start`
(перезапуск процесса) за 0,2–18 секунд до неё. За 2026-07-25 — 19 стартов и ровно 17 таких пар.
⇒ отказ происходит **один раз на старт процесса**, в фазе загрузки лотов, и никогда в обычной игре.

### 1.3 Почему индекс ВСЕГДА ровно 100000

`CItemManager::Init` (`sub_401FE0@0x401FE0`, `ItemRelayServer.c:798-830`):
```c
PrivateProfileIntA = GetPrivateProfileIntA("ITEM_INFO","ItemTotalCount",0,".\\ini\\Section.ini");
*((_DWORD*)ArgList + 14) = PrivateProfileIntA;                 // m_iTotalItemCount = 100000
v7 = operator new(112 * PrivateProfileIntA + 4);               // ФИКСИРОВАННЫЙ массив записей
...
sub_401080(ArgList, *((int*)ArgList + 14), 1);                 // CDirectLinkArray::Init(N, autogrow=1)
```

`CDirectLinkArray::Get_Empty_ArrayIndex` (`sub_4013D0@0x4013D0`, `ItemRelayServer.c:190-270`) при
пустом стеке свободных индексов **сам себя наращивает на 20 %** и печатает
`don't enought array area`:
```c
v22 = (float)*((int*)this + 10);       // 100000
v5  = (int)(v22 + 0.2 * v22);          // 120000  ← новая ёмкость ИНДЕКСНОГО массива
... new CStack(v5);                    // стек инициализируется ПОЛНЫМ: 119999..0
if ( *((int*)this + 10) > 0 ) do { sub_4090E0(newStack); ++v3; } while (v3 < *((int*)this+10));
                                       // снимает 100000 уже занятых -> вершина = индекс 100000
```
А массив самих записей (`m_pItemlist`, 112 байт на лот) **не растёт никогда**. Поэтому первый же
индекс после расширения равен ровно **100000**, и `CItemManager::GetItemlistEmptyPointer`
(`sub_4019E0@0x4019E0`, `ItemRelayServer.c:506-540`) его отвергает:
```c
v3 = sub_4013D0((_BYTE*)this, nullptr);
if ( v3 <= -1 || *(_DWORD*)(this + 56) <= v3 )      // 100000 <= 100000  -> ИСТИНА
    ...("GetItemInfoEmptyPointer() iIndex is incorrect...! iIndex %d", v3);   // и возврат NULL
```
Отсюда и «всегда 100000» в логах: это не 100000 живых лотов, а первая ячейка ЗА концом массива.

### 1.4 Что именно вычерпывает пул — цикл поиска точного индекса

`Process_ItemRegistFromDB` (`sub_403A20@0x403A20`, `ItemRelayServer.c:1934-1958`) для КАЖДОЙ строки
БД требует слот с ТЕМ ЖЕ номером, что записан в строке:
```c
v8 = *(_DWORD *)v49;                    // индекс массива, сохранённый в строке БД
while ( 1 )
{
    v9 = (_DWORD *)sub_4019E0((int)byte_4315A0);        // взять очередной свободный слот
    if ( !v9 ) { ..."Process_ItemRegistFromDB() pItemInfo is NULL...!"; goto LABEL_25; }
    if ( v8 == *v9 ) break;                             // *v9 — собственный номер слота
    if ( !(unsigned __int8)sub_409080(*v9) ) { ..."TempStack is NULL...!"; goto LABEL_25; }
}                                                       // мимо -> на ВРЕМЕННЫЙ стек и по новой
```
Свободные слоты выдаются строго по возрастанию 0, 1, 2, …; «промахи» паркуются на временном стеке
и возвращаются в общий пул только в конце ПАКЕТА (`LABEL_25`, `ItemRelayServer.c:2105-2113`).
Значит цикл умеет шагать только ВПЕРЁД. Как только в наборе строк попадается номер, который уже
выдан в этом же пакете (дубликат либо строка не по возрастанию) — или номер вне диапазона
`0…99999` — условие `v8 == *v9` не выполнится никогда, и цикл вычерпывает все 100000 слотов,
после чего срабатывает расширение из §1.3 и приходит NULL.

### 1.5 Последствие, которое видит игрок

При NULL цикл делает `goto LABEL_25` — **прерывается весь текущий пакет загрузки**. Пакет — это
50 строк (`v6 = (len - 10) / 0x66`, размер записи 102 байта). В логе 2026-07-25 первый пакет
загрузил только `ItemArray 0` и оборвался, а следующий начался с `ItemArray 50`:

```
10:18:51:504  RegistDB  Result Start
10:18:51:504  Regist_Type success ... ItemArray 0   ItemIndex 22647 Nick GM_sitxovski
10:18:51:549  Process_ItemRegistFromDB() pItemInfo is NULL...!
10:18:51:567  RegistDB  Result End
10:18:51:568  RegistDB  Result Start
10:18:51:580  Regist_Type success ... ItemArray 50  ItemIndex 22649 Nick THE8GING8
```

⇒ до **49 лотов за каждый перезапуск** остаются в базе, но **не попадают в память** аукциона:
их не видно в поиске, владелец не может их снять, предметы висят заблокированными
(`UpItemExchangeLock`). Именно так «пропадают» выставленные вещи.

### 1.6 Сопутствующие места, где индекс теряется безвозвратно (второстепенно)

- `sub_4019E0@0x4019E0`: при отказе (индекс вне диапазона или `bAvailable != 1`) выданный индекс
  **не возвращается** в пул.
- `sub_4013D0@0x4013D0`: снятие с вершины стека (`sub_4090E0`) выполняется и на ветках ошибок
  `stack pop value is invalud index` / `don't used array index`.
- Ветка отката/таймаута (`ItemRelayServer.c:3392-3396` и `LABEL_37`, `:3485-3490`) на двух путях
  уходит без вызова `sub_401AB0` (возврат слота).

Эти течи реальны, но объяснить наблюдаемую картину (ровно один отказ на старт, всегда индекс
100000) они не могут — она целиком объясняется §1.4.

## 2. Почему это НЕ лечится в `AsdaPatch.dll` / P19

1. Дефект живёт в другом процессе. `ItemRelayServer.exe` (208 896 б) в таблице импорта имеет только
   `WS2_32 / WININET / KERNEL32 / USER32 / GDI32 / ole32 / OLEAUT32` — нашей DLL там нет, доставить
   её потребует отдельной инъекции дескриптора импорта (`AstoryServer\Patches\AsdaPatch\tools\inject_import.py`).
2. Даже с доставкой правильное лечение — привести в порядок ДАННЫЕ: программа отрабатывает ровно
   так, как написана, а ломает её конкретная строка (или строки) в таблице лотов.

## 3. Что делать владельцу (по убыванию приоритета)

1. **Найти дефектные строки в базе `joy1`** (запрос только на чтение). Нужны, по столбцу, который
   `ItemRelayServer` читает как первый DWORD 102-байтовой записи (номер ячейки массива лотов):
   - строки с ОДИНАКОВЫМ номером (дубликаты);
   - строки с номером `< 0` или `>= 100000`;
   - нарушения возрастания в том порядке, в котором строки отдаёт процедура выборки
     (`UpExchangeItem` — именно её имя лежит в `.rdata` `ItemRelayServer` рядом с загрузкой;
     `ItemRelayServer.c:4430`).
   ★ Точное имя таблицы/столбца здесь **не установлено** — доступа к базе у меня нет, а гадать
   нельзя. Определяется по тексту процедуры `UpExchangeItem` в самой базе.
2. **Удалить/починить эти строки** (лоты вернуть владельцам вручную либо через `UPExchangeItemDelete`).
   После этого перезапустить `ItemRelayServer` и убедиться, что в `Error_Log` за день нет ни
   `CItemManager_*`, ни `CDirectLinkArray_*`.
3. **Увеличивать `ItemTotalCount` НЕ НАДО.** Это помогло бы только в одном частном случае — если
   дефектный номер лежит между 100000 и новым потолком. При дубликате или нарушении порядка эффекта
   нет, а перебор станет длиннее.
4. **Чистка просроченных лотов** (`[TIME_INFO] ItemDeleteTime = 14` дней, `UPTimeoutDeleteItem`)
   полезна сама по себе, но к этому отказу отношения не имеет: пул занят на 2 %.
5. **Опционально, кодовое лечение** (если владелец захочет закрыть класс проблемы целиком):
   в `sub_403A20` ограничить цикл поиска количеством живых записей и при недостижимом номере
   пропускать ОДНУ строку, а не обрывать весь пакет из 50. Это отдельный патч для отдельного
   процесса; здесь он **не делался**.

## 5. Риски

- Правка строк в таблице лотов затрагивает реальные предметы игроков: перед удалением строк снять
  их через штатную процедуру снятия лота, иначе предметы останутся заблокированными
  (`UpItemExchangeLock` без парного `UpItemExchangeRestore`).
- Пока причина не устранена, каждый перезапуск `ItemRelayServer` теряет из памяти до 49 лотов
  (в базе они остаются). Ошибка молчаливая: клиент никакого нотиса не получает.
