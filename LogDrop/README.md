# AsdaLogDrop — приём запечатанных журналов клиента (19.10.2026)

Служба Windows на dev-сервере @@ASTORY_SERVER_HOSTNAME@@: принимает от лаунчера `POST https://@@ASTORY_DOMAIN@@/api/v1/ingest` (через Caddy) и
складывает файлы AsdaLogSeal (`.alog`/`.acrash`) в `@@ASTORY_SERVER_ROOT@@\Working_ASDA\v2\LogDrop\`. Протокол — `Reports/release_logs_2026-10-19/00_SPEC.md`
(часть B и «★ Дополнение»), отчёт — `Reports/release_logs_2026-10-19/B_server.md`, ревизия — `REVIEW_security.md` (В1–В3, В6, М1–М5).

> ⚠ **Логин заявлен клиентом и ничем не доказан.** Любой может прислать журнал «от имени» существующей учётки (ключ шифрования
> открытый, конверт без подписи). **Поддельным может быть и само содержимое**: правильно зашифрованный журнал с любым текстом
> собирается открытым ключом. Папка учётки и текст журнала — подсказка для диагностики, а не доказательство против игрока.
> Расшифровка — только на ПК владельца (`AstoryClient/Tools/LogSeal`).

## Схема
```
лаунчер ──TLS──> Caddy @@ASTORY_DOMAIN@@:443  (@ingest: только POST /api/v1/ingest, request_body max_size 4160KiB)
                   └─ reverse_proxy 127.0.0.1:8446 ──> AsdaLogDrop.exe (служба AsdaLogDrop, NT SERVICE\AsdaLogDrop, sidtype restricted)
                                                         ├─ строгий разбор конверта и контейнера (без расшифровки)
                                                         ├─ SQL logdrop_ro (только SELECT Us_member.Us_id, кэш 10 мин)
                                                         └─ LogDrop\<логин>\<ГГГГ-ММ-ДД>\<серверное имя>.alog|.acrash + .json
```
- Язык/сборка: C# 5, .NET Framework 4.x (встроен в Windows Server 2019), без внешних библиотек; `build.bat` → `out\AsdaLogDrop.exe`.
- Слушает **только 127.0.0.1:8446** (TcpListener на Loopback; соединения не с loopback отбрасываются). Брандмауэр не менялся.
- Учётка службы — виртуальная `NT SERVICE\AsdaLogDrop`: привилегии — только SeChangeNotifyPrivilege; **sidtype restricted** — токен
  с ограничением записи: писать можно только туда, где служба указана явно (`LogDrop\` и `service\logs\`), остальной диск — нет,
  даже где у Users есть создание файлов. `LogDrop\service\` для службы — только чтение/запуск; `service\secrets\` — только чтение.
- ACL `LogDrop` — без наследования от `v2`: только Administrators, SYSTEM и служба. У Users нет ни чтения (шара `H:\` открыта
  Everyone на чтение — NTFS этой папки её закрывает), ни создания папок (нельзя заранее подложить папку учётки или джанкшен).
  Инструмент владельца (`FetchAndDecrypt`) ходит по шаре от `@@ASTORY_SERVER_HOSTNAME@@\Administrator` — доступ сохранён (проверено).
- SQL: вход **`logdrop_ro`** по паролю (под restricted SID Windows-вход SSPI не работает — «Cannot generate SSPI context»);
  пароль — 44 случайных символа, создаёт `sql_login.ps1` на сервере, лежит только в `service\secrets\sql_logdrop_ro.txt`
  (ACL: Administrators, SYSTEM — полный; служба — чтение), в командной строке и журналах не появляется. Право — `SELECT` только
  на столбец `AsdaStoryOp.dbo.Us_member.Us_id`. Запрос один, параметризованный: `SELECT TOP (1) 1 FROM dbo.Us_member WHERE Us_id = @id`.

## Что принимается (иначе отказ)
HTTP (свой строгий разбор, одна заявка на соединение, `Connection: close`):
- ровно `POST /api/v1/ingest` (без query), HTTP/1.1|1.0, заголовок ≤ 16 КиБ, только печатный ASCII, без повторов заголовков;
- `Content-Type: application/octet-stream`; `X-Asda-Install` — ровно 32 hex; **обязателен `Content-Length`**, `Transfer-Encoding` запрещён;
- `X-Forwarded-For` (ставит Caddy) — IP клиента для лимитов (берётся последний адрес); `Expect: 100-continue` поддержан.

Конверт **v2** (все числа little-endian; v1 не принимается), **ровно один файл** (`MaxFiles=1`; N > 1 → 400):
`"ASLU" | u8 2 | u8 N=1 | u16 0 | u8 вид (1 игра, 2 EAC, 3 падение) | u8 A (0..32) | A байт логина | u32 L | L байт файла`;
файл идёт ровно до конца тела; 157 ≤ L ≤ 4 МиБ.

Файл — контейнер AsdaLogSeal (формат — `AstoryClient/Tools/asda_logseal.py`), разбор ровно до конца файла:
- сегмент: `ASLGSEG1`, версия 1, байты 10–11 и 120–127 = 0, keyId ∈ `KeyIds` (keyId ключа LogSeal вашего клиента: `ASTORY_LOGSEAL_KEY_ID` из `_setup/configure.bat`, = `AstoryClient/Tools/data/logseal/current.txt`),
  один keyId на файл, ClientHello `A5 01 4C 00`, эфемерный ключ — **точка на P-256** (x, y < p, y² = x³ − 3x + b);
- кадры: `clen` 17..65552, `seq` строго 1, 2, 3… в каждом сегменте, кадр целиком в файле; сегмент без кадров — отказ;
  обрезанный хвост — отказ (лаунчер сам отрезает его до последнего целого кадра);
- вид сегмента ↔ вид файла: игра → только 3 (журнал движка; ★ М2); EAC → 1 или 2; падение → 4 или 5 (перенос старых);
- не больше 4096 сегментов на файл. Теги GCM не проверяются и не могут быть проверены — закрытого ключа на сервере нет.

Логин: формат `[A-Za-z0-9_.@-]{1,32}` → проверка существования (кэш 10 мин, и «есть», и «нет»). Есть → папка
`<логин нижним регистром>`; нет/пусто/неверный формат → `_unknown`. Логин, опасный как имя папки Windows (начинается не с
буквы/цифры, кончается точкой, содержит `..`, имя устройства `con`/`nul`/`com1`…, `service`), → папка `_acct_<hex логина>`.
Итоговый путь сверяется с корнем; папки учётки/даты — не reparse-точки. БД недоступна → 503 (лаунчер повторит позже).

| файлов в конверте | 1 | 400 |
| запросов с IP | 6/час (засчитываются все попытки) | 429 |

| байт всего | 1 ГиБ/сутки | 429 |

| соединений к службе | 32 (сверх — сброс) | — |
| квота хранилища | 5 ГиБ (всё в LogDrop, кроме `service\`) и ≥ 2 ГиБ свободно на томе; при 80 % — `QUOTA WARNING` в `service_` (раз в час) | 507 |
| сроки | заголовок 10 с, тело 55 с, одна операция 5 с | обрыв |

Бюджеты в байтах списываются **только принятым** (отказы их не едят) и переживают перезапуск: при старте восстанавливаются
по `.json` за последние сутки. Порядок (★ В2): путь → IP (счётчик, 1 одновременно) → install → длина/тип → бюджеты IP/install/общий
(проверка без списания) → слот → квота → тело → конверт → контейнер → учётка → лимит и бюджет логина или `_unknown` → общий →
запись → списание. Мусор до БД не доходит. Старое при переполнении **не удаляется** — только по решению владельца.
Пересчёт квоты — раз в 10 мин отдельной нитью (не больше одного; ★ М3), без захода в reparse-точки; пропущенные из-за суточного
предела строки журналов — раз в 10 мин в `service_` (★ М4).

Caddy (глобально для всего :443, с 19.10): `read_header 5s`, `read_body 60s`, `write 70s` (срок записи ответа в Go включает выгрузку
тела, поэтому он больше `read_body`); срок тела в службе 55 с — меньше обоих. Лаунчеру (C) — свой предел запроса ≤ 50 с.

## Хранение
`LogDrop\<папка учётки>\<ГГГГ-ММ-ДД>\<ГГГГММДД-ччммсс>_<16 hex>.alog|.acrash` и рядом `.json`: время (UTC и местное), id запроса,
IP, install, заявленный логин и его статус (`ok`/`not_found`/`none`/`bad_format`), вид, размер, keyId, сегменты, кадры,
виды сегментов, SHA-256. Имена только серверные; файл пишется как `.part` (CreateNew) и переименовывается.
Ничего не распаковывается и не исполняется; папка по HTTP не раздаётся.

Журналы службы: `LogDrop\service\logs\` — `service_<дата>.log` (старт/стоп/ошибки, восстановление бюджетов, предупреждения квоты),
`rejects_<дата>.log` (IP, install, код, причина, Content-Length — **без тела**), `accepted_<дата>.log`; ≤ 20 МиБ в сутки на файл.

## Развёртывание / обновление
1. `build.bat` (локально) → `out\AsdaLogDrop.exe`; `python tests\test_logdrop.py` — 101 проверка + фаззинг (должно быть «провалов 0»).
2. Скопировать в `@@ASTORY_SERVER_ROOT@@\Working_ASDA\v2\_tmp_logdrop_stage\`: `out\AsdaLogDrop.exe`, `README.md` и из `deploy\` — `LogDrop.ini`,
   и сверять хэш: `copy` через ssh+cmd однажды молча не сработал).
3. На сервере: `powershell -ExecutionPolicy Bypass -File <stage>\install.ps1` — служба (создать/обновить, sidtype restricted),
   ACL (снимок прежних — `service\acl_before_review.txt`), SQL-вход `logdrop_ro` и права, запуск. Первая версия каждого файла — `*.bak_20261019_logdrop`.
4. Caddy: правка только блока `@ingest`; бэкап рядом; `caddy validate --config Caddyfile --adapter caddyfile`, затем
   `caddy reload --config Caddyfile --adapter caddyfile` (admin 127.0.0.1:2019, без разрыва соединений).
5. `.ps1` — в UTF-8 **с BOM** (PowerShell 5.1 иначе читает кириллицу как ANSI); caddy из PowerShell — через `cmd /c … 2>nul`.

## Откат (`@@ASTORY_SERVER_ROOT@@\Working_ASDA\v2\LogDrop\service\rollback.ps1`, от администратора; журналы остаются)
- `-ReviewOnly` — только правки по ревизии: Caddyfile ← `.bak_20261019_review` (8MiB), exe/ini ← первая версия, sidtype unrestricted,
- `-TimeoutsOnly` — только сроки Caddy (read_body 5s, write 10s): Caddyfile ← `.bak_20261019_readbody`.
  ACL ← снимок, права службы сняты, `sc delete`.
- Вручную: Caddy — `copy /y Caddyfile.bak_… Caddyfile` → validate → reload; служба — `sc stop/delete AsdaLogDrop`;

списком учёток. Тест `tests\test_logdrop.py` запускает именно так, на порту 18446 и во временной папке.
